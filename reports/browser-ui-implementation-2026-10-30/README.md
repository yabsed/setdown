웹 테마는 Dark Reader의 공개 API, 고정 서브모듈 및 사이트별 수정 목록을 번들링한다. CSS·이미지 읽기는 소유 프레임·문서 토큰·크기·시간 제한이 있는 별도 경로를 사용한다. 사이트에 데스크톱 API를 노출하지 않는다. 원래 엔진의 교차 출처 제한은 유지한다.

엄격한 script CSP에서도 CSSOM 변경을 추적하도록 번들에 포함된 관찰 코드를 페이지 컨텍스트에 설치한다. 비활성화하면 원본 CSS와 프록시 속성을 복구한다. 같은 문서 내 주소 이동과 다른 창으로의 탭 이동 후에도 새 외부 CSS를 처리한다.

Git 호환 기준은 기존 분석 보고서의 VS Code 1.143.0이다. `git.countBadge`, `git.untrackedChanges`, `scm.countBadge` 조합과 동일한 상태 분류를 사용한다. `.vscode/settings.json`의 지원 설정 및 앱에서 지정한 재정의 값을 합성하며, 배지 설정 하나를 바꾸었다고 다른 작업공간 설정까지 고정하지 않는다. 부분 집계는 `+`로 표시하고 실패한 저장소 경로를 보여 준다. 문제의 `test-results/workbench-baseline` 저장소를 삭제하거나 고쳐서 증상을 감추지 않았다.

## Wayland 탭 이동

[Electron 문서](https://www.electronjs.org/docs/latest/api/base-window#wingetbounds)에 명시된 것처럼 Wayland에서는 전역 창 위치를 얻을 수 없다. 별도 headless Mutter에서 두 창을 화면 좌우에 배치했으나 Electron은 두 창 모두 같은 `(10, 10)` 위치를 반환했다. 기존의 원본 창 좌표 변환과 창 순서 추정으로는 대상 창을 신뢰할 수 없었다.

운영체제가 보낸 dragenter/dragover/drop과 수신 창 로컬 좌표로 소유권을 결정한다. 웹을 표시하는 창은 첫 웹 화면을 열 때 가벼운 전용 수신 화면을 준비하고 드래그 중에만 표시한다. 문서만 있는 창은 기존 셸 수신을 사용하므로 별도 렌더러를 만들지 않는다. 생성한 수신 화면은 이후 탭 종류가 바뀌어도 창이 닫힐 때까지 유지한다. 웹 영역 위에는 같은 색과 크기의 가이드를 그리며 페이지를 캡처·숨김·재배치하지 않는다. 수신 화면의 반복 부착도 제거했다. 토큰을 등록한 창만 이동을 완료할 수 있으며 실제 Esc 취소를 무시하지 않는다.

초기에는 표준 MIME 추가 후 웹·문서 각각 12회가 통과했지만, 40회로 확장하자 동일한 실패가 다시 발생했다. MIME 추가는 해결책이 아니므로 철회했고 경로를 plain text로 노출하지 않는 기존 계약을 유지했다. [실패한 40회 검사 기록](wayland-native-fast-failure/run.log)과 [Wayland 프로토콜 기록](wayland-native-fast-failure/wayland-wire.log)을 보존했다.

프로토콜에서는 대상 창 진입 시 `set_actions(0, 0)`을 전송한 뒤, 렌더러가 승인해도 추가 물리적 motion이 없으면 값이 갱신되지 않았다. 이어진 마우스 놓기에서 `wl_data_source.cancelled()`가 발생했다. Chromium의 [OnDragMotion](https://raw.githubusercontent.com/chromium/chromium/main/ui/views/widget/desktop_aura/desktop_drag_drop_client_ozone.cc)과 [UpdateDragOperation](https://raw.githubusercontent.com/chromium/chromium/main/content/browser/web_contents/web_contents_view_aura.cc) 구현도 마지막 렌더러 결과를 다음 motion에서 읽는 구조다. Esc와 같은 `none` 결과이므로 취소를 무시하고 이동을 확정하는 보정은 넣지 않았다.

Linux에서 XWayland가 제공되면 기본 시작 경로를 X11로 선택한다. Electron의 백엔드는 main 코드보다 먼저 정해지므로 첫 시작에서 창을 만들기 전에 X11 옵션으로 한 번 재실행한다. [실제 재실행 기록](xwayland-drag/startup/startup.json)은 PID 교체, X11 시작 옵션 하나, 파일 인자 보존을 확인한다. 명시적인 실행 옵션은 덮어쓰지 않는다. 명시적인 `--ozone-platform=wayland`와 X11 없는 환경은 그대로 존중하며, 이 경우 위의 Chromium 제약은 남는다. 네이티브 Wayland 자체의 버그를 고쳤다고 주장하지 않는다. 전역 좌표를 사용할 수 있는지는 실제 선택한 백엔드로 판단한다.

`npm run test:xwayland --workspace @setdown/desktop`은 사용자 데스크톱과 연결하지 않는 headless Mutter와 그 자식 XWayland, 전용 프로필·런타임·D-Bus, 가상 입력 장치를 사용한다. 최종 코드에서 [자동 시작 및 웹·문서 각각 40회 검사](xwayland-final/run.log), 총 3개 시나리오가 29.8초에 통과했다. 분할, 중앙 합치기, 탭 삽입, Esc 취소, 반복 이동과 입력값 보존을 검사했다. 별도 [자동 재실행 검사](xwayland-drag/startup/run.log)도 2.2초에 통과했다. `test:wayland`는 동일 시나리오를 네이티브 Wayland에서 실행하는 엄격한 조사용 검사로 남긴다. 재시도나 추가 포인터 움직임으로 실패를 숨기지 않는다. `guide-*.png`는 셸 가이드 캡처이며, `native-guide-layer.png`는 웹 뷰 위의 실제 투명 가이드 화면이다.

## 검증 방식

GUI는 `with-isolated-display.sh`의 Xvfb, 별도 런타임 디렉터리와 D-Bus 세션에서 실행했다. 사용자 데스크톱의 Wayland 소켓을 상속하지 않았다. Esc 전환 검증도 같은 격리 경로를 사용한다. 실제 Chromium, 네이티브 마우스·키 입력, 포커스·IME 및 기존 단언을 유지했다.

- 실제 영상의 프레임 콜백 증가, 재생 상태, 네이티브 뷰 표시 상태를 폴더 메뉴·확장 바·드래그 중 확인한다. Esc 취소와 실제 드롭도 검사한다.
- 웹 8개 테마, 교차 출처 CSS, 같은 문서 내 탐색, 창 이동, 입력 요소의 객체 동일성, 입력값·스크롤, 사이트 예외, 재시작 후 설정을 검사한다.
- 터미널은 테마별 ANSI 16색, indexed·truecolor·명시적 배경·역상 20개 샘플의 실제 렌더링 색을 측정한다. 4.5 기준을 낮추지 않았다. PTY PID와 미전송 입력도 보존되는지 확인한다.
- Git은 배지 설정 27조합, 충돌 분류, 중첩 저장소·심볼릭 링크·서브모듈·worktree·상태 한도·표시 대상·설정 저장을 검사한다.

## 최종 검사 진행 기록

후속 전체 검사에서 드롭 가이드의 창 경계 처리와 테스트 창 선택 문제가 드러났다. [당시 로그](contract-before-boundary-fix.log)는 201개 통과·18개 실패다. 전용 드롭 화면을 일반 앱 창으로 오인하던 fixture 선택을 고쳤으며 PTY·Vim 검증 단언은 유지했다. 기존의 “창 밖” 입력 중 실제로 창 안을 가리키던 세 경우는 현재 창 기준의 실제 바깥 좌표로 바꿨다. 가이드 보존·Git 리뷰 분할·분리 위치에 대한 제품 수정을 반영하고, MIME 관련 기존 단언도 복구했다. 이후 관련 4개 검사는 통과했다.

그 다음 [전체 실행](contract-before-renderer-lifetime-fix.log)은 단위 672개·도구 14개, 타입·Svelte 검사와 Electron 218개가 통과했지만 Git 배지 한 시나리오가 45초 시간 초과 후 worker 종료 대기까지 실패했다. 당시 로그에는 중단 위치가 남지 않아 직접 원인은 미확정이다. 이를 통과로 처리하지 않았다.

문서만 있는 창에서도 웹 전용 드롭 렌더러를 미리 만들던 부분을 제거했다. 웹이 처음 표시될 때만 준비하고 이후에는 유지한다. 불필요한 렌더러와 시작 페이지 경쟁을 줄이는 변경이며, 해당 시간 초과의 원인을 확정했다는 뜻은 아니다. 이후 [Git 배지 검사 3회](git-badge-timeout/after-receiver-scope.log)가 전부 통과했고 XWayland 시작 검사도 문서 전용 창에 추가 드롭 페이지가 없는지 확인한다. 전체 219개와 독립 80회 성능 비교를 최종 코드로 다시 실행했고, 아래 최종 결과에서 모두 통과했다.

## 이전 전체 검증 및 최초 성능 실패

`SETDOWN_BUILD_SOURCEMAP=0 npm run test:preview-contract`가 종료 코드 0으로 완료됐다. [전체 로그](preview-contract.log).

| 항목 | 탭 이동 재설계 전 결과 |
| --- | --- |
| 단위 검증 | 93개 파일, 663개 통과 |
| 도구 검증 | 14개 통과 |
| TypeScript·Svelte | 오류 0, 경고 0 |
| 렌더러·Electron 빌드 | 성공 |
| 실제 Electron | 218개 통과, 10.2분 |

오디오·종료 시나리오도 이 전체 실행에서 통과했다. 이후 첫 성능 비교는 80회 실행을 완료했으나 48개 항목 중 하나에서 실패했다. [원본 결과](preview-latency/comparison.json)와 [로그](preview-benchmark-before-scroll-fix.log)를 보존했다. 준비 시간 0ms·일반 문서·편집 있음·첫 Esc의 중앙값이 326 → 409ms(+83ms, +25.46%)로, 기존 25% 및 50ms 기준을 모두 넘었다. 나머지 47개 항목은 통과했다. 이 실행을 성공으로 처리하지 않았다.

별도 Chromium 추적과 위치 요청 계측에서, Ctrl+End 직후 편집하고 Esc를 누르면 Monaco의 진행 중인 smooth scroll 중간 좌표를 읽는 문제를 확인했다. [추적 자료](cold-esc-diagnosis/)에서 끝에 입력했는데 26번째 줄로 전환했다. 새 회귀 검증은 수정 전 **기대 408, 실제 26**으로 [실패](scroll-destination-before.log)했다. 이 현상은 입력 위치가 설치된 문서 앞부분으로 판정되어 뒤쪽 최신 문단을 순차 hydration으로 기다리게 만든다. 계측 실행의 시간은 성능 판정에 사용하지 않는다.

Esc 직전에 Monaco의 공개 저장·복원 API로 진행 중인 스크롤을 도착 위치에 완료한 뒤 기존 위치 읽기를 실행하도록 수정했다. 애니메이션 대기 시간을 추가하거나 숨은 문서 준비를 입력 경로로 옮기지 않는다. 요청한 소스 위치가 아직 설치되지 않은 부분에 있으면 기존 on-demand hydration을 그대로 사용한다. 추가 수정은 위의 최종 전체 검사와 독립 성능 비교에 포함됐으며 모두 통과했다.

성능 기준본은 `7c7b05ca6124279714f19ccb97e8148b82653636`의 독립 설치 체크아웃이다. `/tmp`가 메모리 파일시스템이어서 약 4.4GB를 차지하던 두 기준본을 `test-results/installed-baselines`의 디스크로 옮겼고 기존 경로는 심볼릭 링크로 유지했다. 이동 후 서브모듈 Git 메타데이터 경로만 복구했으며 기준본 작업 트리는 clean이다. 후보 소스·빌드·node_modules를 기준본에 복사하지 않았다. 양쪽 렌더러 빌드는 `SETDOWN_BUILD_SOURCEMAP=0`을 사용한다.

실제 YouTube 계정·광고별 플레이어 동작, Windows PowerShell/Oh My Posh/WSL 프롬프트, VS Code GUI와 현재 배지 숫자의 직접 대조는 이번 Linux 격리 검증의 범위에 포함하지 않는다. 숫자를 직접 비교할 때는 파일 상태·버전·설정·표시 저장소 집합이 같아야 한다.
