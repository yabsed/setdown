# 한 장의 종이, 두 가지 초점

## 단일 Markdown 파일에서 읽기 화면과 편집 화면은 어떤 관계여야 하는가

2026년 9월 11일 00:49 KST

좋은 마크다운 앱을 켰는데 왼쪽에 폴더 트리가 있고, 위에는 탭이 줄지어 있으며, 가운데는 다시 편집기와 프리뷰로 갈라져 있다. 문서 한 장을 읽고 문장 하나를 고치려던 사람은 어느새 작은 IDE 앞에 앉아 있다. 이것은 기능이 부족해서 생긴 문제가 아니다. 제품이 “문서를 여는 일”을 “프로젝트를 관리하는 일”로 오해해서 생긴 문제다.

원하는 프로그램은 IDE의 축소판이 아니다. 문맥상 사용자가 말한 MarkTex는 [MarkText](https://marktext.me/)를 뜻하는 것으로 보인다. MarkText의 좋은 정신은 실시간 렌더링이나 특정 UI 부품보다, 마크다운 문법을 앞세우지 않고 글을 앞세우는 데 있다. 공식 설명도 이를 “방해 없는 글쓰기”, “한 화면에서 이뤄지는 렌더링”으로 내세운다. 그러나 이 프로젝트는 그 철학을 복사할 필요가 없다. 오히려 한 걸음 더 단순해질 수 있다.

**문서는 하나이고, 화면도 하나이며, 읽기와 편집은 그 문서를 바라보는 두 개의 초점이어야 한다.** 기본은 Crossnote가 그린 아름다운 읽기 화면이다. 고치고 싶은 문단을 더블 클릭하면 같은 자리에 원문 편집기가 나타난다. 고침이 끝나 `Esc`를 누르면 다시 같은 문단의 렌더링 결과로 돌아간다. 나란히 놓인 두 창도, 별도의 “미리보기”도 필요 없다.

이 발상은 직관적이다. 다만 더블 클릭과 `Esc`를 단순한 토글로 구현해서는 그 직관이 금세 깨진다. 두 동작에는 방향이 있어야 한다.

> **더블 클릭은 “여기를 고친다”, `Esc`는 “이제 결과를 본다”.**

## 한 화면이어야 하는 이유

분할 화면은 비교에는 좋지만 읽기에는 나쁘다. 폭을 절반으로 줄이고, 두 스크롤바를 만들며, 사용자가 어느 쪽이 현재 문서인지 계속 판단하게 한다. WYSIWYG는 이 문제를 없애지만 다른 값을 치른다. 복잡한 표, 수식, 다이어그램, 포함 문서처럼 원문과 결과의 구조가 크게 다른 요소에서는 편집기의 내부 문서 모델이 렌더링 엔진과 어긋나기 쉽다. MPE와 동일한 Crossnote 결과를 원한다면 별도의 WYSIWYG 모델을 또 만드는 것은 특히 위험하다.

단일 화면·이중 모드는 양쪽의 장점을 취한다.

| 읽기 모드 | 원문 모드 |
|---|---|
| Crossnote의 완전한 결과 | 실제 `.md` 원문 그 자체 |
| 비례 글꼴과 넉넉한 여백 | 고정폭 글꼴과 VS Code 계열 문법 색상 |
| 링크·수식·표·다이어그램 감상 | 모든 문법을 손실 없이 수정 |
| 우발적 입력으로부터 안전 | 명시적으로 진입한 뒤에만 변경 가능 |

가운데에 “반쯤 렌더되고 반쯤 편집되는” 제3의 모델이 없다. 그래서 Crossnote가 지원하는 기능이 늘어나도 편집기 데이터 모델을 매번 확장할 필요가 없다. 읽기 모드는 언제나 Crossnote 출력이고, 편집 모드는 언제나 텍스트다.

MarkText도 현재 실시간 프리뷰 편집기와 Source Code 모드를 제공하며 단축키로 전환한다. 그 경험이 매력적이라는 사용자의 판단은 옳다. 다만 MarkText 자체는 사이드바에 파일 탐색기·검색·목차를 두고 탭도 지원한다. 이 제품은 그중 “문서에 집중한다”는 정신만 취하고 워크스페이스 관리는 과감히 버려야 한다. [MarkText 기본 사용법](https://marktext.me/docs/basics) · [MarkText 공식 저장소](https://github.com/marktext/marktext)

## 동작 문법은 비대칭이어야 한다

제안한 두 입력은 다음처럼 고정하는 것이 좋다.

```text
읽기 모드에서 문단 더블 클릭 ──→ 그 문단의 원문을 선택한 편집 모드
편집 모드에서 Esc             ──→ 현재 커서 문단을 보여주는 읽기 모드
```

`Esc`를 양방향 토글로 만들지는 않는다. 읽기 화면에서 `Esc`를 눌렀는데 갑자기 편집기가 나타나는 것은 “escape”의 의미와 반대다. 더구나 `Esc`는 찾기 창, 컨텍스트 메뉴, 이미지 확대를 닫는 데도 필요하다. 읽기→편집은 더블 클릭, 편집→읽기는 `Esc`라는 비대칭이 기억하기 쉽고 실수를 줄인다. 키보드만 쓰는 사람에게는 `Enter` 또는 `Cmd/Ctrl+E`로 현재 읽기 위치를 편집하는 보조 동작을 제공하면 된다. `Cmd/Ctrl+E`는 어느 쪽에서도 전환되는 진짜 토글이어도 괜찮다.

상태 전이는 작아야 한다.

```mermaid
stateDiagram-v2
    [*] --> Reading: .md 파일 열기
    Reading --> Editing: 본문 더블 클릭
    Reading --> Editing: Enter / Cmd+E
    Editing --> Reading: Esc
    Editing --> Reading: Cmd+E
    Reading --> Transient: 찾기 · 이미지 확대 · 메뉴
    Editing --> Transient: 찾기 · 자동완성 · 명령 팔레트
    Transient --> Reading: Esc, 원래 읽기 상태였다면
    Transient --> Editing: Esc, 원래 편집 상태였다면
```

마지막 두 줄이 중요하다. `Esc`는 가장 안쪽에 열린 것을 먼저 닫는다. 자동완성 목록이 열린 상태라면 첫 `Esc`는 목록만 닫고, 두 번째 `Esc`가 읽기 모드로 돌아간다. 한글 IME가 조합 중일 때도 모드를 바꾸지 않는다. 먼저 조합을 취소하거나 확정하게 해야 한다. 이 규칙이 없으면 한국어 한 글자를 입력하다 갑자기 화면이 바뀌는 불쾌한 버그가 생긴다.

## 화면이 바뀌어도 장소는 바뀌면 안 된다

이 제품의 성패는 전환 애니메이션보다 **위치 보존**에 달려 있다. 사용자가 800줄짜리 문서 중간의 표를 더블 클릭했는데 편집기가 파일 첫 줄에서 열리면, 두 화면은 같은 문서처럼 느껴지지 않는다.

읽기→편집 전환에서는 클릭된 DOM에서 가장 가까운 `data-source-line`을 찾는다. Crossnote는 프리뷰 요소에 소스 라인을 붙이는 파이프라인을 이미 갖고 있으므로, 첫 버전은 이를 이용해 해당 줄의 첫 번째 의미 있는 문자에 커서를 둔다. 제목의 글자 부분을 눌렀다면 `##` 뒤로, 목록이라면 `- ` 뒤로, 인용문이면 `> ` 뒤로 보내는 정도의 작은 보정은 유용하다. 정확한 열 매핑을 위해 별도 AST를 만드는 것은 나중 일이다.

편집→읽기 전환에서는 커서 줄 이하에서 가장 가까운 `data-source-line` 요소를 찾고, 그 요소가 화면에서 차지하던 세로 위치를 복원한다. 단순히 같은 스크롤 퍼센트로 이동하면 이미지와 다이어그램의 높이 때문에 어긋난다. 저장해야 할 전환 앵커는 다음 네 값이면 충분하다.

| 값 | 용도 |
|---|---|
| `sourceLine` | 두 표현을 잇는 기본 좌표 |
| `sourceOffset` | 편집기 커서 복원 |
| `blockId` | 동일 줄에 여러 요소가 있을 때 보조 좌표 |
| `viewportRatio` | 대상 블록이 화면 위에서 어느 높이에 있었는지 복원 |

전환 중에는 화면을 하얗게 비우지 않는다. 기존 화면을 유지한 채 새 화면을 준비하고 80~120ms 정도의 짧은 교체만 한다. 사용자가 멀미할 정도의 슬라이드나 3D 뒤집기 효과는 필요 없다. 같은 종이의 초점만 바뀐다는 인상을 줘야 한다.

## 더블 클릭에는 작은 함정이 있다

브라우저에서 텍스트 더블 클릭은 보통 단어 선택이다. 그 관습을 편집 진입에 쓰면 읽기 화면에서 단어를 빠르게 선택하는 기능을 잃는다. 그러나 이 제품의 핵심 약속이 “보이는 곳을 더블 클릭해 고친다”라면, 이 충돌은 받아들일 만하다. 드래그 선택과 `Cmd/Ctrl+C`는 그대로 유지하면 된다.

대신 모든 요소에서 같은 동작을 강요해서는 안 된다.

- 일반 문단, 제목, 목록, 인용문, 표 셀은 더블 클릭하면 해당 원문으로 간다.
- 이미지, 수식과 다이어그램은 더블 클릭하면 그것을 만든 소스 블록으로 간다.
- 코드 블록 본문은 더블 클릭 편집을 기본으로 하되, 우측 상단에 한 번 클릭하는 복사 버튼을 둔다.
- 링크는 한 번 클릭하면 연다. 더블 클릭 이벤트를 기다리느라 링크 열기를 지연시키지 않는다. 링크 문법을 고치려면 `Alt/Option+더블 클릭` 또는 블록 여백 더블 클릭을 쓴다.
- 체크박스는 읽기 모드에서 바로 토글하지 않는다. 클릭은 읽기 동작, 더블 클릭은 원문 편집으로 통일한다. 읽기 화면이 조용히 파일을 바꾸는 일은 없어야 한다.

링크만 예외인 이유는 기술적이기도 하다. 더블 클릭은 두 번의 클릭 뒤에 도착하므로 링크의 단일 클릭과 경쟁한다. 모든 링크 클릭을 250ms씩 늦춰 이 문제를 해결하는 것은 제품 전체를 둔하게 만든다. 작은 예외가 더 낫다.

마우스를 올렸을 때 문단 왼쪽에 희미한 편집 표시를 보여주는 것은 선택 사항이다. 상시 도구막대는 피하되, 처음 세 번의 더블 클릭 가능 영역을 알려주는 온보딩에는 도움이 된다. 첫 성공 이후에는 힌트를 사라지게 한다.

## 원문 화면도 읽기 좋아야 한다

편집 화면을 “개발자용 벌칙 화면”으로 만들면 사용자는 곧바로 읽기 모드로 도망친다. 사용자가 말한 VS Code 스타일의 거친 화면은 훌륭한 두 번째 독서 모드가 될 수 있다. 다만 VS Code 전체를 들여올 필요는 없다.

Monaco보다 CodeMirror 6가 이 제품에는 더 잘 맞는다. 필요한 것은 다중 커서, 마크다운 문법 강조, 검색·바꾸기, 괄호 짝, 실행 취소, IME와 접근성이지 디버거와 미니맵이 아니다. 화면 구성은 읽기 모드와 같은 중앙 열 폭을 유지하고, 배경과 글자 크기도 급격히 바꾸지 않는다. 문법 토큰만 절제된 색으로 드러낸다.

권장 기본값은 다음과 같다.

- 고정폭 글꼴 14~15px, 줄 높이 1.65
- 본문 폭 820~900px, 읽기 모드와 동일한 좌우 중심선
- 줄 번호는 기본 끔, 설정에서만 켬
- 미니맵·브레드크럼·탭·활동 막대 없음
- 헤딩, 강조, 링크, 코드, 인용, 리스트 기호와 프런트매터에만 색 사용
- 현재 줄 배경은 아주 약하게, 선택 영역은 분명하게
- 자동 줄바꿈 켬; 긴 코드와 표에서는 가로 스크롤 허용

즉 “VS Code의 색”은 취하되 “VS Code의 사무실”은 들이지 않는다.

## 파일 하나만 연다는 약속

앱을 열면 빈 대시보드나 워크스페이스 선택기가 아니라 문서가 보여야 한다. 진입 경로는 OS에서 `.md` 파일 더블 클릭, 파일을 앱 아이콘에 드롭, `Cmd/Ctrl+O`, 최근 파일뿐이다. 한 창은 한 파일만 소유한다. 다른 파일을 열면 현재 창에서 교체할지 새 창에서 열지는 운영체제 관습에 맞추되, 앱 내부 탭과 폴더 트리는 만들지 않는다.

상시 UI는 제목 표시줄의 파일명, 수정 여부를 나타내는 점 하나면 충분하다. 목차는 필요할 때만 `Cmd/Ctrl+Shift+O`로 떠오르는 오버레이로 제공한다. 설정, 내보내기와 최근 파일도 메뉴에 숨긴다. 기능이 없는 것이 아니라 문서보다 먼저 보이지 않는 것이다.

저장 모델은 두 화면이 같은 버퍼를 공유해야 한다. 모드를 바꾸는 것은 저장이 아니며 파일을 다시 읽는 일도 아니다. 편집기는 메모리의 Markdown 원문을 바꾸고, `Esc`를 누르면 그 최신 버퍼를 Crossnote에 넘긴다. 저장은 `Cmd/Ctrl+S`와 선택 가능한 자동 저장이 맡는다. 렌더링이 늦어지면 이전 프리뷰를 유지하고 제목 옆에 작은 진행 표시만 둔다. 실패하면 편집 내용을 잃지 않은 채 편집 화면으로 돌아가 오류가 난 블록을 가리킨다.

## 구현 순서

첫 번째 프로토타입은 한 문단만 완벽하게 왕복시키면 된다. `.md`를 읽기 모드로 열고, 일반 문단을 더블 클릭해 같은 줄의 CodeMirror로 이동하고, 수정 후 `Esc`를 눌러 같은 화면 높이에 결과를 보여준다. 파일 트리, 탭, 설정 화면과 내보내기는 이 검증에 아무 도움도 주지 않는다.

그다음 제목·목록·표·코드·수식·다이어그램별 소스 앵커를 보정한다. 세 번째로 찾기, IME, 링크와 복사 같은 이벤트 우선순위를 다듬는다. 마지막에 자동 저장과 충돌 복구를 붙인다. 외부 프로그램이 열린 파일을 바꾸면 곧장 덮어쓰지 말고, 디스크판과 메모리판 중 무엇을 유지할지 묻는다.

테스트도 기능 수보다 왕복의 질을 봐야 한다.

1. 문서의 상단·중간·하단에서 전환 후 대상 블록이 같은 화면 높이에 남는가.
2. 한글 조합, 자동완성과 찾기 창에서 `Esc`가 올바른 층만 닫는가.
3. 빠르게 `Esc`와 더블 클릭을 반복해도 오래된 렌더가 새 내용을 덮지 않는가.
4. 표·수식·Mermaid를 고친 뒤 원문이 재포맷되거나 손실되지 않는가.
5. 읽기 모드에서 아무 키나 눌러도 파일이 바뀌지 않는가.
6. 키보드와 스크린리더만으로 두 모드를 오갈 수 있는가.

## 결론

사용자의 구상은 이 제품이 가져야 할 중심 원리로 삼을 만하다. 다만 표현을 조금 다듬어야 한다.

**“예쁜 화면과 거친 화면을 토글한다”가 아니라, “결과를 읽다가 원하는 곳을 고치고, 다시 결과로 빠져나온다.”**

그래서 최종 동작은 다음이 가장 자연스럽다.

1. `.md` 파일은 아름다운 읽기 모드로 열린다.
2. 고치고 싶은 블록을 더블 클릭하면 같은 위치의 원문 모드로 들어간다.
3. `Esc`를 누르면 현재 커서 위치의 읽기 모드로 돌아간다.
4. 키보드 사용자를 위해 `Enter`와 `Cmd/Ctrl+E`를 함께 제공한다.
5. 두 모드는 하나의 Markdown 버퍼와 하나의 undo history를 공유한다.

이 제품은 VS Code에서 디렉터리 목록을 덜어낸 프로그램도, MarkText에 MPE 기능을 더 붙인 프로그램도 아니다. 문서 한 장을 가장 아름답게 읽고, 가장 정직한 원문으로 고치며, 그 둘 사이의 거리를 한 번의 동작으로 없애는 프로그램이다. 그 약속만 지키면 기능이 늘어나도 제품은 무거워 보이지 않는다. ■
