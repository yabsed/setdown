# Zed가 실행 파일을 선택하도록 연결 경로 변경

2026-11-10. 기준: `49b634c7bd45609e9f5597d53bfba36f0d145d8c`.
실제로 사용하는 Zed: `vendor/zed`의 `b5cd310b3b54dfc659fcc06453e6358843dfe216`.

문제는 검색의 정확도만이 아니었다. Setdown은 자체 검색에서 실행 파일처럼 보이는 항목을 찾으면 Zed를 거치지 않고 실행했다. 따라서 Zed의 프로젝트별 선택과 검증이 구현되어 있어도, 고장 난 rustup shim이 먼저 발견되면 그 보호를 받지 못했다. 이번 변경은 **Zed 어댑터가 있는 자동 연결에서 그 우회 경로를 없앤다.**

## 사용자에게 달라지는 점

파일을 열면 해당 프로젝트의 환경을 얻고 Zed 어댑터에 실행 명령을 요청한다. 어댑터가 외부 도구와 관리형 설치를 선택하며, 언어별 검증과 기본 인수도 Zed의 결과를 사용한다. 전역 목록의 `Executable found`가 현재 프로젝트에서 사용할 도구를 결정하지 않는다.

관리형 실행 기록이 있어도 새 연결에서는 Zed가 프로젝트의 도구를 먼저 확인한다. 프로젝트에 정상 도구가 새로 생기면 이전 관리형 명령이 그 선택을 가리지 않는다. 이미 정상 연결된 문서는 재검색 때문에 다른 프로세스로 바뀌지 않는다.

고급 설치 관리에서는 기본 제공·관리형 설치와 외부 실행 파일 후보를 분리했다. 기존의 모호한 설치 재확인 동작은 **Refresh external executable candidates**로 표시한다. `Included`, 관리형 `Installed`, `Executable found`가 서로 다른 증거를 뜻한다. 현재 파일의 실제 연결·오류는 Code support에서 확인한다.

## 실제로 Zed에 맡긴 부분

| 책임 | 사용한 구현 |
| --- | --- |
| 프로젝트 셸 환경 | Zed `util::shell_env::capture`와 `--printenv` 콜백 |
| 외부 실행 파일과 프로젝트 toolchain 선택 | Zed `LspInstaller::check_if_user_installed` |
| 언어별 실행 검증 | 각 Zed 어댑터의 구현. Rust는 실제 `--help` 실행 결과를 확인 |
| 관리형 실행 파일 선택과 준비 | Zed `get_language_server_command` 및 확장 어댑터 |
| 기본 실행 인수·초기화·서버 설정 | 어댑터 결과에 사용자 지정 사항을 적용 |

프로젝트 환경은 분석 root별로 보관하고 재검색 시 무효화한다. 활성 venv·Conda나 명시적인 상속 환경은 유지한다. 셸 실행 실패를 다른 프로젝트의 환경으로 숨기지 않는다. Windows는 상속 환경을 사용하며, 이번 실행 검증 플랫폼은 Linux다.

환경 변수는 이름 순으로 정규화한 뒤 실행 기록을 식별한다. Zed의 HashMap 직렬화 순서가 달라지는 것만으로 앱 재시작 후 캐시가 사라지지 않는다. 어댑터 인수에는 Node 서버의 스크립트 경로가 들어갈 수 있으므로 사용자 인수는 그 명령을 보존하고 뒤에 추가한다. 실제 Node 실행과 역순 환경 변수로 재시작하는 검사로 이 두 경계를 확인한다.

Zed도 모든 언어 서버를 동일하게 검증하지 않는다. 예를 들어 Rust 어댑터는 고장 난 shim을 실행 검사로 거부하지만 Go 어댑터의 외부 경로 선택은 `which`를 사용한다. 따라서 이 변경도 “모든 외부 설치를 100% 찾아서 정상임을 인증한다”는 약속은 하지 않는다. 파일 후보, 실제 초기화 성공, 프로젝트 분석 결과를 구분하는 것이 계속 필요하다.

## 다운로드를 끈 경우

기본 제공 서버와 직접 선택한 실행 파일은 계속 사용할 수 있다. 기본 Zed 어댑터는 별도 호스트에서 외부 실행 파일을 확인한다. 이 호스트에는 Zed의 HTTP 차단 클라이언트를 적용하고 Node 다운로드도 끈다.

WASI 확장은 자체 설치 코드를 실행할 수 있고 Zed의 `allow_binary_download` 옵션을 일괄 준수하는 인터페이스가 아니다. 다운로드가 꺼져 있으면 미리 검증한 프로젝트 실행 기록이나 명시적인 실행 파일이 필요하다. 준비되지 않은 확장을 호출하고 나중에 다운로드만 막았다고 가정하지 않는다.

유효한 관리형 실행 기록은 Zed의 새 선택이 실패했을 때 재사용한다. 파일 크기·수정 시각, 프로젝트 입력과 실행 설정이 바뀐 기록은 재사용하지 않는다. 다운로드 정책 자체를 바꾸는 것은 같은 명령의 기록을 무효화하지 않는다. 다른 프로젝트나 변경된 환경에 같은 설치가 존재한다는 사실만으로 기존 기록을 적용하지 않는다.

## 남긴 Setdown 코드의 범위

기본 제공 Python·TypeScript 서비스, 사용자가 지정한 실행 파일과 사용자 연결, Zed 어댑터가 없는 프로필의 호환 경로는 유지한다. 전역 후보 목록도 수동 연결과 문제 해결용으로 남아 있다. 이 검색은 Zed가 지원하는 자동 연결의 실행 파일을 결정하지 않는다.

Monaco 문서·미저장 버퍼·Undo, 노트북 문서, IPC, 진단 소유권, 프로세스 수명과 JSON-RPC 연결도 여전히 Setdown의 통합 계층이다. Zed의 `LspStore`는 Zed의 버퍼·worktree·GPUI 모델과 결합되어 있으므로 이 작업에서 전체 런타임을 교체했다고 주장하지 않는다. 이번에는 실제 원인이었던 실행 파일 선택 경로와 프로젝트 환경부터 Zed에 맡겼다.

주요 변경은 [language-manager.ts](../../apps/desktop/src/main/language/language-manager.ts), [language-provisioner.ts](../../apps/desktop/src/main/language/language-provisioner.ts), [Rust 호스트](../../tooling/language-host/src/main.rs), [설치 상태 표시](../../apps/desktop/src/renderer/language/language-presentation.ts)에 있다. [제품 문서](../../docs/language-support.md)와 [검증 계약](../../docs/preview-performance-contract.md)도 갱신했다. vendor 코드는 수정하지 않았다.

## 검증

[검증 스크립트](finish-validation.sh)는 전체 단위·도구·빌드·GUI 검사 후 실제 Zed 호스트 검사, 기준본 대비 성능 비교, 실제 fortls·rust-analyzer 검사, Linux 패키징과 패키지 실행 검사를 수행한다. GUI는 Xvfb와 분리된 runtime·D-Bus를 사용하며 사용자 화면에 창을 띄우지 않는다. 메모리는 4GiB 상한, Cargo는 1개 작업으로 제한한다.

새 회귀 검사는 다음을 확인한다.

- Setdown의 전역 검색보다 Zed가 먼저 실행 명령을 결정한다.
- 고장 난 Rust shim의 `--help` 실패를 실제 Zed가 거부한다.
- 프로젝트 toolchain의 정상 실행 파일을 선택하고 다른 프로젝트로 그 선택을 전달하지 않는다.
- 실제 Electron에서 고장 난 PATH 후보를 건너뛰고 Zed의 저장된 서버에 연결한다. 미저장 변경과 Undo도 확인한다.
- 외부 Go 서버를 실행 중에 설치한 뒤 재검색하면 현재 미저장 모델에 연결하고, 정상 세션은 유지한다.
- 다운로드 차단, 변경된 설치 파일의 기록 무효화, 명시적 인수 보존과 프로젝트 환경 캐시 갱신을 확인한다.

실행 파일 선택 회귀 검사는 고장·성공을 재현하는 작은 실행 파일과 LSP fixture를 사용한다. 어댑터와 호스트, Electron은 실제 빌드다. 실제 fortls와 rust-analyzer의 언어 기능은 별도 통합 검사로 확인한다.

원시 결과: `target/validation/zed-resolution-2026-11-10/`. 기준본은 `49b634c`의 소스와 같은 vendor 커밋, 독립된 Node/Electron 의존성으로 준비했다. 기준·변경 빌드 모두 `SETDOWN_BUILD_SOURCEMAP=0`을 사용한다. 성능 측정은 기존 5회 반복·8개 시나리오·48개 비교와 25% 및 50ms의 동시 초과 기준을 유지한다.
