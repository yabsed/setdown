## 1. 경영 요약

Setdown은 로컬 문서를 읽고 편집하는 Electron 데스크톱 애플리케이션이다.
마크다운 편집과 프리뷰가 중심이지만, 실제 공격 표면은 그보다 훨씬 넓다.
내장 웹 브라우저, Chrome 확장, PDF 뷰어, 이미지 편집, 비디오, Jupyter 노트북 실행,
통합 터미널, Git 연동, 다수의 언어 서버(LSP)가 하나의 앱 안에 들어 있다.

이 구조에서 가장 중요한 사실은 다음과 같다.

**골격 방어는 잘 설계되어 있다.**
확인한 모든 창과 뷰는 `sandbox: true`, `contextIsolation: true`,
`nodeIntegration: false` 를 사용한다.
프리로드 스크립트는 `ipcRenderer` 자체를 페이지에 노출하지 않고, 명시적인 API 객체만
`contextBridge` 로 노출한다.
자식 프로세스 실행은 예외 없이 `shell: false` 와 인자 배열을 쓴다.
외부 링크는 프로토콜 화이트리스트와 확인 대화상자를 거친다.
즉, Electron 앱에서 흔히 발견되는 저수준 실수는 이 코드베이스에서 대체로 발견되지 않았다.

**위험은 골격이 아니라 세 군데에 몰려 있다.**

첫째, **의존성**이다.
`npm audit --omit=dev` 기준으로 프로덕션 의존성에서 취약점 65건
(critical 2건, high 43건, moderate 12건, low 8건)이 보고된다.
개발 의존성까지 합치면 100건이다.
다만 이 숫자 전체가 곧바로 악용 가능함을 뜻하지는 않는다.
대표적인 critical 권고인 DOMPurify 건은 이 코드가 사용하지 않는 `IN_PLACE`
옵션이 전제라 조건이 충족되지 않는다.
진짜 문제는 숫자보다 관리 방식이다.
루트 `package.json` 의 `overrides` 가 `dompurify` 와 `sharp` 를 취약한 버전에
고정해 두어, 패치가 나와도 자동으로 올라가지 않는 구조가 되어 있다.

둘째, **신뢰할 수 없는 입력을 여는 행위 자체**이다.
이 앱의 본질적인 사용법이 남이 만든 마크다운, 노트북, 폴더, 저장소, 웹페이지를
여는 것이기 때문이다.
폴더를 열면 Git 조회가 돌고, 문서를 열면 언어 서버가 실행되며,
노트북에서 실행 버튼을 누르면 Python 코드가 사용자 권한으로 돈다.
이들은 기능이지만, VS Code가 도입한 워크스페이스 신뢰(Workspace Trust) 같은
확인 단계가 없어 "열기"와 "실행"의 경계가 사용자 기대보다 가깝다.

셋째, **내장 브라우저와 확장**이다.
원격 웹 콘텐츠와 서드파티 확장 코드를 앱 안으로 들이는 순간,
앱의 보안은 Chromium 패치 속도와 확장 권한 관리에 종속된다.
자동 업데이트가 없는 배포 방식은 이 종속을 더 위험하게 만든다.

종합하면, **지금 당장 사용을 중단해야 할 수준의 결함은 확인되지 않았다.**
대신 의존성 핀 해제와 패치, 셸 창 탐색 정책 추가, 프리뷰 CSP 도입,
로컬 파일 실행 시 확인 절차라는 비교적 작고 명확한 조치들로
위험의 큰 부분을 줄일 수 있다.
중장기적으로는 워크스페이스 신뢰 개념과 자동 업데이트가 필요하다.

## 2. 점검 범위와 방법

### 2.1 범위

- 애플리케이션 코드: `apps/desktop/src` 전체 (점검 시점 약 593개 파일).
  메인 프로세스(`src/main`), 프리로드(`src/preload`, `src/preview-runtime`,
  `src/browser-runtime`), 렌더러(`src/renderer`), 공유 코어(`src/core`),
  프로토콜 타입(`src/protocol`)을 포함한다.
- 구성: 루트 `package.json`, `apps/desktop/package.json` (의존성, 스크립트,
  `electron-builder` 설정), `apps/desktop/index.html` (셸 CSP),
  `apps/desktop/vite.config.ts` 등 빌드 구성의 보안 관련 부분.
- 의존성: `package-lock.json` 기준 설치 트리 전체. `npm audit` 전체 실행과
  `npm audit --omit=dev` 실행을 모두 수행했다.
- 보조 도구: `apps/code-growth` 의 Python 스크립트는 저장소 자체 분석용이며
  배포 앱에 포함되지 않는다. 시크릿 패턴 검색 범위에는 포함했고,
  상세 감사는 하지 않았다.

### 2.2 범위 밖

- 배포된 바이너리(AppImage, deb, rpm, NSIS 설치 파일)의 실제 내용물 검사.
- `vendor/` 아래 서브모듈들. 이들은 참조용으로 보이며 배포 포함 여부는
  확인하지 않았다 (SEC-16에서 공급망 관점으로만 언급한다).
- 악성 입력 제작과 실행을 통한 동적 검증, 퍼징, 침투 테스트.
- 운영체제, 사용자 계정, 네트워크 환경 자체의 보안.

### 2.3 방법

1. 구조 파악. 워크스페이스 구성, 패키지 목록, 빌드와 패키징 설정을 읽었다.
2. Electron 보안 설정 전수 확인. 모든 `BrowserWindow` 와 `WebContentsView`
   생성 지점에서 `webPreferences` 를 확인했다.
3. 위험 패턴 검색. 프로세스 실행, HTML 주입, 외부 링크 열기, 프로토콜 핸들러,
   권한 핸들러, 다운로드, TLS 우회 패턴 등을 정규식으로 찾고,
   발견 지점의 본문을 직접 읽어 확인했다. 사용한 패턴은 부록 B에 적었다.
4. 핵심 파일 정독. `src/main/main.ts`, `src/main/ipc/install-ipc.ts`,
   `src/main/ipc/window-ipc.ts`, `src/preload/index.ts`,
   `src/main/windows/window-manager.ts`, `src/main/browser/browser-manager.ts`,
   `src/main/browser/browser-permissions.ts`,
   `src/main/browser/extension-package.ts`,
   `src/main/project/engines/git-cli.ts`,
   `src/main/notebook/kernel-manager.ts`,
   `src/main/language/server-session.ts`,
   `src/main/language/server-discovery.ts`,
   `src/main/terminal/terminal-manager.ts`,
   `src/renderer/pdf/pdf-runtime.ts`,
   `src/renderer/notebook/notebook-content.ts`,
   `src/core/browser/browser-url.ts` 등을 직접 읽었다.
5. 의존성 감사. `npm audit` 과 `npm audit --omit=dev --json` 을 실행해
   심각도별 건수와 직접 의존성의 해당 범위를 확인했다.
6. 시크릿 검색. API 키, 토큰, 비밀번호, 개인키 패턴을 소스와 설정에서 찾았다.
   하드코딩된 시크릿과 `.env` 파일은 발견되지 않았다.

### 2.4 심각도 기준

이 보고서의 심각도는 다음 기준으로 매겼다.

- **높음**: 신뢰할 수 없는 입력을 여는 통상적인 사용만으로 코드 실행,
  임의 파일 읽기·쓰기, 세션 탈취로 이어질 가능성이 현실적이거나,
  이미 공개된 취약점이 도달 가능한 경로에 있다.
- **중간**: 추가 조건 (사용자 클릭, 다른 취약점과의 결합, 특정 설정)이
  필요하지만, 성립하면 영향이 크거나, 심층 방어의 한 층이 비어 있다.
- **낮음**: 영향이 제한적이거나 전제 조건이 강하다. 위생과 강화 차원의 항목.

가능성(발생 용이성)과 영향(피해 규모)은 각 항목에서 분리해 적었다.
공개 권고가 있는 의존성은 권고의 심각도와 이 앱에서의 도달 가능성을
구분해서 평가했다. 권고가 critical이라도 전제 옵션을 쓰지 않으면
그렇게 명시했다.

## 3. 자산, 공격자, 신뢰 경계

### 3.1 지켜야 할 자산

- 사용자의 파일 시스템 전체. 앱은 사용자 권한으로 실행되며,
  메인 프로세스는 임의 경로 읽기와 쓰기가 가능하다.
- 문서 내용 자체. 열람 중인 문서, 초안, 스냅샷, 자동 저장 데이터.
- 내장 브라우저의 세션. `persist:setdown-browser` 파티션에 저장되는
  쿠키와 로그인 상태, 방문 기록, 북마크, 다운로드 기록.
- 사용자 데이터 디렉터리의 상태 파일들. 읽기 위치, 최근 폴더, 다운로드
  라이브러리, 편집기 스냅샷 등 (`app.getPath('userData')` 아래 JSON).
- 실행 권한 그 자체. 터미널, 노트북 커널, 언어 서버, Git은 모두
  사용자 권한으로 임의 코드 실행이 가능한 통로이다.

### 3.2 상정한 공격자

- **악성 문서 제작자.** 마크다운, 노트북(`.ipynb`), PDF, 이미지, 비디오
  파일을 만들어 피해자가 Setdown으로 열게 한다.
- **악성 프로젝트 제작자.** 폴더나 Git 저장소 전체를 배포한다.
  `.git` 설정, 프로젝트 설정 파일, 소스 코드, 문서가 모두 포함된다.
- **악성 웹사이트 운영자.** 피해자가 내장 브라우저로 자기 사이트를
  방문하게 한다. 원격 콘텐츠를 완전히 통제한다.
- **악성 확장 제작자.** Chrome 확장 스토어 또는 로컬 폴더·ZIP·CRX 형태로
  확장을 배포해 설치를 유도한다.
- **공급망 공격자.** npm 패키지, 전이 의존성, 빌드 도구를 오염시키거나
  이미 공개된 취약점을 이용해 배포물이나 개발 환경을 노린다.

상정하지 않은 공격자는 다음과 같다.
이미 사용자 계정으로 임의 코드를 실행할 수 있는 로컬 공격자는
앱을 거칠 이유가 없으므로 제외했다.
다만 SEC-15에서 로컬 데이터가 평문이라는 사실 자체는 기록한다.

### 3.3 신뢰 경계

이 앱의 신뢰 경계는 크게 다섯 층이다.

1. **메인 프로세스 (신뢰).** Node.js 전체 권한. 파일, 프로세스, OS 연동 담당.
2. **셸 렌더러 (신뢰하되 샌드박스).** 로컬에 번들된 앱 UI.
   프리로드가 제공하는 넓은 API를 통해 메인에 요청한다.
3. **마크다운 프리뷰 (반신뢰).** 정화된 문서 HTML을 그리지만,
   문서 내용은 신뢰할 수 없는 입력이다. 별도 `WebContentsView`와
   전용 프리로드를 쓴다.
4. **내장 브라우저 (불신).** 임의의 원격 웹 콘텐츠와 확장이 도는 곳.
   별도 세션 파티션으로 분리되어 있다.
5. **자식 프로세스 (불신 입력 처리).** 언어 서버, Python 커널, Git,
   ripgrep, 터미널 셸. 입력은 불신이지만 실행 권한은 사용자와 같다.

보안 사고는 대체로 아래쪽 층이 위쪽 층으로 넘어갈 때 발생한다.
그래서 이 보고서는 경계를 넘는 통로, 즉 IPC, 커스텀 프로토콜,
링크 열기, 프로세스 실행 지점을 집중적으로 봤다.

## 4. 전체 보안 태세 요약

세부 항목에 들어가기 전에, 영역별 인상을 먼저 정리한다.

**Electron 골격: 양호.**
창 생성 지점을 전수 확인한 결과, 보안 3종 설정의 누락은 없었다.
보조 창들(메뉴 오버레이, 위치 오버레이, 이미지 내보내기, PDF 내보내기,
탭 드래그, 확장 표면, Places 서비스)은 대부분 탐색 거부와 창 열기 거부까지
걸려 있다. 유일한 예외가 메인 셸 창이다 (SEC-04).

**명령 실행 위생: 양호.**
셸 문자열 조립이 없다. Git, ripgrep, 언어 서버, 노트북 커널, 터미널 모두
고정된 실행 파일과 인자 배열로 기동한다.
인자 주입을 막는 `--` 분리와 `--literal-pathspecs` 같은 세부 처리도 되어 있다.

**콘텐츠 정화: 대체로 양호, 층이 얇은 곳이 있음.**
노트북 출력과 웹 리더 본문은 DOMPurify로 정화하고, 허용 태그와 속성을
좁게 잡았다. 마크다운 프리뷰는 crossnote의 정화기에 의존하고
스크립트 실행을 끈 설정으로 돌린다.
다만 프리뷰 페이지에 CSP라는 두 번째 층이 없다 (SEC-06).

**권한과 다운로드: 양호.**
웹 권한은 페이지 수명 단위, 기본 거부, 영구 저장 없음으로 설계되어 있다.
다운로드는 저장 대화상자를 강제해 조용한 내려받기가 되지 않는다.

**의존성 관리: 취약.**
의존성 수가 많고(전체 1,268개), 취약점 건수가 많으며,
핵심 정화·이미지 라이브러리가 구버전에 고정되어 있다.
자동 감사 게이트가 있는지도 확인되지 않았다 (SEC-01).

**신뢰 모델: 미흡.**
문서와 폴더와 저장소를 여는 행위에 대한 신뢰 확인 개념이 없다.
기능이 풍부할수록 "열기"의 부작용이 커지는데, 그에 맞는 경고나
제한 모드가 없다 (SEC-02, SEC-12).

**배포 강화: 미흡.**
자동 업데이트가 없고, Electron fuses를 명시적으로 끄는 설정이 보이지 않는다.
내장 브라우저를 품은 앱에서는 패치 지연 자체가 위험 요소이다 (SEC-11).

## 6. 위험 상세 분석

### SEC-01. 의존성 취약점

- 심각도: **높음** (관리 구조 기준). 개별 권고의 실제 위험은 아래에서 나눠 평가한다.
- 영향 범위: 앱 전체. 특히 악성 입력을 직접 처리하는 정화기, 마크다운 파서,
  이미지 라이브러리.
- 근거 명령: `npm audit`, `npm audit --omit=dev`, `npm audit --omit=dev --json`.

#### 관찰된 사실

`npm audit` 전체 실행 결과는 100건이었다.
low 10건, moderate 30건, high 54건, critical 6건이다.
프로덕션만 추린 `npm audit --omit=dev` 결과는 65건이었다.
low 8건, moderate 12건, high 43건, critical 2건이다.
설치된 패키지 총수는 1,268개이며, 그중 프로덕션 705개, 개발 382개,
선택 283개이다.

직접 의존성(`apps/desktop/package.json`) 중 권고가 있는 것은 다음과 같다.
`crossnote` 0.9.35, `dompurify` 3.4.15, `electron-chrome-web-store` 0.13.0,
`markdown-it` 14.3.1, `sanitize-html` 2.18.0, `sharp` 0.35.4 가
high 이상으로 보고됐다.
루트 `package.json` 은 `overrides` 로 `dompurify` 를 `3.4.15` 에,
`sharp` 를 `0.35.4` 에 고정하고 있다.

#### SEC-01A. DOMPurify 3.4.15 (권고 critical, 실제 위험 낮음)

감사 도구는 DOMPurify에 critical을 매긴다.
대표 권고는 `IN_PLACE` 모드에서 노드를 제거하는 후처리 훅이
분리된 서브트리의 이벤트 핸들러를 남겨 DOM XSS가 된다는 내용
(GHSA-p98j-92pf-mc4p, 해당 범위 `>=3.4.13 <=3.4.15`)과,
`IN_PLACE` 가 강제 제거된 rawtext 루트를 반환해 재해석 시
공격자 마크업이 실행된다는 내용(GHSA-6688-9rhm-gjv2, 범위 `<=3.4.15`)이다.
이 외에도 3.4.16 이하를 대상으로 하는 후속 권고가 여럿 보고됐다.

그러나 이 앱에서의 사용 방식을 확인하면 전제가 맞지 않는다.
`apps/desktop/src` 전체에서 `IN_PLACE`, `RETURN_DOM`,
`SAFE_FOR_TEMPLATES` 옵션 사용은 발견되지 않았다.
사용 지점은 두 곳이다.
`src/renderer/notebook/notebook-content.ts` 의 `notebookHtml` 은
문자열 입력을 문자열로 정화하며, `script`, `iframe`, `svg`, `form` 등을
금지하고 데이터 속성까지 막는다.
`src/renderer/browser/WebReaderSurface.svelte` 는 웹 리더 본문을
같은 방식으로 정화한다.
두 곳 모두 기본 문자열 정화 경로이며, 문제의 `IN_PLACE` DOM 정화가 아니다.

따라서 이 권고만으로 지금 XSS가 가능하다고 단정할 수 없다.
그럼에도 업데이트를 권하는 이유는 세 가지이다.
첫째, 정화기는 악성 입력과 가장 가까이 있는 부품이라
권고 범위에 들어 있다는 사실 자체가 부담이다.
둘째, `overrides` 고정은 하위 패키지(crossnote, mermaid, monaco)가
가져오는 DOMPurify까지 같은 버전에 묶는다.
셋째, 나중에 누군가 `IN_PLACE` 같은 옵션을 무심코 켜면
그 순간 잠재 위험이 실제 위험으로 바뀐다.

#### SEC-01B. markdown-it 14.3.1 (DoS, 실제 위험 중간)

직접 의존성 `markdown-it` 14.3.1은 14.3.3 미만과 14.3.2 미만을 대상으로 하는
2차 시간 복잡도 권고들에 해당한다.
smartquotes 규칙, 인라인 HTML 파싱, 여러 줄 링크 참조 정의,
linkify 경로가 지목됐다 (예: GHSA-r7fv-28h4-cvq7, GHSA-vfgh-jcmw-g37q,
GHSA-gfr2-rv44-r23c).
전이 경로의 `linkify-it` 에도 같은 계열의 권고가 있다.
별도로 `markdown-it-html5-embed` 아래에 낡은 markdown-it 사본이 있어
12.3.2 미만 대상 권고까지 함께 보고됐다.

영향은 코드 실행이 아니라 서비스 거부이다.
수백 KB짜리 교묘한 마크다운이 이벤트 루프를 수십 초 막을 수 있다는 것이
권고의 요지이다.
이 앱에서 마크다운 렌더링은 워커(`src/main/preview/render-worker.ts`)에서
돌므로, 멈춤이 곧 메인 프로세스 전체의 멈춤은 아니다.
그래도 악성 문서를 열면 프리뷰가 장시간 응답하지 않고,
CPU를 점유한 채 앱이 사실상 사용 불능이 될 수 있다.
문서를 여는 것만으로 도달하는 경로라 가능성을 중간으로 봤다.

#### SEC-01C. sanitize-html 2.18.0 (스택 오버플로, 실제 위험 낮음~중간)

2.18.0은 버려진 iframe의 대체 내용을 다시 정화할 때 무한 재귀로
스택이 넘치는 권고(GHSA-c9rx-x947-fp3h, 범위 `>=2.18.0 <2.18.1`)에 해당한다.
사용 지점은 `src/core/browser/reader-export.ts` 의 `sanitizedReaderHtml` 이며,
웹 리더 기사를 파일로 내보낼 때 메인 측에서 호출된다.
악성 웹페이지 본문을 리더로 추출해 내보내는 흐름에서 도달할 수 있다.
결과는 프로세스 충돌 수준의 DoS로 예상되며, 2.18.1로 올리면 해소된다.

#### SEC-01D. sharp 0.35.4와 librsvg (네이티브 파서, 실제 위험 중간)

`sharp` 는 하위 네이티브 라이브러리 librsvg의 취약점
(GHSA-wq5f-xc86-pv6w, 범위 `<0.35.5`) 때문에 high로 보고됐다.
`sharp` 는 메인 프로세스에서 이미지 메타데이터 읽기와 변환에 쓰인다
(`src/main/documents/image-edit-ipc.ts`).
SVG는 이 앱이 이미지 문서로 여는 형식이므로,
악성 SVG를 열거나 편집하는 흐름에서 네이티브 파서가 입력을 받는다.
네이티브 파서 취약점은 메모리 손상으로 이어질 수 있어
자바스크립트 라이브러리 취약점보다 무겁게 본다.
루트 `overrides` 가 0.35.4로 고정하고 있어 역시 핀 해제가 먼저이다.
상한 없는 입력 경로 문제는 SEC-09에서 따로 다룬다.

#### SEC-01E. crossnote 경유 전이 의존성

high 이상으로 보고된 전이 패키지에는 `tar`(critical), `adm-zip`,
`extract-zip`, `undici`, `cheerio`, `jsdom`, `postcss` 계열 다수,
`source-map-js`, `minimatch`, `brace-expansion`, `ip`, `basic-ftp`,
`zod`, `puppeteer-core` 등이 있다.
대부분은 `crossnote` 를 통해 들어온다.
crossnote의 자체 의존성 목록에는 마크다운 렌더링에 필요한 범위보다
훨씬 넓은 패키지들이 들어 있다.
React 관련 패키지, `qiniu`, `imagemagick-cli`, `node-tikzjax`,
`puppeteer-core`, `chrome-paths` 등이 그 예이다.

여기서 중요한 구분이 있다.
설치되어 있다는 것과, 악성 입력이 그 코드에 닿는다는 것은 다르다.
`tar` 의 임의 파일 덮어쓰기 권고는 앱이 tar 아카이브를 풀 때만 문제가 된다.
이 앱의 확장 패키지 해제는 자체 ZIP 파서를 쓰므로 그 경로는 tar와 무관하다.
반면 crossnote는 마크다운 렌더링의 핵심 경로에 있으므로,
그 하위의 파서와 정화 관련 패키지(cheerio, markdown-it 플러그인,
mermaid, katex 등)는 악성 문서 입력이 실제로 닿는다.

문제는 이 구분을 사람이 매번 수작업으로 해야 한다는 점이다.
의존성이 1,268개에 이르면 어떤 권고가 도달 가능한지 추적하는 비용이
패치 비용을 넘어선다.
그래서 권장 방향은 건별 변명이 아니라 일괄 갱신과 자동 게이트이다.
더 근본적으로는, crossnote에서 실제로 쓰는 기능 범위만큼만 의존하도록
렌더링 파이프라인의 의존 표면을 줄이는 작업을 중장기로 검토할 가치가 있다.
이 앱은 이미 crossnote를 제한된 설정으로 감싸 쓰므로
(`render-worker.ts` 에서 스크립트 실행과 HTML5 임베드를 끄고
읽기 전용 파일시스템을 주입한다), 설정상 완화는 잘 되어 있는 편이다.

#### SEC-01F. 개발·빌드 의존성

개발 트리에서는 `tinypool` 의 프로토타입 오염을 통한 원격 코드 실행 권고와
`tar` 권고 등이 critical로 보고됐다.
`vitest`와 `vite`, `@vitest/mocker` 에도 경로 순회와 코드 주입 계열 권고가 있다.
이들은 배포 앱에 실리지 않으므로 최종 사용자 위험은 아니다.
그러나 테스트 서버를 네트워크에 노출하거나 오염된 저장소에서
테스트를 실행하면 개발자 장비가 대상이 된다.
CI도 같은 이유로 갱신 대상에 포함해야 한다.

#### 권장 조치

1. 루트 `overrides` 의 `dompurify` 와 `sharp` 핀을 최신 패치 버전으로
   올리거나, 고정이 필요한 이유를 주석으로 남기고 주기적으로 재검토한다.
2. `markdown-it` 를 14.3.3 이상, `sanitize-html` 을 2.18.1 이상으로 올린다.
3. `npm audit fix` 로 해결 가능한 전이 건을 일괄 정리한다.
   `npm audit` 출력 기준 상당수가 자동 수정 가능으로 표시됐다.
4. CI에 `npm audit --omit=dev` 를 게이트로 넣는다.
   처음에는 critical과 high를 실패 조건으로 삼고,
   도달 불가능함이 확인된 건은 사유와 만료일을 적은 예외 목록으로 관리한다.
5. 갱신 후에는 기존 검증 절차를 그대로 돌린다.
   프리뷰 관련 의존성을 건드리므로 `npm run test:preview-contract` 가
   최소 검증이다. 저장소의 `AGENTS.md` 도 같은 요구를 적고 있다.

### SEC-02. 신뢰할 수 없는 프로젝트 폴더 (Git과 언어 서버)

- 심각도: **높음**
- 가능성: 중간. 영향: 높음 (사용자 권한 코드 실행).
- 관련 파일: `src/main/project/engines/git-cli.ts`,
  `src/main/project/git-service.ts`, `src/main/project/project-service.ts`,
  `src/main/language/server-session.ts`,
  `src/main/language/server-discovery.ts`,
  `src/main/language/language-manager.ts`.

#### 관찰된 사실

프로젝트 폴더를 선택하면 앱은 그 폴더에서 Git 저장소를 찾고
상태를 조회한다. Git 실행은 `GitCli` 가 담당한다.
인자는 배열로 전달되고 `--literal-pathspecs` 가 항상 붙으며,
파일 경로는 `--` 뒤에 놓인다.
환경에는 `LC_ALL=C` 와 `GIT_TERMINAL_PROMPT=0` 만 추가로 설정된다.
명령 문자열을 셸로 실행하는 코드는 없다.

문서를 열면 언어 서버가 붙을 수 있다.
서버 탐색(`ServerDiscovery`)은 실행 파일을 찾되 실행하지는 않고,
실제 기동은 문서 세션(`ServerSession`)이 `spawn(..., { shell: false })`
로 수행한다.
탐색 범위는 PATH와 사용자 도구 디렉터리, 가상환경 등이 중심이며,
워크스페이스 안의 임의 실행 파일을 무조건 집어 실행하는 구조는
확인되지 않았다.
내장 서버도 있다. `typescript-language-server`, `pyright`,
`basedpyright` 등이 의존성에 포함되어 패키징 시 함께 실린다.

#### 왜 위험한가

인자 주입이 막혀 있어도, Git과 언어 서버는 본질적으로
"프로젝트 안의 설정을 읽어 동작하는 프로그램"이다.
공격자는 명령 인자가 아니라 설정 파일을 통해 동작을 바꿀 수 있다.

Git 쪽의 고전적인 예는 다음과 같다.
저장소의 `.git/config` 에 적힌 `core.fsmonitor`, `core.pager`,
외부 diff 드라이버, 자격 증명 헬퍼, 훅 경로는
특정 Git 명령이 실행될 때 외부 프로그램을 부른다.
이 앱은 diff에서 `--no-ext-diff` 를 쓰는 등 일부는 피하고 있지만,
상태 조회, 스테이징, 커밋, fetch, pull, push를 모두 제공하므로
훅 실행까지 포함해 Git의 실행 표면을 넓게 노출한다.
특히 커밋은 원래 훅을 실행하는 명령이다.
사용자는 "폴더를 열었을" 뿐이라고 느끼지만,
앱은 그 폴더를 신뢰하는 전제로 상태 조회를 시작한다.

언어 서버 쪽도 구조는 같다.
서버 바이너리 자체는 사용자 환경에서 찾지만,
서버는 프로젝트의 설정 파일(`tsconfig.json`, `pyproject.toml`,
`pyrightconfig.json`, `.editorconfig` 등)을 읽어 해석한다.
설정에 따라 인터프리터 선택, 추가 경로, 플러그인 성격의 동작이 달라진다.
또한 언어 서버는 프로젝트 전체를 인덱싱하면서 대량의 파일 파싱을
사용자 권한 프로세스에서 수행한다.
서버나 그 파서에 취약점이 있으면 문서를 여는 행위만으로 도달한다.

이것은 이 앱만의 버그가 아니라 편집기류 전반의 문제이다.
VS Code가 워크스페이스 신뢰를 도입한 이유가 바로 이것이다.
중요한 것은 현재 Setdown에는 이에 해당하는 확인이나 제한 모드가
확인되지 않는다는 점이다.
처음 보는 폴더를 열 때 사용자에게 "이 폴더의 Git 설정과 언어 도구가
실행될 수 있다"는 사실을 알리거나, 신뢰 전까지 자동 실행을 미루는
장치가 없다.

#### 공격 흐름 예시

1. 공격자가 문서와 소스가 담긴 저장소를 공개한다.
   `.git` 설정이나 프로젝트 설정에 실행을 유도하는 값을 심는다.
2. 피해자가 그 폴더를 Setdown으로 연다.
3. 폴더 열기와 문서 열기 과정에서 Git 조회와 언어 서버 기동이 일어나고,
   설정에 심긴 실행이 사용자 권한으로 수행된다.
4. 공격자는 사용자 계정을 얻는다. 문서, 브라우저 세션, SSH 키 등
   그 계정이 닿는 모든 것이 범위가 된다.

이 흐름이 성립하려면 구체적인 설정 악용이 필요하므로
모든 폴더 열기가 곧바로 실행으로 이어진다고 단정하지는 않는다.
그러나 통제가 없으므로, 성립 여부는 Git과 각 언어 서버의
설정 해석 방식에 전적으로 맡겨져 있다.

#### 권장 조치

1. 단기: Git 호출 시 위험한 설정을 무력화하는 옵션을 검토한다.
   예를 들어 상태 조회처럼 읽기 전용인 명령에는
   `-c core.fsmonitor=` 류의 덮어쓰기와 페이저 비활성화를 붙이고,
   환경에 `GIT_CONFIG_NOSYSTEM` 이나 훅 경로 통제를 적용할지 결정한다.
   어떤 명령에서 훅 실행이 의도된 동작인지(커밋 등) 목록을 먼저 만든다.
2. 단기: 처음 여는 폴더에 대해 최소한의 안내를 표시한다.
   자동 실행을 막지 않더라도, 사용자가 위험을 인식할 수 있게 한다.
3. 중기: 워크스페이스 신뢰 개념을 도입한다.
   신뢰하지 않은 폴더에서는 Git 자동 조회와 언어 서버 기동을 보류하고,
   문서 열람과 편집만 허용한다.
   사용자가 신뢰를 승인한 폴더 목록은 사용자 데이터에 저장한다.
4. 중기: 언어 서버가 프로젝트 설정으로 실행 파일이나 인터프리터를
   바꿀 수 있는 경로를 목록화하고, 그 경로는 신뢰된 폴더에서만 허용한다.

### SEC-03. 내장 브라우저와 Chrome 확장

- 심각도: **높음**
- 가능성: 중간. 영향: 높음 (세션 탈취, 계정 침해, 확장 권한 남용).
- 관련 파일: `src/main/browser/browser-manager.ts`,
  `src/main/browser/browser-permissions.ts`,
  `src/main/browser/browser-downloads.ts`,
  `src/main/browser/browser-extensions.ts`,
  `src/main/browser/extension-package.ts`,
  `src/main/browser/extensions/` 하위 모듈,
  `src/browser-runtime/page-preload.ts`,
  `src/core/browser/browser-url.ts`.

#### 관찰된 사실

내장 브라우저는 `WebContentsView` 로 구현되며
`session.fromPartition('persist:setdown-browser')` 라는
영속 세션을 쓴다.
`webPreferences` 는 `sandbox: true`, `contextIsolation: true`,
`nodeIntegration: false` 이며, 여기에
`nodeIntegrationInSubFrames: true` 가 붙어 있다
(`browser-manager.ts` 331-336행 부근).
이 옵션은 서브프레임에도 세션 프리로드 스크립트가 들어가게 하기 위한 것으로,
페이지 자바스크립트에 Node 권한을 주는 설정은 아니다.
실제로 페이지 프리로드(`page-preload.ts`)는 `contextBridge` 로
아무것도 노출하지 않는다.
CSS 주입과 휠 줌, Escape 전달만 수행하며,
"페이지 JS에 API를 노출하지 않는다"는 취지의 주석과 코드가 일치한다.

탐색 정책도 갖춰져 있다.
`will-navigate` 와 창 열기 핸들러는 http와 https가 아닌 주소를 막고,
외부 앱으로 넘길 때는 확인 대화상자를 띄우며 빈도 제한까지 건다
(`browser-manager.ts` 의 `external` 메서드).
허용 프로토콜은 http, https, mailto, tel 뿐이다.
주소창 입력 해석(`browserURL`)은 자격 증명이 박힌 URL을 거부하고,
스키마 없는 입력은 검색 질의로 취급한다.

권한 처리는 보수적이다.
`BrowserPermissions` 는 알림, 카메라, 마이크, 위치만 취급하고,
그 외 권한과 서브프레임 요청, 다른 오리진 요청은 거부한다.
결정은 페이지 수명에 한정되며 디스크에 저장되지 않는다.
포인터 잠금과 정화된 클립보드 쓰기만 보이는 탭에서 자동 허용된다.

다운로드는 `will-download` 에서 저장 대화상자 옵션을 강제한다.
사용자 확인 없이 파일이 조용히 내려앉는 구조는 아니다.

확장은 `electron-chrome-extensions` 와
`electron-chrome-web-store` 로 구현되어 있다.
내장 uBlock 외에도 웹스토어 ID, 로컬 폴더, ZIP, CRX로 설치할 수 있다.
Manifest V2와 V3를 모두 받는다.
설치 전에는 패키지를 스테이징 디렉터리에 풀어 권한을 요약 표시하고,
사용자가 승인해야 확정된다.
웹스토어 설치는 내려받은 패키지의 키에서 도출한 ID가 요청한 ID와
일치하는지 검사한다.
ZIP 해제는 자체 파서(`extension-package.ts`)가 담당하며,
절대 경로와 `..` 경로를 거부하고, 항목 수 상한 10,000개,
항목당 100MB, 전체 200MB 상한을 둔다.
`inflateRawSync` 에도 최대 출력 길이를 지정해 압축 폭탄을 막는다.
이 부분은 직접 구현한 파서치고 방어가 잘 되어 있다.

#### 왜 그래도 위험한가

통제가 잘 되어 있어도, 브라우저를 내장하는 순간 앱의 위험 프로필이 바뀐다.

첫째, 원격 콘텐츠의 양이 다르다.
문서 뷰어는 가끔 남의 문서를 열지만, 브라우저는 상시로 임의의
웹 콘텐츠를 실행한다.
Chromium 렌더러 취약점 하나의 가치가 그만큼 커진다.
샌드박스와 컨텍스트 격리가 있어도, 렌더러 침해는 브라우저 세션 안의
쿠키와 로그인 상태를 노리는 것으로 충분한 경우가 많다.
이 앱의 브라우저 파티션은 영속적이므로 한 번 로그인하면 세션이 남는다.

둘째, 확장은 설계상 강력한 권한을 가진다.
호스트 권한을 가진 확장은 사용자가 방문하는 페이지의 내용을 읽고 바꿀 수 있다.
MV2 확장은 웹 요청 차단 같은 더 강한 능력까지 허용한다.
설치 확인 화면이 있어도, 사용자는 대개 권한 목록을 제대로 읽지 않는다.
권한 요약이 최대 12줄로 잘리는 점(대화상자 크기 문제 때문이며
코드 주석에 이유가 적혀 있다)도 정보 전달의 한계이다.
확장 하나가 오염되거나 소유권이 바뀌면, 그 확장이 도는 모든 탭이 위험해진다.

셋째, 확장 호스트 구현 자체가 공격 표면이다.
`electron-chrome-extensions` 위에 자체 브리지
(`extensions/host-bridge.ts`, `extension-network.ts`,
`extension-downloads.ts`, `extension-permissions.ts` 등)를 얹어
Chrome API를 흉내 낸다.
확장 코드는 신뢰할 수 없는 입력인데, 그 입력을 상대하는 브리지가
메인 프로세스에서 동작한다.
이번 점검에서 이 브리지들의 입력 검증을 전수 감사하지는 못했다.
표면이 넓으므로 별도 집중 점검 대상으로 남겨 둔다.

넷째, 패치 속도이다.
Electron 버전을 올리지 않으면 Chromium 패치도 멈춘다.
자동 업데이트가 없으면 사용자는 낡은 Chromium으로 계속 웹을 돌아다닌다.
SEC-11과 연결되는 지점이다.

#### 권장 조치

1. 브라우저 세션의 민감성을 문서화하고, 가능하면 세션 데이터
   초기화 동선을 명확히 제공한다.
2. 새 확장을 설치할 때 호스트 권한이 `<all_urls>` 급이면
   한 번 더 강한 경고를 낸다. 잘린 권한 목록에는
   전체 개수를 함께 보여 준다 (현재도 초과 개수는 표시된다).
3. 확장 브리지 모듈만 대상으로 한 별도 감사를 수행한다.
   특히 다운로드, 네트워크 인증, 권한 위임 경로를 우선한다.
4. Electron 갱신 주기를 정하고 지킨다. 브라우저 기능이 있는 한
   이것은 선택이 아니라 운영 비용이다.
5. MV2 지원 종료를 검토한다. 호환성 요구가 강하지 않다면
   MV3만 받는 것이 표면을 줄인다.

### SEC-04. 메인 셸 창의 탐색 정책 누락

- 심각도: **중간**
- 가능성: 낮음 (단독으로는 공격 경로가 아님). 영향: 높음 (다른 결함과 결합 시).
- 관련 파일: `src/main/windows/window-manager.ts` (49-58행, 111-113행),
  `apps/desktop/index.html` (셸 CSP).

#### 관찰된 사실

메인 창은 셸 UI를 담는다. 보안 설정 자체는 올바르다.
`contextIsolation: true`, `nodeIntegration: false`, `sandbox: true` 가
설정되어 있고, 개발 서버 주소가 있으면 그 URL을, 없으면 로컬
`dist/index.html` 파일을 로드한다.
그러나 이 창의 `webContents` 에는 `will-navigate` 리스너도,
`setWindowOpenHandler` 도 등록되어 있지 않다.

다른 표면들과 비교하면 누락이 분명하다.
이미지 내보내기 창, 메뉴 오버레이, 위치 오버레이, 탭 드래그 창,
확장 표면은 모두 탐색과 창 열기를 거부한다.
내장 브라우저 뷰는 프로토콜 검사와 확인 절차를 거치는 핸들러를 둔다.
프리뷰 뷰도 최소한 전용 프로토콜 위에서만 동작한다.
유독 가장 권한이 넓은 프리로드를 가진 셸 창에만 이 정책이 없다.

셸에는 CSP라는 완화책이 있다.
`index.html` 의 정책은 `default-src 'self' data: blob:` 을 뼈대로 하고,
스크립트는 `'self'` 와 `'wasm-unsafe-eval'` 만 허용한다.
스타일은 `'unsafe-inline'` 을 허용하고, 이미지는 http와 https까지 허용한다.
이 정책은 셸 안에서 임의 스크립트가 도는 것을 상당 부분 막는다.

#### 왜 위험한가

셸 렌더러는 이 앱에서 가장 넓은 권한 통로를 가진다.
`src/preload/index.ts` 가 노출하는 `marktex` API는 파일 읽기와 저장,
프로젝트 조작, Git 조작, 터미널, 노트북 실행까지 닿는다.
이 API 자체는 로컬 앱 코드만 쓰도록 설계되어 있다.
탐색 정책이 없다는 것은, 어떤 이유로든 셸 창이 원격 주소로 이동하거나
팝업을 열게 되면 그 이동을 가로막는 마지막 장치가 없다는 뜻이다.
원격 페이지가 같은 `webContents` 에 로드되면 프리로드는 새 문서에도
주입되므로, 공격자 페이지가 `window.marktex` 에 닿을 수 있다.
그 순간 파일 읽기와 명령 실행에 준하는 권한이 넘어간다.

현재 코드에서 셸이 스스로 원격으로 이동하는 경로는 확인되지 않았다.
링크 클릭은 IPC를 통해 처리되고, 웹 콘텐츠는 별도 브라우저 뷰가 담당한다.
그래서 이 항목은 단독 취약점이 아니라 **심층 방어의 공백**으로 분류한다.
앞으로 셸 렌더러에서 XSS가 하나라도 나오거나, 링크 처리 로직에
구멍이 생기면, 이 공백이 피해를 결정한다.
수정 비용이 매우 작은 항목이라 우선순위는 오히려 높다.

#### 권장 조치

1. 셸 창 생성 직후 핸들러를 등록한다.
   `will-navigate` 에서는 허용된 출발점(로컬 파일 또는 개발 서버 주소)이
   아닌 이동을 모두 막는다.
   `setWindowOpenHandler` 는 항상 `deny` 를 반환한다.
2. 개발 모드 주소는 환경변수에서 오므로, 허용 목록을 만들 때
   그 값만 정확히 허용한다.
3. 기존 단위 테스트 관행에 맞춰, 셸 창 정책을 검증하는 테스트를 둔다.
   다른 창들의 정책 테스트가 이미 있는 패턴을 따르면 된다.

### SEC-05. 로컬 링크와 다운로드 파일의 OS 실행

- 심각도: **중간**
- 가능성: 중간 (클릭 유도). 영향: 높음 (OS 핸들러를 통한 실행).
- 관련 파일: `src/main/ipc/install-ipc.ts` 의 `openLink` 함수
  (258-282행, `shell.openPath` 는 274행),
  `src/main/browser/browser-downloads.ts` 의 열기 명령.

#### 관찰된 사실

문서 안의 링크를 누르면 `document:open-link` IPC를 거쳐
메인의 `openLink` 가 처리한다.
http와 https는 내장 브라우저로, mailto와 tel은
`shell.openExternal` 로 넘어간다.
로컬 자원 URL이면 경로를 정규화해 실재 파일인지 확인한 뒤,
앱이 열 수 있는 문서 형식(`isOpenableDocument`)이면 앱 안에서 열고,
아니면 `shell.openPath(checked)` 로 운영체제 기본 프로그램에 넘긴다.
인식하지 못한 프로토콜은 열지 않는다.
이 화이트리스트 방식 자체는 올바르다.

다운로드도 비슷하다.
완료된 다운로드 항목의 "열기"는 `shell.openPath` 를 호출하고,
"폴더에서 보기"는 파일 관리자를 연다.
이 경로는 사용자가 다운로드 목록에서 명시적으로 누르는 동작이다.

#### 왜 위험한가

`shell.openPath` 는 단순 열기가 아니다.
운영체제는 확장자와 파일 연결에 따라 프로그램을 실행한다.
리눅스의 `.desktop` 파일, 실행 비트가 선 스크립트 파일 관리자 연동,
윈도의 실행 파일과 설치 파일, 문서 파일에 연결된 취약한 외부 프로그램까지
모두 포함된다.
즉 마크다운 문서가 로컬 파일 링크를 걸고, 사용자가 그 링크를 누르면,
앱 밖의 임의 프로그램이 그 파일을 입력으로 실행될 수 있다.
문서만으로는 파일이 생기지 않으므로, 공격자는 대개 문서와 파일을
같이 배포하거나(압축 파일, 저장소), 사용자 컴퓨터에 있을 법한
경로를 노리는 형태로 조합한다.

완화 요인도 분명하다.
자동 실행이 아니라 사용자의 클릭이 필요하다.
열 수 있는 문서는 앱 안에서 열리므로 일상적인 상대 링크는 안전하다.
문제는 그 외 파일로 넘어갈 때 사용자에게 아무 구분도 없다는 점이다.
같은 클릭인데 어떤 경우는 앱 안 열람이고, 어떤 경우는 OS 실행이다.
사용자는 그 차이를 알 수 없다.

다운로드 열기는 그 자체가 의도된 기능이지만,
브라우저에서 받은 실행 파일을 목록에서 눌러 바로 실행하는 동선이라
경고 없는 실행이라는 점에서 같은 범주로 본다.
주류 브라우저들이 실행 파일 다운로드와 열기에 경고를 붙이는 이유와 같다.

#### 권장 조치

1. 앱이 직접 열 수 없는 로컬 파일을 OS로 넘기기 전에 확인 대화상자를 낸다.
   파일 전체 경로와, 기본 프로그램으로 열린다는 사실을 보여 준다.
2. 실행 성격이 강한 확장자(실행 파일, 설치 파일, `.desktop`, 스크립트류)는
   경고를 강화하거나 기본 동작을 "폴더에서 보기"로 바꾼다.
3. 다운로드 "열기"도 같은 기준을 적용한다.
   문서와 미디어는 바로 열고, 실행 파일류는 확인을 거친다.
4. 이 정책의 대상 목록을 코드 한곳에서 관리하고 테스트를 붙인다.
   기존에 `src/main/ipc/open-link.test.ts` 가 있으므로
   거기에 분기 검증을 추가하는 형태가 자연스럽다.

### SEC-06. 마크다운 프리뷰의 콘텐츠 보안 정책 부재

- 심각도: **중간**
- 가능성: 낮음 (정화기 우회가 전제). 영향: 높음.
- 관련 파일: `src/core/preview/preview-install.ts`
  (`createLeanPreviewTemplate`),
  `src/main/preview/render-worker.ts`, `src/main/preview/preview-manager.ts`
  (프리뷰 뷰 설정 82-86행), `src/preview-runtime/preload.ts`,
  `src/preview-runtime/content-controller.ts`.

#### 관찰된 사실

마크다운 렌더링은 워커에서 crossnote로 수행된다.
설정은 방어적으로 잡혀 있다.
`enableScriptExecution: false`, `enableHTML5Embed: false` 로 두고,
`notebook.previewScriptsEnabled = false` 를 명시하며,
읽기 전용 파일시스템을 주입한다.
프로토콜 화이트리스트도 http, https, file, marktex-resource, mailto, tel 로
제한한다.
렌더 결과는 crossnote의 정화기(`sanitizeRenderedHTML`)를 거친 HTML이라는
전제로, 프리뷰 측 설치 경로가 이를 `innerHTML` 로 심는다.
코드 주석도 이 전제를 명시하고 있다.
다만 mermaid, wavedrom, vega, tikz 같은 클라이언트 렌더링 요소가 있는
문서는 crossnote 런타임 초기화 경로로 보낸다
(`requiresCrossnoteInstall`).

프리뷰 뷰 자체는 샌드박스와 컨텍스트 격리가 켜져 있고
Node 통합이 꺼져 있다.
프리뷰 프리로드는 `contextBridge` 로 `marktexPreviewHost.send` 하나만
노출한다. 이는 `preview:message` IPC로 임의의 메시지 객체를
메인에 보낼 수 있는 통로이다.
또한 `preview:command` 로 받은 메시지를
`window.postMessage(message, '*')` 로 페이지에 전달한다.

lean 템플릿 생성 함수는 crossnote 템플릿의 head를 재사용한다.
head 안에 스크립트가 있으면 lean 경로를 포기하고 전체 런타임으로
물러서는 검사가 있다.
그러나 생성되는 프리뷰 문서에 CSP 메타 태그는 없다.
프로토콜 핸들러(`main.ts` 의 `marktex-preview` 처리)도
`content-type` 만 붙여 반환하고 보안 헤더를 붙이지 않는다.

#### 왜 위험한가

현재 구조에서 프리뷰 문서 내용의 안전은 정화기 하나에 달려 있다.
정화기는 잘 만든 부품이지만, 역사적으로 우회 사례가 반복되는 영역이다.
특히 raw HTML을 허용하는 마크다운 렌더링에서는 입력이 곧 공격 표면이다.
이 앱은 crossnote와 그 하위 파서 여럿(cheerio, markdown-it 플러그인,
mermaid 등)을 거치므로 정화 체인이 길다.
체인의 어느 한 곳에서 스크립트나 이벤트 핸들러가 새면,
프리뷰 페이지에는 그것을 실행 단계에서 막을 CSP가 없다.

스크립트가 실행되면 피해 범위는 프리뷰 안에 머물지 않을 수 있다.
프리뷰 프리로드가 노출한 `marktexPreviewHost.send` 로 메인에 메시지를
보낼 수 있고, `marktex-resource` 프로토콜로 문서 폴더 내 파일을
읽으려 할 수 있다 (SEC-07).
메인 쪽 메시지 처리가 각 메시지를 검증하는지가 다음 방어선이 된다.
즉 이 항목은 단독 결함이라기보다, "정화기가 뚫리는 날"의
피해 규모를 정하는 항목이다.

셸 쪽에 CSP가 이미 도입되어 있다는 점은 긍정적이다.
프리뷰만 같은 대우를 받지 못하고 있는 상태라고 보면 된다.

#### 권장 조치

1. 프리뷰 문서에 CSP 메타를 넣거나, 프로토콜 응답에 CSP 헤더를 붙인다.
   시작점은 `default-src 'none'` 에 가까운 정책에서 필요한 것만 여는 것이다.
   스타일과 폰트와 이미지, KaTeX와 다이어그램 런타임이 요구하는
   최소 허용을 실험으로 정한다.
   이 과정에서 bridge 스크립트가 인라인인지 파일인지 확인하고,
   인라인이 필요하면 해시나 nonce 방식을 검토한다.
2. mermaid 등 클라이언트 렌더링 경로는 문서가 요구할 때만 활성화되므로,
   그 경우에만 정책을 넓히는 차등 적용을 검토한다.
3. `marktexPreviewHost.send` 가 받는 메시지 형태를
   프리로드 단계에서 화이트리스트로 좁힌다.
   임의 객체 전달보다 `type` 검증이 있는 편이 안전하다.
4. 정화 우회를 가정한 회귀 테스트를 둔다.
   이벤트 핸들러 속성과 `javascript:` URL, SVG 기반 마크업을 넣은
   문서가 프리뷰에서 실행되지 않음을 실제 Electron으로 확인한다.
   저장소 관행상 `test:preview-contract` 에 포함시키는 형태가 맞다.

### SEC-07. `marktex-resource` 프로토콜과 프리뷰 토큰

- 심각도: **중간**
- 가능성: 낮음. 영향: 중간 (문서 폴더 내 파일 읽기).
- 관련 파일: `src/main/main.ts` (63-66행 스킴 등록, 103-114행
  `readableResource`, 138-163행 `installProtocols`),
  `src/main/preview/preview-manager.ts` (64-81행 토큰 발급),
  `src/main/preview/resource-url.ts`.

#### 관찰된 사실

두 개의 커스텀 스킴이 특권 스킴으로 등록되어 있다.
`marktex-resource` 는 `standard`, `secure`, `supportFetchAPI`,
`corsEnabled`, `stream` 특권을 가진다.
`marktex-preview` 는 `standard`, `secure`, `supportFetchAPI` 를 가진다.

자원 읽기는 검사를 거친다.
`readableResource` 는 경로를 정규화한 뒤, 열린 문서의 루트나
프로젝트 루트, crossnote 루트 안에 있을 때만 허용한다.
열린 비디오 파일은 예외적으로 그 파일 자체를 허용한다.
검사 실패 시 403을 돌려준다.
비디오는 Range 요청을 스트림으로 답하고,
그 외에는 `net.fetch` 로 파일 내용을 반환한다.

다만 응답에는 `access-control-allow-origin: *` 와
`access-control-expose-headers: Content-Range, Accept-Ranges` 가 붙는다.
코드 주석은 셸과 프리뷰의 오리진이 달라 CORS가 필요하다고 설명한다.

프리뷰 문서는 토큰으로 주소가 정해진다.
`storeDocument` 는 `${Date.now()}-${Math.random().toString(36).slice(2)}`
형태의 토큰을 발급한다.
문서는 맵에 최대 64개까지 보관되며 오래된 것부터 지워진다.
프로토콜 핸들러는 토큰만으로 문서를 돌려준다.

#### 왜 위험한가

핵심 검사는 경로 범위 검사이며, 이 검사는 존재한다.
문제는 그 주변의 여유이다.
CORS `*` 는 이 프로토콜에 접근할 수 있는 어떤 오리진의 스크립트든
응답 본문을 읽을 수 있게 한다.
범위 검사 덕분에 읽을 수 있는 파일은 열린 문서 폴더와 프로젝트 안으로
한정되지만, 프로젝트를 연 상태에서는 그 안의 모든 파일이 대상이다.
소스 코드 저장소를 프로젝트로 연 경우라면 설정 파일까지 포함된다.
내장 브라우저는 별도 파티션을 쓰므로 기본 세션에 등록된 이 핸들러에
웹페이지가 직접 닿는지는 세션 구성에 달려 있다.
그러나 프리뷰에서 스크립트가 실행되는 상황(SEC-06)에서는
같은 기본 세션 안이므로 닿을 수 있다.
결국 SEC-06의 피해 범위를 키우는 증폭 요소이다.

토큰은 보안 경계라고 보기 어렵다.
`Date.now()` 와 `Math.random()` 조합은 추측 가능성이 있고,
암호학적 난수가 아니다.
같은 세션에서 스크립트를 실행할 수 있는 공격자가 토큰을 맞히면
다른 탭의 프리뷰 HTML 전체를 읽을 수 있다.
문서 본문이 그대로 노출되는 셈이다.
반대로 스크립트 실행이 불가능한 평상시에는 이 토큰이 없어도
문제가 되지 않는다. 그래서 단독 심각도는 낮고 결합 시 중간으로 본다.

#### 권장 조치

1. 토큰을 `randomUUID()` 나 `randomBytes` 기반 값으로 바꾼다.
   이미 코드베이스 다른 곳에서 `randomUUID` 를 쓰고 있다.
2. CORS 허용 오리진을 `*` 대신 실제 요청 오리진 중 허용된 것으로 좁힌다.
   `marktex-preview://` 와 셸 오리진만 반영하는 방식이 후보이다.
   비디오 요소의 교차 오리진 재생이 필요한지는 실제 재생으로 검증한다.
3. 프리뷰 문서 보관 기간을 탭 수명과 연동한다.
   탭이 닫히면 해당 토큰은 바로 폐기하는 편이 노출 기간을 줄인다.
4. 경로 검사는 현재 방식을 유지한다.
   정규화 후 내부 판정이라는 방식 자체는 올바르고, 심볼릭 링크 처리까지
   확인한 추가 테스트를 붙이면 더 좋다.

### SEC-08. PDF 렌더링 옵션

- 심각도: **중간**
- 가능성: 낮음. 영향: 중간.
- 관련 파일: `src/renderer/pdf/pdf-runtime.ts` (`getDocument` 호출),
  의존성 `pdfjs-dist` 6.3.289.

#### 관찰된 사실

PDF는 셸 렌더러 안에서 pdf.js로 그린다.
파일 바이트는 IPC(`pdf:range`)로 범위씩 읽어 `PDFDataRangeTransport` 로
공급한다. 자동 가져오기와 스트리밍은 끄고, 청크 크기는 64KB이다.
cMap과 표준 폰트, WASM 자산은 로컬 번들에서 온다.
뷰어 옵션에는 `annotationMode: AnnotationMode.ENABLE` 이
설정되어 있어 주석과 폼이 활성화된다.
캔버스 최대 픽셀은 16M으로 제한되어 있다.
링크 클릭은 섀도 DOM에서 가로채 http, https, mailto만
앱의 링크 처리로 넘긴다.
비밀번호가 필요한 PDF는 사용자에게 물어 그 값을 pdf.js에 전달한다.

`getDocument` 호출에는 `isEvalSupported` 가 명시되어 있지 않다.
또한 스크립팅 관리자(scripting manager)를 뷰어에 연결하지 않으므로,
PDF 안의 자바스크립트 액션이 실행되는 경로는 기본적으로 닫혀 있는 것으로
보인다. 이 점은 코드로 확인한 범위에서의 판단이며,
pdf.js 내부 기본값에 대한 전수 확인은 하지 않았다.

#### 왜 위험한가

pdf.js에는 `isEvalSupported` 가 켜진 환경에서 악성 PDF의 폰트 파싱을 통해
자바스크립트 실행으로 이어졌던 전례(CVE-2024-4367)가 있다.
현재 사용 중인 6.x 버전은 그 문제를 고친 이후의 계열이지만,
옵션을 명시하지 않으면 안전 여부가 라이브러리 기본값의 변화에
그대로 노출된다.
PDF는 대표적인 불신 입력이고, 렌더링이 셸 렌더러 프로세스 안에서
일어난다는 점도 중요하다.
셸 렌더러에서 스크립트 실행이 가능해지면 SEC-10에서 다루는
넓은 프리로드 API가 바로 옆에 있다.
CSP의 `script-src 'self'` 가 완충 역할을 하겠지만,
eval 계열은 정책 해석이 미묘하므로 앱 쪽에서 명시적으로 끄는 것이 낫다.

주석 활성화 자체는 기능이지만, 주석 안의 링크와 액션이
추가 표면이라는 점은 인지할 필요가 있다.
링크 가로채기가 있어 외부 이동은 통제되고 있다.

#### 권장 조치

1. `getDocument` 에 `isEvalSupported: false` 를 명시한다.
   폰트 렌더링 품질에 영향이 없는지 샘플 PDF로 확인한다.
2. 폼 입력이 필요하지 않은 읽기 전용 용도라면
   `AnnotationMode.ENABLE_FORMS` 와 `ENABLE` 의 차이를 검토해
   필요한 최소 모드를 고른다.
3. pdf.js 갱신 시 보안 관련 기본값 변경이 없는지 릴리스 노트를 확인하는
   절차를 의존성 갱신 체크리스트에 넣는다.

### SEC-09. 이미지 처리와 자원 고갈

- 심각도: **중간**
- 가능성: 중간. 영향: 중간 (메인 프로세스 메모리 압박과 충돌).
- 관련 파일: `src/main/documents/image-edit-ipc.ts` (28행, 44행, 94행),
  `src/main/documents/image-file.ts`, `src/main/documents/pasted-image.ts`.

#### 관찰된 사실

이미지 편집은 메인 프로세스에서 `sharp` 로 처리된다.
메타데이터를 읽는 경로는 `sharp(bytes, { limitInputPixels: MAX_EDIT_PIXELS })` 로
입력 픽셀 상한을 지정한다 (28행, 94행).
그런데 미리보기 PNG를 만드는 경로는
`sharp(bytes).autoOrient().resize(...).png().toBuffer()` 로
상한 지정이 없다 (44행).
`sharp` 의 기본 입력 픽셀 제한이 있기는 하지만,
이 앱이 정한 상한과 같은지는 확인하지 않았다.

이미지 편집은 별도 표면이 따로 있다.
`image-export` 파티션을 가진 숨은 창에서 캔버스 렌더링을 수행하고,
그 창의 HTML에는 `default-src 'none'` 수준의 CSP가 있다.
이 격리 자체는 좋은 설계이다.

#### 왜 위험한가

압축 폭탄 이미지는 작은 파일이 거대한 픽셀 버퍼로 풀리는 공격이다.
메인 프로세스에서 디코딩하면 메모리가 메인에서 소모되고,
앱 전체가 느려지거나 강제 종료될 수 있다.
사용자가 악성 이미지를 편집기로 여는 행위만으로 도달한다.
네이티브 디코더(sharp와 libvips, librsvg)의 메모리 취약점과 결합하면
단순 DoS를 넘는 결과도 가능하다.
SEC-01D의 librsvg 권고와 같은 맥락이다.

#### 권장 조치

1. 모든 `sharp` 호출에 `limitInputPixels` 를 일관되게 지정한다.
   상한 상수를 한곳에서 가져오도록 정리한다.
2. 입력 바이트 자체의 크기 상한도 확인한다.
   파일 크기 상한과 픽셀 상한은 서로 보완 관계이다.
3. SVG처럼 문서 성격이 강한 형식은 래스터 상한과 별개로
   외부 참조를 막는 설정이 적용되는지 확인한다.
   librsvg가 파일이나 네트워크 참조를 따라가지 않는 구성을 검증한다.
4. 거대한 선언 크기를 가진 이미지 샘플로 회귀 테스트를 만든다.

### SEC-10. IPC 표면과 발신자 검증 일관성

- 심각도: **중간**
- 가능성: 낮음. 영향: 높음.
- 관련 파일: `src/main/ipc/window-ipc.ts`, `src/main/ipc/install-ipc.ts`,
  `src/preload/index.ts`, `src/protocol/desktop-api.ts`.

#### 관찰된 사실

IPC 등록은 대체로 잘 구조화되어 있다.
`windowIpc` 헬퍼는 모든 핸들러에서 `event.sender.id` 로 창 상태를 찾고,
없으면 거부한다.
즉 임의의 `webContents` 가 채널을 불러도 자기 창에 속한 상태로만 동작한다.
여러 핸들러에 입력 검증이 들어가 있다.
예를 들어 떨어뜨린 파일 경로는 절대 경로인지, 길이가 16,384를 넘지 않는지,
널 바이트가 없는지 검사한다.
노트북 마크다운 렌더링은 열린 노트북인지와 1MB 상한을 검사한다.
프로젝트 파일 조작은 `assertProjectFile`, `assertDocument` 같은
범위 검사를 거친다.

예외가 하나 있다.
`document:discard` 는 이 래퍼를 쓰지 않고
`ipcMain.handle` 로 직접 등록되어 있다 (`install-ipc.ts` 166행).
발신자 창 상태 확인 없이 받은 문서 스냅샷을 그대로 폐기 처리한다.

또 하나 눈에 띄는 것은 표면의 너비이다.
셸 프리로드가 노출하는 `marktex` API는 문서, 프로젝트, Git, 브라우저,
터미널, 노트북, 언어 서버, 이미지 편집까지 백 수십 개의 호출을 묶는다.
이 중에는 설계상 강력한 것도 있다.
`document:read-location` 은 절대 경로나 `file:` URL이면
그 파일을 읽어 돌려준다. 프로젝트 범위 검사가 없는, 의도된
"위치로 열기" 기능이다.
`terminal:write` 와 `notebook:run` 은 각각 셸 입력과 코드 실행이다.

#### 왜 위험한가

이 구조의 안전은 "셸 렌더러 코드는 신뢰할 수 있다"는
단일 전제에 기대고 있다.
셸 렌더러는 로컬 번들이고 CSP가 걸려 있어 평상시에는 이 전제가 성립한다.
그러나 셸 안에서 스크립트 실행이 가능해지는 결함이 하나라도 생기면
(정화 우회, 렌더러 의존성 XSS, 탐색 정책 부재와 결합한 원격 로드 등),
공격자는 곧바로 파일 읽기와 코드 실행에 준하는 권한을 얻는다.
다른 Electron 앱들도 같은 구조를 흔히 쓰지만,
이 앱은 API 표면이 특히 넓어 결합 시 피해가 크다.

`document:discard` 의 불일치는 그 자체로는 사소하다.
현재 이 채널을 부를 수 있는 것은 해당 프리로드를 가진 셸뿐이기 때문이다.
다만 패턴이 깨진 지점이 하나 있으면, 나중에 프리로드를 공유하거나
새 표면이 늘 때 실수가 복사되기 쉽다.
일관성 자체가 통제라고 보고 기록한다.

#### 권장 조치

1. `document:discard` 를 `channels.handle` 로 옮겨 발신자 검증을 통일한다.
   문서가 해당 창의 것인지 확인하는 조건을 더한다.
2. 채널 목록을 점검해, 원시 `ipcMain.handle` 과 `ipcMain.on` 으로
   직접 등록된 곳이 더 있는지 전수 확인한다.
   언어 서버와 프리뷰 IPC처럼 별도 모듈에서 등록하는 것도 포함한다.
3. 강력한 핸들러(임의 경로 읽기, 터미널 입력, 노트북 실행,
   파일 삭제와 이동)에는 창 상태에 더해 "사용자 동작에서 비롯됐는가"에
   준하는 추가 조건을 둘 수 있는지 검토한다.
   최소한 각 핸들러의 입력 상한과 범위 검사가 문서화되어 있는지 확인한다.
4. 프리로드 API 변경 시 보안 검토 항목으로 취급한다.
   새 메서드를 노출할 때마다 반대편 검증을 함께 요구하는 관행이 도움이 된다.

### SEC-11. Electron 배포 강화와 업데이트

- 심각도: **중간**
- 가능성: 중간 (시간이 지날수록 증가). 영향: 높음.
- 관련 파일: `apps/desktop/package.json` 의 `build` 설정,
  `apps/desktop/scripts/rebuild-native.mjs`, `src/main/main.ts` (52행 재기동).

#### 관찰된 사실

Electron은 개발 의존성 `44.7.2` 로 선언되어 있고,
실제 설치 버전도 그와 같음을 확인했다.
패키징은 `electron-builder` 이며 리눅스는 AppImage, deb, rpm을,
윈도는 NSIS 설치 파일을 만든다.
자동 업데이트 구성(`electron-updater` 등)은 확인되지 않았다.
Electron fuses를 뒤집는 설정도 보이지 않는다.
`asarUnpack` 으로 sharp, node-pty, pyright, 타입스크립트,
언어 서버, 커널 브리지 스크립트 등이 풀린 채 실린다.

시작 과정에는 특이한 재기동 로직이 있다.
X11 백엔드가 필요하면 앱이 `--ozone-platform=x11` 을 붙여
자신을 다시 실행한다.
주석은 Electron의 재실행기가 설정하는 `no_new_privs` 를 피하기 위해서이며
렌더러 샌드박스는 바뀌지 않는다고 설명한다.
재기동은 단일 인스턴스 잠금을 잡기 전에 일어나고,
넘기는 인자는 기존 인자에서 ozone 관련 항목을 뺀 것이다.

터미널은 PTY 환경에서 `ELECTRON_RUN_AS_NODE` 와 `NODE_OPTIONS` 를 지운다.
패키징된 Electron 바이너리가 Node처럼 도는 경로를 의식한 처리이다.

#### 왜 위험한가

자동 업데이트가 없으면 보안 패치의 전달이 사용자 수동 재설치에 달린다.
일반 문서 뷰어라면 치명적이지 않을 수 있지만,
이 앱은 내장 브라우저와 확장을 품고 있어 Chromium 패치 지연이
곧 노출 기간이 된다.

fuses는 패키징된 앱의 런타임 스위치를 잠그는 장치이다.
설정이 없으면 기본값이 적용되는데, 그중 `RunAsNode` 계열은
앱 바이너리를 Node 실행기로 쓰는 길을 남긴다.
터미널 환경에서 관련 변수를 지운 처리는 좋은 방어이지만,
공격자가 이미 셸을 얻은 상황에서는 큰 의미가 없다.
가치는 낮은 권한의 발판을 코드 실행으로 키우는 경로를 줄이는 데 있다.
또한 `--inspect` 류 인자를 막는 퓨즈도 기본 상태에 맡겨져 있다.

재기동 로직은 그 자체로 취약점이라기보다 주의 지점이다.
제어권을 넘기는 인자에 파일 경로가 포함될 수 있으므로,
인자 해석이 흔들리면 의도치 않은 파일 열기나 옵션 주입으로 번질 수 있다.
현재 코드는 인자를 배열로 넘기고 ozone 항목만 걸러내므로
구체적인 결함은 확인되지 않았다.

#### 권장 조치

1. `@electron/fuses` 로 배포 시점에 퓨즈를 명시적으로 설정한다.
   `RunAsNode` 를 끄고, Node 옵션과 검사 인자를 막으며,
   asar 무결성 검증을 켜는 구성을 검토한다.
   네이티브 모듈을 푸는 현재 구성과 충돌하지 않는지 패키징 후 실행으로
   검증한다.
2. 자동 업데이트를 도입하거나, 최소한 새 버전 알림을 제공한다.
   서명과 배포 채널이 필요한 작업이라 중기 과제로 두되,
   브라우저 기능을 유지하는 한 우선순위를 낮추지 않는다.
3. Electron 갱신을 정기 작업으로 정한다.
   갱신 시에는 Chromium 보안 수정 포함 여부를 릴리스 노트에 적는
   관행을 만들면 사용자가 업데이트 시점을 판단하기 쉽다.

### SEC-12. 노트북 실행 (설계상 코드 실행)

- 심각도: **중간**
- 가능성: 중간 (사회공학). 영향: 높음.
- 관련 파일: `src/main/notebook/kernel-manager.ts`,
  `src/main/notebook/kernel-bridge.py`,
  `src/main/notebook/notebook-ipc.ts`,
  `src/renderer/notebook/notebook-content.ts`.

#### 관찰된 사실

노트북 처리는 조심스럽게 설계되어 있다.
파일을 여는 것만으로는 커널이 뜨지 않는다.
클래스 주석이 "명시적으로 시작된 커널만, 파일 열기 시 실행 없음"을
명시하고, 코드도 실행 요청에서만 프로세스를 만든다.
실행 요청은 `validateNotebookRun` 이 아이디 형식, 절대 경로와 `.ipynb` 여부,
셀 수와 셀당 1MB·전체 4MB 상한을 검사한다.
Python은 `shell: false` 로 실행되며 `-E -u` 플래그를 쓴다.
브리지(`kernel-bridge.py`)는 노트북 메타데이터의 kernelspec 명령을
따르지 않고, 선택된 인터프리터로 직접 커널 스펙을 구성한다.
표준 입출력 프로토콜에는 메시지 크기 상한과 이벤트 종류 검사가 있다.

저장된 출력의 표시는 불신 전제이다.
`notebookHtml` 은 다른 앱에서 "신뢰됨"으로 표시된 출력도 정화한다.
스크립트, iframe, SVG, 폼, 스타일을 금지하고,
이미지는 래스터 데이터나 허용된 자원 URL만 남기며,
링크는 http와 https만 유지한다.
텍스트 출력은 ANSI 이스케이프를 제거하고 표시 길이를 제한한다.

#### 왜 그래도 위험한가

실행 버튼을 누르면 노트북의 코드 셀이 사용자 권한으로 그대로 돈다.
이것은 버그가 아니라 노트북이라는 형식의 본질이다.
위험은 사용자가 그 사실을 얼마나 분명히 아는지에 달려 있다.
남이 만든 노트북은 "문서처럼 생긴 프로그램"이다.
출력은 저장된 채로 예쁘게 보이므로, 실행하면 같은 결과가 나올 것이라는
인상을 준다. 실제로는 셀 내용이 무엇이든 실행된다.
선택된 Python 환경이 프로젝트의 가상환경이라면,
그 환경에 설치된 패키지까지 실행 범위에 들어간다.

또한 인터프리터 선택 경로가 있다.
사용자가 고른 Python 경로가 실행 파일인지 검사하지만,
그 경로 자체가 악성 프로젝트 안에 있는 실행 파일을 가리키도록
유도될 여지는 사용자 선택 단계에 남아 있다.

#### 권장 조치

1. 처음 보는 노트북에서 첫 실행을 할 때, 코드가 사용자 권한으로
   실행된다는 확인을 한 번 표시한다.
   같은 파일의 반복 실행에서는 방해가 되지 않게 생략한다.
2. 현재 어떤 인터프리터로 실행되는지 실행 버튼 근처에 상시 표시한다.
   이미 실행 이벤트에 Python 경로가 포함되므로 표시 재료는 있다.
3. SEC-02의 워크스페이스 신뢰를 도입한다면, 신뢰하지 않은 폴더의
   노트북 실행도 그 확인 흐름에 묶는다.

### SEC-13. 통합 터미널

- 심각도: **낮음**
- 가능성: 낮음. 영향: 높음 (그 자체가 셸이므로).
- 관련 파일: `src/main/terminal/terminal-manager.ts`,
  `src/main/terminal/terminal-ipc.ts`.

#### 관찰된 사실

터미널은 `node-pty` 로 사용자 셸(윈도에서는 PowerShell)을 실행한다.
세션은 창 소유자 단위로 관리되고, 아이디와 크기 값은 검증되며,
창당 최대 12개로 제한된다.
환경은 프로세스 환경을 물려받되 `ELECTRON_RUN_AS_NODE` 와
`NODE_OPTIONS` 를 삭제한다.
출력은 확인응답(ack) 기반으로 흐름이 제어되어,
과도한 출력이 IPC를 마비시키지 않도록 상한에서 일시 정지한다.
시작 디렉터리는 존재하는 디렉터리인지 확인해 fallback 한다.

#### 평가

터미널은 사용자가 명시적으로 여는, 그 자체가 코드 실행인 기능이다.
이 앱에서 추가로 생기는 위험은 주로 두 가지이다.
하나는 다른 기능의 결함이 터미널 입력 채널(`terminal:write`)로
번지는 경우로, SEC-10의 셸 API 논의와 같다.
다른 하나는 악성 프로그램 출력이 터미널 에뮬레이터의 이스케이프
해석을 악용하는 고전적 문제이다.
xterm 계열 렌더링을 쓰므로 해석은 그 라이브러리의 몫이며,
제목 변경 같은 시퀀스가 UI를 속이는 수준을 넘지는 않는 것으로 본다.
환경에서 위험한 변수 두 개를 지운 것은 좋은 처리이다.
이 항목은 기록 목적이며 별도 조치는 요구하지 않는다.

### SEC-14. 자원 고갈 전반

- 심각도: **낮음**
- 가능성: 중간. 영향: 낮음 (앱 응답성 상실 수준).
- 관련 파일: `src/main/preview/render-worker.ts`,
  `src/main/project/engines/ripgrep-files.ts`,
  `src/main/project/engines/git-cli.ts`,
  `src/main/notebook/kernel-manager.ts`,
  `src/renderer/pdf/pdf-runtime.ts`.

이 앱은 큰 입력에 대한 상한을 여러 곳에 두고 있다.
확인된 예는 다음과 같다.
Git 출력은 최대 버퍼와 타임아웃이 있고,
ripgrep 파일 목록도 10초 타임아웃과 최대 버퍼가 있다.
노트북 실행은 셀 크기와 전체 크기에 상한이 있고,
커널 프로토콜 버퍼는 10MB를 넘으면 실패 처리한다.
PDF는 캔버스 픽셀 상한 16M이 있고,
노트북 출력 표시는 길이 제한과 절단을 한다.
확장 아카이브 해제는 항목 수와 크기 상한이 있다.
터미널 출력은 흐름 제어가 있다.

남는 구멍은 파싱 시간의 상한이다.
마크다운 렌더링의 2차 복잡도 권고(SEC-01B)처럼,
크기는 작아도 시간이 폭발하는 입력은 바이트 상한으로 막히지 않는다.
렌더링이 워커에 있어 메인까지 멈추지는 않지만,
워커가 하나의 문서에 묶이면 후속 렌더가 줄줄이 늦어진다.
워커 작업에 시간 상한을 두고, 초과 시 그 작업을 포기하고
오류를 표시하는 방식이 후보이다.
다만 수식이 많은 정상 문서의 렌더가 본래 무거운 앱 특성상,
상한을 정하는 일은 성능 계약과 맞물린다.
저장소의 프리뷰 성능 계약 문서를 함께 보며 정해야 한다.

또 다른 지점은 파일 크기 상한의 일관성이다.
텍스트 파일에는 상한 상수가 있으나, 모든 문서 형식과 모든 읽기 경로에
같은 상한이 적용되는지는 이번에 전수 확인하지 않았다.
큰 파일을 여는 행위가 곧 메모리 요구로 이어지는 경로가 있다면
같은 범주의 위험으로 본다.

권장 조치는 두 가지이다.
첫째, 마크다운 파서를 패치 버전으로 올려 알려진 2차 경로를 없앤다.
둘째, 워커 작업과 자식 프로세스 호출에 이미 있는 타임아웃 관행을
렌더 작업에도 확대 적용할지 검토한다.

### SEC-15. 로컬에 저장되는 데이터

- 심각도: **낮음**
- 가능성: 낮음 (로컬 접근 전제). 영향: 중간 (개인정보 노출).
- 관련 파일: `src/main/reading/reading-position-store.ts`,
  `src/main/settings/auto-save-store.ts`,
  `src/main/browser/browser-downloads.ts`,
  `src/main/browser/browser-places.ts`,
  `src/main/editor/snapshot-store.ts`, `src/main/main.ts` 의 상태 파일 생성부.

앱은 사용자 데이터 디렉터리에 여러 상태 파일을 평문 JSON으로 쓴다.
읽기 위치, 자동 저장 설정, 최근 폴더, 다운로드 기록, 줌 설정이 그렇다.
브라우저의 방문 기록과 북마크는 별도 표면의 IndexedDB에 저장된다.
편집기 스냅샷은 복구용 문서 내용을 담을 수 있다.
브라우저 쿠키는 Chromium 프로필의 일반적인 방식으로 저장된다.

이것은 데스크톱 앱의 평범한 방식이며, 그 자체로 결함은 아니다.
기록하는 이유는 두 가지이다.
첫째, 사용자 계정을 얻은 공격자나 기기를 공유하는 사람에게는
읽은 문서의 경로와 방문 기록이 그대로 개인정보이다.
둘째, 스냅샷과 자동 저장 데이터는 원본 문서를 지워도 내용이 남을 수 있어,
"삭제했다"는 사용자 기대와 어긋날 수 있다.
상태 파일 쓰기는 임시 파일에 쓰고 이름을 바꾸는 원자적 방식을 사용해
손상 대응은 되어 있는 것으로 확인했다.

권장 조치는 가볍다.
기록과 스냅샷을 지우는 동선을 UI에 명확히 드러내고,
무엇이 어디에 저장되는지 문서화한다.
암호화는 같은 계정의 공격자를 막지 못하므로 우선순위가 낮다.
다만 브라우저 세션을 오래 유지하는 설계인 만큼,
쿠키 저장소가 OS 키체인 기반 암호화를 쓰는지 Electron 기본 동작을
확인해 두는 정도는 가치가 있다.

### SEC-16. 저장소 위생과 공급망 표면

- 심각도: **낮음**
- 가능성: 낮음. 영향: 중간 (개발·빌드 환경).
- 관련 파일: `.gitignore`, `.gitmodules`, `vendor/`,
  `apps/desktop/scripts/` 의 빌드 스크립트들.

시크릿 검색에서는 하드코딩된 키나 토큰, `.env` 파일을 찾지 못했다.
검색에 걸린 `token` 관련 문자열은 문서 토큰과 권한 토큰 같은
코드 식별자였다.
다만 `.gitignore` 에 `.env` 계열 항목이 없다.
지금은 해당 파일이 없으므로 문제없지만,
앞으로 누가 로컬 환경 파일을 만들면 실수로 커밋될 수 있다.
한 줄이면 막을 수 있는 종류의 위생 항목이다.

저장소에는 서브모듈이 매우 많다.
`.gitmodules` 에는 crossnote와 monaco, vscode부터 브라우저와
확장 관련 프로젝트까지 수십 개가 등록되어 있고,
`vendor/` 아래에 체크아웃되어 있다.
이들은 참조와 연구 목적이 강해 보이며, 빌드가 실제로 무엇을
가져다 쓰는지는 이번 점검 범위를 벗어난다.
공급망 관점에서는 두 가지를 권한다.
하나는 서브모듈을 재귀적으로 받는 과정에서 실행되는 스크립트가 있는지
확인하는 것이다.
다른 하나는 빌드 산출물에 실제로 들어가는 것이 `node_modules` 의
선언된 의존성뿐인지, `vendor` 의 복사본이 섞이지 않는지 명시하는 것이다.
복사해서 쓰는 코드가 있다면 그 부분은 자체 코드로 취급해 감사 대상에
포함해야 한다.

빌드 스크립트는 `apps/desktop/scripts/` 에 모여 있고
전용 테스트(`npm run test:tooling`)가 존재한다.
개발 실행은 Vite 개발 서버를 `127.0.0.1` 에만 바인딩하므로
개발 중 외부 노출 면은 작다.
이 항목은 배포 사용자보다 개발 환경을 지키는 차원의 기록이다.

## 7. 잘 되어 있는 통제 (긍정적 확인 사항)

위험만 나열하면 그림이 왜곡된다.
이번 점검에서 확인한, 유지해야 할 통제를 정리한다.
이 목록은 회귀 방지 기준으로도 쓸 수 있다.

### 7.1 Electron 창과 뷰 설정

확인한 생성 지점은 모두 같은 보안 3종을 지켰다.
대표 위치는 다음과 같다.
메인 셸 `src/main/windows/window-manager.ts`,
프리뷰 `src/main/preview/preview-manager.ts`,
PDF 내보내기 `src/main/preview/pdf-exporter.ts`,
이미지 내보내기 `src/main/documents/image-export-manager.ts`,
메뉴 오버레이 `src/main/menu/menu-overlay.ts`,
위치 오버레이 `src/main/browser/location-overlay.ts`,
Places `src/main/browser/browser-places.ts`,
리더 내보내기 `src/main/browser/reader-exporter.ts`,
확장 표면 `src/main/browser/extensions/extension-surface.ts`,
탭 드래그 `src/main/browser/browser-tab-drag.ts`,
브라우저 뷰 `src/main/browser/browser-manager.ts`.
보조 창 다수는 여기에 탐색 거부와 창 열기 거부까지 더했다.
`webSecurity` 를 끄거나 `allowRunningInsecureContent` 를 켜는 설정은
발견되지 않았다.
TLS 인증서 오류를 무시하는 코드도 발견되지 않았다.

### 7.2 프리로드 설계

셸 프리로드는 `contextBridge.exposeInMainWorld('marktex', api)` 로
타입이 정해진 객체 하나만 노출한다.
`ipcRenderer` 자체나 임의 채널 호출 기능은 노출하지 않는다.
이벤트 구독은 채널별로 감싼 함수로만 제공되며 해제 기능을 돌려준다.
페이지 프리로드와 프리뷰 프리로드는 노출 표면이 더 좁다.
특히 페이지 프리로드는 아무것도 노출하지 않는다.

### 7.3 프로세스 실행

`shell: true` 사용은 발견되지 않았다.
확인한 실행 지점은 모두 인자 배열과 `shell: false` 또는 `execFile` 이다.
Git은 `--literal-pathspecs` 와 `--` 분리를 쓰고,
diff는 `--no-ext-diff` 를 쓴다.
ripgrep은 `--no-config` 와 빈 설정 경로 환경으로 사용자 설정을 배제한다.
언어 서버와 Python 커널도 같은 방식이며,
분석 준비 작업은 "명시적 설정 동작에서만, 고정 인자, 셸 없음"이라는
주석과 함께 시간과 출력 상한을 둔다.
터미널은 위험한 환경 변수 두 개를 지우고 시작한다.

### 7.4 URL과 외부 링크 정책

주소 해석은 한곳(`src/core/browser/browser-url.ts`)에 모여 있고
테스트가 있다.
http와 https만 웹 주소로 인정하고,
자격 증명이 포함된 주소와 과도한 길이를 거부한다.
브라우저의 외부 앱 열기는 프로토콜 화이트리스트,
확인 대화상자, 빈도 제한, 보이는 탭에서만 허용이라는 조건을 겹쳤다.
문서 링크 열기도 같은 화이트리스트를 따르며
모르는 프로토콜은 열지 않는다.

### 7.5 권한과 다운로드

웹 권한은 기본 거부, 주 프레임의 동일 오리진만, 페이지 단위 결정,
영구 저장 없음, 동시 요청 수 제한과 타임아웃을 갖췄다.
다운로드는 저장 대화상자를 강제하고,
다운로드 기록은 불러올 때 형태 검증을 거쳐 비정상 행을 버린다.

### 7.6 확장 패키지 처리

자체 ZIP/CRX 파서는 경로 순회를 거부하고 크기 상한을 둔다.
설치는 스테이징, 권한 표시, 승인, 확정의 단계를 거친다.
웹스토어 설치는 기대한 확장 ID와 실제 패키지의 ID 일치를 검사한다.
내장 확장은 사용자 설치로 덮을 수 없게 막혀 있다.

### 7.7 노트북과 웹 리더의 불신 전제

노트북은 열기로 실행되지 않고, 메타데이터가 실행 명령을 정하지 못한다.
저장된 출력은 출처의 신뢰 표시와 무관하게 정화한다.
웹 리더 본문은 셸에서 그리기 전에 DOMPurify를 거치고,
내보내기 시에는 메인에서 `sanitize-html` 로 다시 정화하며
쇄용 창에는 별도 CSP를 건다.
리더 내보내기 창의 정책은 `default-src 'none'` 기반이다.

### 7.8 자원 프로토콜의 범위 검사

`marktex-resource` 읽기는 정규화된 경로가 열린 문서나 프로젝트
루트 안에 있을 때만 허용된다.
상위 폴더 임의 읽기를 막는 이 검사는 핵심 통제로서 올바르게 자리 잡고 있다.
SEC-07의 지적은 이 검사의 부재가 아니라, 그 주변 설정(CORS와 토큰)에
관한 것이다.

### 7.9 IPC 입력 검증 관행

주요 핸들러들은 길이 상한, 절대 경로 여부, 형식 검사, 소유 검사를
갖추고 있다. 프로젝트 파일 연산은 범위 확인 함수를 거친다.
브라우저 탭 생성은 아이디 형식과 히스토리 항목을 검증한다.
이 검증들이 있는 덕분에, 발신자가 셸 렌더러로 제한되는 현재 구조에서는
메인 프로세스가 비정상 입력에 비교적 단단하다.

## 8. 종단 간 공격 시나리오

개별 항목이 어떻게 이어지는지 보기 위해 대표 흐름 네 가지를 적는다.
어느 흐름도 이번에 실제 재현한 것은 아니다.
각 단계가 어떤 발견 항목에 기대는지 표시했다.

### 시나리오 A. 악성 마크다운 파일

1. 공격자가 raw HTML과 다이어그램을 섞은 마크다운을 배포한다.
   문서 안에는 정화기 우회를 노리는 마크업과, 로컬 파일 링크가 들어 있다.
2. 사용자가 프리뷰를 연다.
   - 정화기가 막으면 여기서 끝난다. 현재로서는 이 결과가 기대값이다.
   - 파서가 2차 복잡도 입력에 걸리면 프리뷰가 오래 멈춘다 (SEC-01B).
   - 정화 우회가 성립하면 프리뷰에서 스크립트가 돈다.
     CSP가 없어 실행 단계의 차단은 없다 (SEC-06).
3. 스크립트는 `marktexPreviewHost.send` 로 메시지를 보내고,
   `marktex-resource` 와 CORS `*` 를 이용해 문서 폴더의 파일을 읽는다
   (SEC-07).
4. 사용자가 본문의 로컬 링크를 누르면 앱이 못 여는 파일이
   OS 핸들러로 실행될 수 있다 (SEC-05).

차단 지점은 정화기, CSP, 자원 프로토콜 범위, 링크 확인의 네 곳이다.
현재는 첫 지점과 범위 검사만 서 있고 중간 두 지점이 비어 있다.

### 시나리오 B. 악성 저장소 폴더

1. 공격자가 그럴듯한 오픈소스 프로젝트를 공개한다.
   코드와 문서가 정상처럼 보이고, `.git` 설정과 프로젝트 설정에
   실행 유도 값을 심는다.
2. 사용자가 폴더를 프로젝트로 연다.
   Git 상태 조회와 파일 감시가 시작된다 (SEC-02).
3. 사용자가 소스 파일을 열면 언어 서버가 기동해 프로젝트 설정을 읽는다.
4. 사용자가 노트북이 있으면 열어 본다.
   실행 버튼을 누르기 전까지는 안전하다 (SEC-12).
5. 어느 단계에서든 설정 기반 실행이 성립하면 사용자 권한을 얻는다.

이 흐름은 취약점 하나가 아니라 "열면 도구가 돈다"는 관행 전체에 기대므로,
대응도 패치가 아니라 신뢰 확인이라는 제품 결정이 필요하다.

### 시나리오 C. 악성 웹사이트와 확장

1. 사용자가 내장 브라우저로 공격자 사이트를 방문한다.
2. 사이트는 팝업, 외부 프로토콜, 권한 요청, 다운로드를 시도한다.
   이 단계의 통제는 확인 대화상자와 권한 기본 거부가 막는다.
3. 사이트가 Chromium 렌더러 취약점을 노리면 결과는 패치 수준에 달린다.
   자동 업데이트 부재로 노출 기간이 길어질수록 가능성이 커진다
   (SEC-03, SEC-11).
4. 별도로, 사용자가 유용해 보이는 확장을 설치한다.
   호스트 권한을 가진 확장은 이후 모든 탭의 내용을 읽을 수 있다.
5. 다운로드한 실행 파일을 목록에서 바로 열면 경고 없이 실행된다
   (SEC-05).

### 시나리오 D. 오염된 의존성을 통한 공급망 경로

1. 전이 의존성 하나에 취약점이나 악성 버전이 생긴다.
2. 고정된 핀과 자동 게이트 부재로 발견이 늦어진다 (SEC-01).
3. 그 패키지가 렌더링이나 정화처럼 불신 입력 경로에 있으면
   문서 열기가 곧 도달 경로가 된다.
   빌드 도구 쪽이면 개발자와 CI가 대상이 된다 (SEC-01F, SEC-16).

이 흐름은 확률 게임이다.
의존성 1,268개를 유지하는 한, 통제는 개별 패키지의 선의가 아니라
감사와 갱신의 자동화여야 한다.

### 9.4 작업 순서에 대한 의견

의존성 갱신과 셸 창 탐색 정책은 서로 독립적이므로 병행할 수 있다.
CSP 도입은 프리뷰 렌더 결과에 영향을 줄 수 있어
의존성 갱신과 같은 변경에 섞지 않는 편이 좋다.
원인 분리가 쉬워야 회귀를 잡을 수 있다.
워크스페이스 신뢰는 제품 경험에 닿는 변경이라
범위를 정하는 논의가 먼저 필요하고, 그 논의 전까지는
Git 설정 무력화 같은 소극적 조치를 먼저 넣어 두는 순서가 안전하다.

## 10. 잔여 위험과 수용 기준 제안

모든 조치를 마쳐도 남는 위험이 있다.
이를 명시해 두면 "고쳤다"는 말의 범위가 분명해진다.

- **렌더러와 파서의 제로데이.**
  Chromium, pdf.js, sharp, Monaco, crossnote 체인은 방대하다.
  패치를 따라가는 것 외에 근본 대책은 없다.
  수용 기준은 "알려진 취약점이 도달 가능 경로에 남아 있지 않을 것"과
  "패치 릴리스를 낼 수 있는 절차가 있을 것"으로 잡는 것이 현실적이다.
- **확장의 본질적 권한.**
  호스트 권한 확장을 허용하는 한, 확장 선택에 따른 위험은 남는다.
  수용 기준은 설치 시 정보 제공의 충실성과 제거의 용이성이다.
- **터미널과 노트북의 의도된 실행.**
  사용자가 직접 실행하는 기능은 막는 것이 대책이 아니다.
  수용 기준은 실행이 명시적 동작에서만 일어난다는 점이며,
  현재 설계는 이를 대체로 지키고 있다.
- **폴더 신뢰의 사회적 측면.**
  확인 대화상자를 넣어도 사용자는 습관적으로 승인할 수 있다.
  그래도 승인이라는 행위가 존재하면 자동 실행과는 책임 경계가 다르다.
- **로컬 데이터 평문.**
  같은 계정 공격자에 대한 방어는 OS의 몫이다.
  앱의 수용 기준은 저장 위치와 삭제 방법의 투명성이다.

이 보고서의 높음 항목 셋 중 SEC-01과 SEC-03은 운영으로 관리하는
위험이고, SEC-02는 제품 정책으로 결정해야 하는 위험이다.
어느 쪽도 일회성 패치로 끝나지 않으므로,
로드맵의 완료 기준은 "조치를 넣었다"가 아니라
"조치가 유지되는 절차가 있다"가 되어야 한다.

## 13. 부록 C. 확인하지 못한 항목과 후속 검증 계획

정적 감사만으로 확정할 수 없었던 항목들이다.
후속 작업에서 실제로 확인해야 할 목록으로 남긴다.

### 동적 검증이 필요한 항목

1. **정화 체인의 실제 우회 여부.**
   raw HTML, 이벤트 속성, SVG, MathML 변형 마크업을 넣은 문서를
   실제로 열어, 프리뷰와 노트북 출력과 웹 리더 어디에서도
   스크립트가 실행되지 않는지 확인해야 한다.
   CSP를 넣은 뒤에는 같은 문서로 정책 차단까지 재확인한다.
2. **브라우저 파티션에서 자원 프로토콜에 닿는가.**
   `protocol.handle` 이 기본 세션에 등록되는 구성에서,
   `persist:setdown-browser` 파티션의 웹페이지가
   `marktex-resource://` 를 가져올 수 있는지 실제 실행으로 확인한다.
   결과에 따라 SEC-07의 가능성 평가가 바뀐다.
3. **Git 설정 기반 실행의 성립 여부.**
   `core.fsmonitor` 등을 심은 시험 저장소를 격리 환경에서 열어,
   폴더 열기와 상태 조회만으로 외부 프로그램이 도는지 확인한다.
   성립하면 SEC-02의 우선순위를 높이고,
   어떤 설정 키가 문제인지 목록을 만든다.
4. **언어 서버 설정 경로.**
   악성 `pyrightconfig.json` 이나 `tsconfig.json` 이
   인터프리터나 플러그인 실행으로 이어지는지 서버별로 확인한다.
5. **PDF 스크립팅 상태.**
   자바스크립트 액션이 들어 있는 샘플 PDF와 폰트 기반 시험 파일로,
   스크립트가 돌지 않음을 확인한다.
6. **이미지 폭탄과 악성 SVG.**
   선언 픽셀이 거대한 이미지와, 외부 참조를 가진 SVG를 열고
   메모리 사용과 네트워크·파일 접근이 없는지 본다.
7. **패키징 산출물.**
   빌드된 AppImage를 풀어 asar 내용과 `asarUnpack` 파일을 확인하고,
   fuses 상태를 검사 도구로 읽어 본다.
   의도하지 않은 파일(시험 자료, 소스 맵의 민감 정보 등)이
   실렸는지 점검한다.

### 도구 도입 제안

- Electron 전용 정적 검사 도구(예: electronegativity류)를 CI에 넣어
  이번 보고서의 수작업 검사를 상시 검사로 바꾼다.
- `npm audit` 외에 OSV 기반 스캐너를 병행하면 npm 권고 DB에 없는
  항목까지 볼 수 있다.
- 악성 입력 회귀 모음을 테스트 픽스처로 승격한다.
  정화와 파서를 건드릴 때마다 같은 입력으로 다시 확인하는 구조가
  가장 값싼 방어이다.

### 재점검 시점 제안

- 즉시 조치 묶음을 적용한 직후. 감사 수치와 셸 정책을 재확인한다.
- CSP와 CORS 변경 도입 후. 기능 회귀와 차단 효과를 함께 본다.
- Electron 메이저 갱신 때. `webPreferences` 기본값 변화가 없는지
  생성 지점을 다시 훑는다.
- 확장과 브라우저 관련 큰 변경 때. 브리지 감사를 포함한다.
