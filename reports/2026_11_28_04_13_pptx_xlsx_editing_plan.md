# PPTX와 XLSX를 Word 편집기와 같은 방식으로 편집하게 만드는 방안

작성일: 2026-11-28 · 계획 보고서 · 기준 `950e9de486d218bf2ba93a34a60be477802b1044` · Electron 45.3.3 · 현재 뷰어 `@file-viewer/*` 3.3.3 · Word 편집기 `@docx-editor.dev/core` 2.41.1

Word 편집기를 만든 eigenpal의 자매 저장소 두 개를 서브모듈로 넣고, 그 엔진을 실제 Electron에서 실제 문서로 돌려 본 뒤 쓴 계획이다. 제품 코드는 바꾸지 않았다. 표시는 세 가지다.

- **확인**: 2026-11-28에 이 기기에서 직접 실행하거나 원본 파일에서 직접 본 것.
- **추정**: 실행하지 않고 코드나 문서를 읽어 내린 판단.
- **제안**: 내 권고다.

실험 코드, 결과 파일, 화면 비교 그림은 [office-editors-spike-2026-11-28/](office-editors-spike-2026-11-28/)에 있다. 사용자의 덱으로 찍은 화면은 저장소에 넣지 않고 `target/validation/office-editors-spike-2026-11-28/`(git 제외)에 두었다.

## 구현 결과 (같은 날 추가)

아래 계획의 PPTX 부분은 같은 날 구현했다. 이 절만 구현 뒤에 썼고, 나머지는 계획 당시 그대로다. 구현이 지키는 것과 소유 모듈은 `docs/contracts/reading-surfaces.md`의 "Presentation editing" 절에 있다.

| 계획 | 구현된 것 |
| --- | --- |
| 7.1 공용화 | `main/documents/office-package.ts`·`office-edit-ipc.ts`, `renderer/office-edit/`(세션 기반, 글꼴 공급, 어느 편집기의 탭인지 판정). Word 편집기는 이 공용 코드를 쓴다 |
| 7.2 화면 | 읽기는 세로로 이어진 슬라이드, 편집은 옆 목록과 무대. 글자를 더블 클릭하면 그 슬라이드의 그 자리에서 편집이 시작되고, `Esc` 한 번으로 읽기로 돌아온다 |
| 7.3의 면 뽑기 | `core/fonts/font-collection.ts`. 글꼴 모음의 0번 아닌 면도 단일 글꼴로 넘긴다 |
| 7.3의 줄 높이 | 필요 없었다. 엔진은 글꼴과 무관하게 줄을 글자 크기의 1.2배로 잡고 대체 글꼴의 줄 상자를 읽지 않는다. 그래서 줄 상자를 선언하지 않는다 |
| 7.5의 4단계 | 새 슬라이드·복제·삭제와 글상자·도형·선·표(3 × 3)·그림 파일 넣기. 순서 바꾸기는 넣지 않았다 |
| 아이콘 | Seti에 없는 프레젠테이션·한글 문서 아이콘 두 개를 직접 그려 넣고, Office 계열 확장자를 모두 계열 아이콘으로 보낸다(`core/files/office-file-icons.ts`) |

계획과 달라진 점과 새로 알게 된 것.

- **저장본의 바이트.** 엔진은 저장할 때 XML 부품을 모두 다시 쓴다. 3.2절의 비교는 공백을 정규화한 내용 비교였고 그 결론(내용이 같다)은 그대로다. 바이트는 원본이 XML을 어떻게 썼느냐에 달렸다. LibreOffice가 만든 테스트 덱은 부품 20개 중 17개의 바이트가 달라진다(빈 요소가 `<a/>` 꼴이 되고, 선언에 `standalone`이 붙고, 요소 사이 줄바꿈이 없어진다). 테스트는 고치지 않은 부품의 내용을 비교한다. Setdown은 고치지 않은 덱을 저장하지 않는다.
- **글꼴이 도착하는 순서.** 엔진은 글꼴 파일을 받은 뒤 브라우저에 글꼴을 등록하고, 등록이 끝나야 덱을 다시 배치한다. 이미 그려 둔 슬라이드 그림은 브라우저가 한가할 때에야 고쳐 그린다. 그래서 한글 글꼴이 없는 기기에서는 덱이 열린 직후 한글이 잠깐 네모로 보였다(확인: 묶음 글꼴만 설치한 기기를 흉내 낸 테스트). 지금은 두 단계가 끝난 뒤에 덱을 열고, 그 전에는 슬라이드 그림을 청하지 않는다.
- **`Esc`.** 엔진의 `Esc`는 글 → 도형 → 선택 없음으로 한 단계씩 물러난다. 읽기로 돌아가려면 세 번이 필요해서, 화면이 엔진보다 먼저 `Esc`를 받는다(조합 중의 `Esc`는 입력기 것으로 둔다).
- **편집 메뉴의 실행 취소.** 엔진은 무대 안의 자기 `textarea`로 글자를 받는다. "입력 칸은 자기 기록을 쓴다"는 규칙이 이 칸까지 잡아서 메뉴의 실행 취소가 엔진에 닿지 않았다. 무대 안의 칸은 예외로 했다.

8절의 결함은 이렇게 되었다. 원 저장소에는 아무것도 올리지 않았다.

| 결함 | 상태 |
| --- | --- |
| file-viewer의 EMF 경로 | Setdown 빌드에서 고친 사본을 쓴다(이전과 같음) |
| pptx-editor: `p:style` 채우기 | 그대로다. 계약 문서에 알려진 한계로 적었다 |
| pptx-editor: 글꼴 모음의 0번 아닌 면 거부 | Setdown 쪽에서 면을 뽑아 넘겨 피했다 |
| xlsx-editor의 세 가지 | 그대로다. XLSX는 지금 뷰어에 남는다 |

## 결론

**PPTX는 지금 넣을 수 있다. XLSX는 지금 넣으면 안 된다.**

| | PPTX (`@pptx-editor.dev/core` 0.8.0) | XLSX (`@xlsx-editor.dev/core` 0.1.0-beta.2) |
| --- | --- | --- |
| 실제 문서 열기 | 손상되지 않은 덱 87개 중 87개 | 통합 문서 340개 열림. 유효한 Strict 형식 4개는 거부 |
| 고치지 않고 저장 | 87개 모두 부품 손실 없음 | 339개 모두 부품 손실 없음 |
| 화면 | 현재 뷰어보다 LibreOffice에 가깝다(184장 중 113장, 반대 16장) | 차트 등은 안 그린다. 격자와 서식은 그린다 |
| 편집 후 저장 | 바뀐 슬라이드 부품 하나만 달라지고 LibreOffice가 연다 | 수식 결과가 **틀린 채로** 저장되고 LibreOffice가 그 틀린 값을 보여 준다 |
| 실제 한글 입력기 | 정상 | 셀을 고르고 바로 치면 첫 음절이 깨진다(`한글` → `gㅏㄴ글`) |
| 망가진·악성 파일 | 퍼저 산출물 10개를 모두 거부하고 계속 동작 | 110 KB 파일 하나가 렌더러 프로세스를 죽인다(현재 뷰어는 0.3초에 연다) |
| 설치된 글꼴 공급 | Word 편집기와 같은 API로 동작 | 다른 API지만 동작 |
| 판단 | **도입** (제안) | **보류**, 조건이 채워지면 다시 측정 (제안) |

PPTX를 넣을 때 Setdown이 새로 만드는 것은 엔진이 아니다. Word 편집기 때와 같은 세 가지다: 엔진을 감싸는 런타임 모듈 하나, Svelte로 만든 작은 도구 막대와 슬라이드 목록, 저장 전 검사. 글꼴 공급·편집 세션·저장 규칙은 Word 편집기 것을 일반화해서 같이 쓴다(7절).

| 단계 | 내용 | 끝나면 얻는 것 |
| --- | --- | --- |
| 1 | Word 편집기의 공용 부분 일반화: 글꼴 공급, 편집 세션, 저장 IPC | 동작 변화 없음. 두 번째 편집기를 받을 자리 |
| 2 | `.pptx` 읽기 화면을 새 엔진으로 교체(보기 모드) | 지금보다 정확한 슬라이드 화면, 한글 글꼴 포함 |
| 3 | 편집: 글자 고치기, 실행 취소, 저장, 다른 이름으로 저장, 복구 | 덱의 글을 고쳐 저장 |
| 4 | 슬라이드 추가·복제·삭제·순서, 작은 도구 막대 | "모바일 Google Slides" 수준의 편집 |
| 보류 | XLSX 편집 | 6절의 조건이 채워진 뒤 |

먼저 정해 주셔야 할 것은 10절의 두 가지다.

## 1. 무엇을 어떻게 쟀나

| 항목 | 내용 |
| --- | --- |
| 서브모듈 | `vendor/pptx-editor` `9f53f40`(2026-11-27, v0.8.0), `vendor/xlsx-editor` `b118923`(2026-11-25, v0.1.0-beta.2). 인덱스에 올려 두었고 커밋하지 않았다 |
| 실험 방식 | 저장소 밖 작업 폴더에 npm의 Apache-2.0 패키지 두 개만 설치. React·Vue 없이 엔진만 붙인 페이지 두 개를 Vite(`base: './'`)로 빌드해 **`file://`에서**, 샌드박스가 켜진 실제 Electron 45.3.3으로 열었다. Setdown 렌더러가 로드되는 방식과 같다 |
| 화면 | 모든 실행은 `scripts/with-isolated-display.sh`의 숨은 화면에서 했다. 사용자 바탕화면에는 창이 뜨지 않았다 |
| 덱 묶음 | Apache POI `test-data/slideshow` `f63b77b`(2026-11-25)의 `.pptx` 95개와 `.pptm` 3개. 버그 번호가 붙은 파일이 많다 |
| 통합 문서 묶음 | 같은 커밋의 `test-data/spreadsheet`에서 `.xlsx` 353개와 `.xlsm` 14개 |
| 한글 문서 | `elice-bsg/presentation_files` `5e68519`(MIT)의 25장 덱(맑은 고딕, 한글 1,484자), `eGovFramework/egovframe-common-components` `4d6fc7f`(Apache-2.0)의 통합 문서 |
| 사용자 문서 | 사용자가 준 9장짜리 덱의 사본(로고가 EMF인 그 덱). 저장소에는 넣지 않았다 |
| 기준 렌더러 | LibreOffice 26.8.2(전용 프로필, 창 없음)로 PDF를 만든 뒤 쪽마다 그림으로 바꿨다 |
| 현재 뷰어 | 이 작업 트리로 빌드한 Setdown에서 같은 덱을 열어 슬라이드마다 찍었다 |

LibreOffice는 정답이 아니라 세 번째 의견이다. 예를 들어 사용자의 덱 로고(EMF)는 LibreOffice가 아예 그리지 않는다(확인).

## 2. 두 저장소가 주는 것

Word 편집기와 구조가 같다. `core` 패키지가 틀 없이 쓸 수 있는 편집기를 내주고, 도구 막대와 메뉴는 React·Vue 어댑터에만 있다.

| | pptx-editor | xlsx-editor |
| --- | --- | --- |
| 첫 배포 | 2026-11-05 (0.1.0) | 2026-11-23 (0.1.0-beta.0) |
| 지금 | 0.8.0 (2026-11-26). 3주 동안 9번 배포(0.1.0 → 0.8.0) | 0.1.0-beta.2 (2026-11-25) |
| 저장소의 자기 평가 | 없음 | README 첫 줄: "**Beta.** XLSX Editor is not ready for production use. The API can change in each release." |
| 붙이는 법 | `createPptxEditor()` → `attach(element)` → `load(bytes)` → `save()` | `createXlsxEditor()` → `attach(element)` → `load(bytes)` → `save()` |
| 그리는 곳 | SVG DOM | Canvas 2D |
| 엔진이 직접 하는 것 | 선택과 핸들, 제자리 글 편집, 조합 입력, 키보드, 클립보드, 실행 취소 | 셀 편집, 키보드, 클립보드, 행·열·병합, 실행 취소 |
| 호스트가 만들어야 하는 것 | 도구 막대, 슬라이드 목록, 노트, 찾기 막대 | 도구 막대, 수식 입력줄, 시트 탭 |
| 호스트용 도우미 | `CHROME_GROUPS`(22묶음 119개), `toolbarCommandState`, `runToolbarCommand`. **Word 편집기와 이름이 같다**(확인) | `CHROME_GROUPS`(13묶음 44개), 같은 이름의 도우미 |
| 계산 | 해당 없음 | **없다.** 문서의 표현: "The engine never evaluates a formula. It shows the cached value." 수식 엔진은 계획만 있다(작업 17개 중 0개 완료, 추정: 저장소 문서를 읽음) |
| 라이선스 | `core`는 Apache-2.0. 차트 그리기 등은 별도 Pro 패키지(평가판 라이선스) | `core`는 Apache-2.0 |

Pro 패키지는 설치하지도 실행하지도 않았다. Apache 패키지는 Pro를 import하지 않는다(추정: 소스 검색).

## 3. PPTX 실측

### 3.1 열기, 저장, 다시 열기

| 측정 | 결과 (확인) |
| --- | --- |
| `file://`에서 로드 | HarfBuzz WASM(444 kB)과 묶음 글꼴이 그대로 로드됨. 페이지 오류 0, 실패한 요청 0 |
| 덱 98개 열기 | 87개 열림. 나머지 11개는 zip이 아닌 파일이다(퍼저 산출물 10개, 이름만 `.pptx`인 파일 1개). 엔진은 `damaged`로 보고하고 죽지 않는다 |
| 열기 시간 | 중앙값 31 ms, 상위 10% 47 ms, 최대 112 ms(48장짜리) |
| 저장 시간 | 중앙값 7 ms, 최대 659 ms |
| 저장한 것을 다시 열기 | 87개 모두 열리고 슬라이드 수가 같다(합계 558장) |
| 메모리 | 같은 덱을 40번 열고 닫아도 수집 후 힙 13 → 15 MiB. 48장 덱은 힙 23 MiB, 렌더러 전체 220 MiB |

87개 덱에 들어 있는 것: 노트 29, 애니메이션 28, 전환 24, 포함된 개체 21, 표 20, EMF·WMF 그림 18, VML 13, 차트 11, SmartArt 6, 동영상·소리 2, 댓글 1, 포함 글꼴 1.

### 3.2 고치지 않고 저장했을 때 잃는 것

원본과 저장본을 부품 단위로 비교했다(XML은 공백을 정규화한 뒤 비교).

| 검사 | 결과 (확인) |
| --- | --- |
| 빠지거나 생긴 부품 | 87개 중 0개 |
| 그림·글꼴·포함 개체 같은 이진 부품 | 87개 모두 바이트까지 같음 |
| 저장된 XML이 올바른 XML인가 | 87개 모두 |
| XML 내용까지 모두 같은 덱 | 86개 |
| 다른 1개 | `LIBRE_OFFICE-100610-0.pptx`의 슬라이드 8에서 표 칸 속성(`a:tcPr`)이 추가됨. 원인은 분석하지 않았다 |

애니메이션, 전환, 노트, 포함 개체처럼 엔진이 그리지 않는 내용도 저장하면 그대로 남는다.

| 포함 개체(OLE) | 회색 상자에 "ole" | 엉뚱한 파란 그라데이션 | 미리보기 그림 |

현재 뷰어가 차트를 안 그리는 것은 4초를 기다려도 같았다(확인: 두 덱에서 150 ms 뒤와 4초 뒤의 그림이 픽셀까지 같다). 그래서 차트 때문에 읽기 화면이 지금보다 나빠지지는 않는다.

### 3.4 편집

사용자 덱의 첫 슬라이드 제목을 실제 마우스·키보드 입력으로 고쳤다(확인).

1. 제목을 한 번 누르면 그 자리에 커서가 놓인다(엔진의 숨은 입력 칸이 포커스를 받는다).
2. `End`, 영문과 숫자 입력, 한글 문자열 삽입(입력기 없이) → 슬라이드에 바로 반영.
3. `Esc` → 도형 선택 상태. `Ctrl+Z` → 원래 제목. `Ctrl+Y` → 고친 제목. 연속으로 친 글자는 실행 취소 한 번으로 묶인다.
4. 저장 22 ms. 부품 67개 중 **`ppt/slides/slide1.xml` 하나만** 달라졌다.
5. 엔진으로 다시 열면 고친 제목이 보인다. LibreOffice도 9쪽으로 열고 첫 쪽에서 고친 제목을 읽는다.

해 보지 않은 편집: 그림 넣기, 표 편집, 도형 옮기기·크기 바꾸기, 슬라이드 추가·삭제·순서 바꾸기, 다른 앱과의 복사·붙여넣기.

### 5.2 편집하면 생기는 일

`54524.xlsx`: `A2`=1, `A3`=2, `A4`=`SUM(A2:A3)`(저장된 결과 3). 실제 키보드로 고쳤다(그림: [xlsx-stale-sum.png](office-editors-spike-2026-11-28/images/xlsx-stale-sum.png)).

| 동작 | 결과 (확인) |
| --- | --- |
| `A2`에 40 입력 | `A4`는 계속 **3**을 보여 준다. 엔진 상태에는 `stale: true`가 서지만 격자에는 아무 표시가 없다 |
| `B1`에 `=A2+1` 입력 | 칸이 **비어** 보인다 |
| 저장 | `calcChain.xml`이 빠지고 `fullCalcOnLoad="1"`이 붙는다. `A4`에는 옛 값 `<v>3</v>`이 그대로, `B1`에는 값 없이 수식만 저장된다 |
| 그 파일을 LibreOffice 26.8.2(새 프로필, 기본 설정)로 열기 | `B1` = 41(계산됨). **`A4` = 3**. 합계가 틀린 채로 보인다 |

`fullCalcOnLoad`는 Excel에게 "열 때 다시 계산하라"는 표시다. Excel은 따를 것이다(추정: Excel이 없어 확인하지 못했다). LibreOffice는 기본 설정에서 저장된 값을 믿는다(확인). 즉 Setdown에서 숫자 하나를 고쳐 저장한 파일을 LibreOffice 사용자에게 보내면 틀린 합계를 보게 된다.

## 6. XLSX를 지금 넣지 않는 이유와 다시 볼 조건

이유는 넷이다. 모두 5절에서 확인한 것이다.

1. **계산이 없다.** 고친 값에 딸린 수식 결과가 틀린 채 저장되고, LibreOffice가 그 값을 그대로 보여 준다. 묶음의 37%가 수식을 쓴다.
2. **한글을 셀에 바로 치면 깨진다.**
3. **작은 파일 하나가 창을 죽인다.**
4. 저장소가 스스로 베타라고 하고, 유효한 Strict OOXML 파일을 열지 못한다.

선택지는 셋이다.

| | 내용 | 판단 |
| --- | --- | --- |
| A | 지금 뷰어를 유지하고, 새 버전이 나올 때마다 [spike/](office-editors-spike-2026-11-28/spike/)의 스크립트로 다시 잰다 | **권고** |
| B | 수식이 없는 통합 문서(묶음의 63%)에서만 값 고치기를 허용 | 2번과 3번이 그대로 남는다. 수식 있는 파일에서 "왜 여기선 안 되냐"가 된다. 권하지 않는다 |
| C | 계산 엔진(HyperFormula는 GPL-3.0, IronCalc는 MIT/Apache)을 옆에 붙인다 | 엔진의 공개 API에는 수식 칸의 결과 값을 밖에서 넣을 길이 보이지 않는다(추정). 엔진 내부를 고쳐야 하고, 그러면 포크를 떠안는다. 권하지 않는다 |

다시 볼 조건(제안). 앞의 셋은 자료 폴더의 스크립트(`edit-xlsx.mjs`, `ime.mjs`, `poc.mjs`)로 그대로 다시 확인할 수 있다.

- 값을 고치면 딸린 수식이 다시 계산되어 보이고, 그 값이 저장된다.
- 셀을 고르고 바로 친 한글이 온전히 들어간다.
- `poc-shared-strings.xlsx`를 열어도 렌더러가 살아 있다.
- 베타 딱지가 떨어진다.

### 7.2 화면 (제안)

요청하신 기준은 "버튼이 적고 메모장처럼 고치는" 모바일 문서 앱이다. 슬라이드에서 그에 해당하는 모양은 다음과 같다.

- **읽을 때**: 지금처럼 슬라이드가 세로로 이어진다. 엔진의 `renderThumbnail`로 슬라이드마다 정적인 그림을 만든다.
- **고칠 때**: 슬라이드의 글을 누르면 그 슬라이드가 편집 무대가 되고 그 자리에서 커서가 놓인다. 3.4절에서 확인한 동작이다.
- **도구 막대**: 실행 취소·다시 실행, 글꼴 크기, 굵게·기울임·밑줄, 글자색, 정렬, 글머리표, 슬라이드 추가·복제·삭제, 배율. 엔진의 119개 중 15개 안팎이다. 표·그림·도형·애니메이션 도구는 넣지 않는다.
- 엔진의 `CHROME_GROUPS`가 아이콘 경로를, `toolbarCommandState`가 켜짐·꺼짐을, `runToolbarCommand`가 실행을 맡는다. `DocxSurface.svelte`의 도구 막대 코드와 같은 패턴이다.

`.pptx`만 이 화면으로 연다. `.pptm`, `.potx`, `.ppsx`, `.ppt` 등은 지금의 읽기 전용 뷰어에 남긴다(Word에서 `.docx`만 편집기로 여는 것과 같은 규칙). PDF 저장은 지금 경로를 그대로 둔다.

### 7.3 글꼴

1. `installedFontSupply`와 `koreanLastResort`를 공용 위치로 옮긴다. 두 함수는 엔진의 글꼴 타입을 모르는 채로 테스트되어 있다.
2. 주 프로세스의 글꼴 응답에서 모음 파일의 면은 독립 글꼴 한 개로 뽑아 보낸다. 모음 파일의 표 목록에서 그 면의 표만 모아 새 sfnt를 쓰는 순수 함수이고, `core/fonts/font-file.ts`가 이미 읽는 구조다. Word 엔진은 면 번호를 받으므로 Word 쪽 동작은 바꾸지 않는다.
3. 없는 한글 글꼴을 대신 그릴 때의 줄 높이. Word용 값(`koreanLineBox`)은 Word의 줄 간격 규칙에서 나온 것이라 PowerPoint에는 맞지 않을 수 있다(추정). PowerPoint가 저장한 덱에는 첫 슬라이드의 미리보기 그림(`docProps/thumbnail.jpeg`)이 들어 있는 경우가 많으니, 그것과 줄 위치를 대조해 값을 정한다.

### 7.4 지켜야 할 것과 테스트

Word 편집기의 E2E 요구사항이 그대로 요구사항이다: 읽기에서 편집으로, 저장 후 다시 열기, 한글 조합 입력, 다른 이름으로 저장, 밖에서 바뀐 파일을 덮어쓰지 않기, 링크, 프로세스가 죽은 뒤 복구, 이름만 `.pptx`인 파일 거부. 여기에 더한다.

- 고치지 않고 저장한 덱이 원본과 부품 단위로 같다(3.2절의 검사를 단위 테스트로).
- 한 슬라이드의 글을 고치면 그 슬라이드 부품만 달라진다.
- 맑은 고딕 덱이 설치된 한글 글꼴로 그려진다(엔진의 `substitutedFonts`로 단언).
- 차트·OLE 자리 표시 상자가 든 덱을 저장해도 차트·개체 부품이 그대로다.
- 실제 입력기 순서로 친 한글이 온전하다(3.5절의 순서를 한 번의 `evaluate`로 재생).

`docs/contracts/reading-surfaces.md`의 Office 절에 `.pptx` 예외를 `.docx`와 같은 형식으로 적고, `docs/architecture/external-code.md`에 패키지 행을 더한다. 미리보기 성능 계약의 범위(미리보기 준비·표시, 원본 ↔ 읽기 전환)는 건드리지 않는다.

## 9. 확인하지 못한 것

- **Windows와 macOS.** 모든 실행은 Linux의 숨은 X 화면에서 했다.
- **Microsoft Office로 열어 보기.** 저장본은 엔진 자신과 LibreOffice 26.8.2로만 열었다.
- **긴 편집.** 글자 입력, 실행 취소, 저장만 했다. 3.4절 끝에 적은 편집은 해 보지 않았다.
- **엔진의 보기 모드.** 찾기, 배율, 슬라이드 쇼는 API가 있는 것만 보았고 돌리지 않았다.
- **`renderThumbnail`의 비용.** 7.2절의 "세로로 이어진 읽기 화면"이 큰 덱에서 빠른지는 2단계에서 잰다. 느리면 한 장씩 보여 주는 무대와 옆 목록으로 바꾼다.
- **Setdown 렌더러 안에서의 빌드.** 실험은 별도 Vite 프로젝트였다. Setdown의 CSP에는 이미 `wasm-unsafe-eval`이 있고(확인) 같은 방식으로 자산을 싣는 Word 엔진이 빌드되고 있으므로 문제는 없을 것이다(추정).
- **Pro 패키지.** 설치하지 않았다.
- **Ecma 고지와 GPL-3.0-only의 양립.** 4절.
- 화면 유사도 점수는 거친 척도다. 순위를 가리는 데만 썼고, 0.96과 0.94의 차이에 의미를 두지 않는다. 그림을 직접 본 판단은 3.3절의 표에 따로 적었다.

## 10. 정해 주실 것

1. **PPTX를 7절대로 진행할지.** 진행한다면 읽기 화면을 "세로로 이어진 슬라이드"(지금과 같은 느낌)로 할지, "한 장 + 옆 목록"(PowerPoint 느낌)으로 할지. 내 권고는 앞의 것이다.
2. **8절의 결함을 원 저장소에 알릴지.**

XLSX는 6절의 조건이 채워질 때까지 지금 뷰어로 둔다.
