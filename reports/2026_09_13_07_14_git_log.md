결론부터 말하면, Git 기록상 Setdown의 단기 개발 밀도는 **극도로 높은 편**이다. 주관적으로 점수를 매기면 단기 프로토타이핑 밀도는 약 **9/10**이다.

다만 현재 전체 히스토리는 마지막 `ending readme`까지 77개 커밋·54시간 5분이다. 이 마지막 커밋은 README와 그래프 생성 코드이므로, 앱 개발 자체는 기존 그래프처럼 약 53시간 39분으로 보는 것이 적절하다.

### 시간 밀도

| 지표 | 결과 |

커밋의 약 82%가 앞선 커밋으로부터 30분 이내에 나왔다. 작업을 시작하면 거의 끊기지 않고 구현·확인·수정을 반복했다는 뜻이다.

90분 이상의 공백을 별도 작업 세션으로 간주하면 여섯 세션으로 나뉜다. 그중 핵심 세션은 다음 세 개다.

| 세션 | 커밋 | 관측 구간 |
|---|---:|---:|
| 9월 11일 오후 | 20개 | 3시간 15분 |

전체 커밋의 약 **90%인 69개가 이 세 구간에 집중**됐다. 마지막 세션에서는 밤 11시 33분부터 아침 7시 5분까지 28개 커밋이 이어졌다.

또한 전체 커밋 중 34개, 약 44%가 밤 11시부터 오전 7시 59분 사이에 만들어졌다. 이는 높은 집중도를 보여주지만 지속 가능한 개발 리듬은 아니었다.

### 코드 변화 밀도

README·보고서·lockfile·자산·vendor를 제외한 코드 경로만 계산하면 다음과 같다.

| 지표 | 결과 |
|---|---:|
| 코드 변경 커밋 | 62개 |
| 추가 | 13,747줄 |
| 삭제 | 3,642줄 |
| 총 churn | 17,389줄 |
| 최종 코드 | 10,105줄 |
| 코드 커밋당 churn 중앙값 | 137줄 |
| 상위 25% 경계 | 425줄 |
| 상위 10% 경계 | 638줄 |

최종 코드는 10,105줄이지만 실제 Git이 기록한 수정량은 17,389줄이다. 3,642줄을 삭제하면서 다시 만들었기 때문이다.

```text
13,747줄 추가
− 3,642줄 삭제
= 10,105줄 최종 코드
```

총 churn은 최종 코드량의 약 1.72배다. 단순히 코드를 한 방향으로 쌓은 것이 아니라, 상당한 양을 폐기하고 교체했다는 뜻이다. 커밋 이름에서도 이러한 흐름이 보인다.

```text
성능의 복귀
일단 개선
일단 빠름
흔들림 완화
듀얼코어 전환
성능 개선
멀티코어 활용하기
```

즉, 이 개발은 사전에 완성된 설계를 그대로 입력한 과정이라기보다 **실행하면서 병목을 발견하고 구조를 반복적으로 바꾼 탐색형 개발**이었다.

### 가장 변화가 컸던 커밋

|---|---:|---:|---:|
| `transition` | 1,588 | 57 | 1,645 |

특히 `일단 빠름`은 1,052줄을 건드렸지만 순증가는 100줄뿐이다. 이것은 기능 추가보다 기존 구현을 대규모로 다시 구성한 커밋이다. 짧은 기간에도 단순 누적뿐 아니라 구조 교체가 일어났다.

### 테스트 밀도

최종 10,105줄의 구성은 다음과 같다.

| 구성 | 줄 수 | 비율 |
|---|---:|---:|
| 제품·지원 코드 | 8,280줄 | 81.9% |
| 테스트 코드 | 1,784줄 | 17.7% |
| 루트 설정 | 41줄 | 0.4% |

현재 확인되는 테스트 케이스는 86개다. 코드 변경 커밋 62개 중 39개가 테스트 파일도 건드렸다. 약 **63%의 코드 커밋이 테스트 변경을 동반한 셈**이다.

53시간짜리 프로젝트가 기능 구현에만 몰리지 않고 코드의 약 18%를 테스트에 사용한 것은 좋은 신호다. 단기 프로토타입치고 검증 밀도도 높다.

### 밀도가 집중된 장소

역사적 churn이 가장 컸던 파일은 다음과 같다.

| 파일 | 누적 churn |
|---|---:|
| `src/renderer/main.ts` | 4,613줄 |
| `src/main/main.ts` | 3,910줄 |
| `src/preview/bridge.ts` | 1,311줄 |

세 파일이 전체 코드 churn의 약 **57%**를 차지한다. 빠른 개발의 중심이 탭·UI·렌더링·프로세스 제어를 담당하는 세 거대 파일에 집중됐다는 의미다.

이것은 두 가지를 동시에 보여준다.

- 핵심 제품 경험을 매우 빠르게 깊게 구현했다.
- 속도를 얻는 대신 구조적 복잡성이 몇 파일에 축적됐다.

따라서 가장 정확한 결론은 이것이다.

> Setdown은 53시간 동안 많은 코드를 쌓은 프로젝트가 아니라, 53시간 안에 제품 구조를 여러 번 바꾸면서도 실행 가능한 결과와 테스트를 함께 남긴 고밀도 개발 스프린트였다.

밀도는 확실히 높았다. 오히려 다음 과제는 더 빠르게 만드는 것이 아니라, 그 속도로 생긴 복잡성을 천천히 정리하고 실제 사용자에게 검증하는 것이다.
