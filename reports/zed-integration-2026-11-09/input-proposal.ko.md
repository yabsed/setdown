**실제로 Zed 소스를 가져와 깊게 도입한다면, 내가 가장 설득력 있다고 보는 구조는 “Setdown의 문서·UI 위에, Zed에서 가져온 언어 도구 실행 계층을 붙이는 것”이야.**

여기서 “가져온다”는 것은 `LspInstaller`라는 이름만 흉내 내서 TypeScript로 새로 만드는 수준이 아니야. **Zed의 Rust 코드와 언어 확장 코드를 실제로 빌드하고 실행하며, Setdown은 그 위에 필요한 연결부를 만드는 방식**을 말해.

다만 조사하면서 중요한 경계도 확인했어. **언어 도구 실행 계층을 가져오는 것과 Zed의 프로젝트 엔진 전체를 가져오는 것은 규모가 상당히 다른 작업**이야.

아래는 Zed의 `b5cd310b3b54…` 커밋과 Setdown의 현재 언어 지원 문서, 그리고 Zed Svelte 확장의 실제 소스를 읽고 내린 설계 판단이야. 통합 빌드나 성능 검증을 수행한 결과는 아니므로, 가능한 구조와 이미 확인한 구현을 구분해서 설명할게.

## 1. 먼저 정정할 것: Zed에서 가져올 것은 다운로드 코드보다 훨씬 많다

앞에서는 내가 “자동 설치 계층을 추가하면 된다”에 너무 초점을 맞췄어.

그것은 **최소 개선안**으로는 맞지만, 네가 말하는 강한 도입을 충분히 설명하지 못해.

Zed의 실제 구현에서 재사용할 가치가 큰 것은 다음과 같은 묶음이야.

| 실제 Zed 구성 요소 | 맡고 있는 책임 |
|---|---|
| `node_runtime` | Node 실행 환경과 npm 패키지를 다루는 공통 기반 |
| `languages` | 내장 언어별 서버 설치·실행·설정 어댑터 |
| `language_extension` | 언어 확장을 언어 서버 어댑터로 연결 |
| `extension_host` | Rust로 작성되어 WASM으로 컴파일된 확장을 실행 |
| `project`의 관련 서비스 | 프로젝트 루트, 실행 환경, 툴체인, 버퍼와 LSP의 관계 관리 |
| `remote_server`의 `HeadlessProject` | 화면 없이 프로젝트 서비스를 구성하는 실제 실행 구조 |

이들은 완전히 독립된 작은 라이브러리들은 아니야. 예를 들어 `languages`는 `language`, `project`, `node_runtime`, `settings`, `gpui` 등에 의존해. 반면 `node_runtime`은 그보다 작은 의존 범위를 갖고 있어. **부품마다 재사용하기 좋은 경계가 다르다는 뜻**이지.  

그리고 중요한 발견이 있었어.

**Zed에는 이미 화면 없이 작동하는 `HeadlessProject`와 `HeadlessExtensionStore`가 있다.** 전자는 실제로 `WorktreeStore`, `BufferStore`, `LspStore`, `ToolchainStore` 등을 구성하고, 후자는 `WasmHost`를 만들어 언어 확장 등을 로드해.  

따라서 앞서 이야기한 “Zed의 네이티브 화면을 Electron에 그대로 넣기 어렵다”는 사실과, **“Zed의 내부 기능을 Setdown에서 실행할 수 있는가”는 별개의 문제**야.

화면을 내장하지 않고도 내부 기능을 재사용할 길이 실제 소스에 존재해.

## 2. 강한 도입의 가치는 ‘언어별로 이미 해결한 문제’를 실행 가능한 형태로 물려받는 데 있다

이걸 가장 잘 보여주는 실제 사례가 **Svelte**야.

Setdown을 Setdown으로 개발하려면 `.svelte` 파일 하나에서 자동완성이 되는 것보다 더 많은 것이 필요하잖아. TypeScript 파일에서 Svelte 컴포넌트를 가져오고, 컴포넌트의 타입을 이해하고, 두 종류의 파일 사이를 오가야 해.

Zed의 Svelte 확장 소스를 보니 다음을 실제로 수행하고 있어.

```text
Svelte 확장 실행
    ↓
svelte-language-server 설치
    ↓
typescript-svelte-plugin 설치
    ↓
Node로 Svelte 서버 실행
    ↓
Svelte 서버 초기화 옵션 제공
    ↓
vtsls의 globalPlugins에 Svelte 플러그인 연결
```

구체적으로 `language_server_command()`는 두 npm 패키지를 준비하고, `language_server_additional_workspace_configuration()`는 대상 서버가 `vtsls`일 때 `typescript-svelte-plugin`의 위치를 전달해. 

**이것이 단순 자동 설치와 강한 재사용의 차이야.**

단순히 서버 다운로드 URL을 가져오면 “Svelte 서버가 실행된다”까지만 얻을 수 있어.

하지만 실제 확장과 그 확장을 호출하는 호스트까지 가져오면, **Svelte 지원이 TypeScript 지원에 어떤 설정을 추가해야 하는가**라는 연동 지식도 가져올 수 있지.

물론 이것만으로 Setdown에서 모든 Svelte 작업이 검증됐다는 뜻은 아니야. 하지만 네가 직접 다시 조사하고 구현해야 할 언어별 결합 부분이 이미 소스에 들어 있는 거야.

또 하나 중요한 점은, **그 코드가 모두 `zed-industries/zed` 한 저장소 안에 있는 것은 아니라는 것**이야. Svelte는 별도의 `zed-extensions/svelte` 저장소에서 제공돼. 강한 도입의 대상은 Zed 본체뿐 아니라, 실제로 사용할 언어 확장들의 소스와 버전까지 포함해야 해. [Zed](https://zed.dev/docs/languages/svelte)

## 3. 내가 권하는 최종 구조: Setdown + Zed 기반 Tooling Host

나는 현재 Setdown을 기준으로 다음과 같은 구조를 권하겠어.

여기서 **Tooling Host**는 제안하는 이름이고, 아래 전체 구조가 현재 구현되어 있다는 뜻은 아니야.

```text
Setdown
│
├─ 화면 계층
│   ├─ Svelte 작업 공간
│   ├─ Monaco 코드 편집기
│   ├─ Markdown Reader
│   ├─ 브라우저
│   └─ Jupyter 노트북
│
├─ Setdown 문서·편집 계층
│   ├─ 현재 문서 내용
│   ├─ Undo / Redo
│   ├─ 저장·복구
│   ├─ 여러 화면의 동일 문서 공유
│   └─ 진단 표시·탐색·편집 적용
│
├─ Electron main의 언어 서비스 연결부
│   ├─ 사용자 설정과 프로젝트 문맥 전달
│   ├─ 도구 준비 요청
│   ├─ LSP 프로세스·세션 관리
│   └─ 표준 LSP 통신
│
└─ setdown-tooling-host       ← 별도 Rust 프로세스
    │
    ├─ Zed에서 가져온 NodeRuntime
    ├─ Zed 내장 언어 어댑터
    ├─ Zed 언어 확장 연결 계층
    ├─ Zed WASM 확장 호스트
    ├─ 필요한 환경·프로젝트 탐색 기능
    └─ Setdown 정책·경계 어댑터
```

핵심은 역할 분담이야.

> **Zed에서 가져온 계층은 “어떤 도구를 어떤 환경과 설정으로 준비할 것인가”를 담당한다.  
> Setdown은 “현재 문서를 어떻게 편집하고, 저장하고, 사용자에게 보여줄 것인가”를 담당한다.**

이는 단순한 개념 모방이 아니야. Rust 프로세스 안에서 실제 Zed 구성 요소와 실제 언어 확장이 실행되는 구조니까.

Zed의 `WasmHost`는 실제로 Wasmtime을 사용하고, 확장의 `language_server_command`, 초기화 옵션, workspace 설정 같은 호출을 수행한다. 이 코드를 재사용하면 확장 실행 환경 전체를 JavaScript로 다시 구현하는 일을 피하는 방향을 잡을 수 있어. 

### 왜 별도 Rust 프로세스인가?

**원본 Rust 코드를 가능한 한 유지하기 위해서**야.

Codex에게 Zed의 Rust 코드를 전부 TypeScript로 번역시키면 첫 결과물은 만들 수 있겠지만, 그때부터 Setdown은 자체 번역본을 유지하게 돼. Zed가 버그를 고쳐도 그 수정이 Setdown에 어떤 의미인지 다시 해석해야 하지.

반면 원본 코드를 유지하고 그 바깥에 작은 인터페이스를 두면, 업스트림 변경을 비교하고 받아들이는 기준이 더 명확해져.

별도 프로세스는 Electron과 Rust의 경계를 명확하게 만들기도 해. 통신 규약, 시작과 종료, 장애 복구를 명시적으로 다룰 수 있으니까.

다만 **별도 프로세스로 나눴다고 자동으로 가벼워지거나 보안 샌드박스가 되는 것은 아니야.** 이 선택의 첫 번째 이유는 성능 보장이 아니라, 재사용과 유지보수의 경계야.

## 4. 이 Host는 실행 파일 경로 하나만 반환해서는 안 된다

이 부분이 실제 구현에서 가장 중요해.

앞선 답변의 이런 인터페이스는 출발점으로 너무 좁았어.

```ts
install(version): Promise<string>
```

네가 원하는 강한 도입에서는 “설치된 실행 파일 경로”만으로 언어 지원을 표현할 수 없어.

실행 파일 외에도 실행 인수, 런타임, 환경 변수, 프로젝트 루트, 초기화 옵션, workspace 설정, 다른 서버에 제공할 설정, 확장 버전과 사용자 선택의 관계가 필요하거든.

Zed의 실제 확장 어댑터도 이들을 구분해서 다뤄. `initialization_options()`, `workspace_configuration()`, 다른 언어 서버를 대상으로 하는 추가 설정 등의 호출이 따로 존재해. 

따라서 Setdown과 Host 사이에는 **문맥에 묶인 언어 지원 계획**이 오가야 해.

개념적으로는 이런 내용이야.

```text
프로젝트: Setdown 소스 폴더
언어: TypeScript + Svelte

사용할 도구
  - vtsls
  - svelte-language-server

런타임
  - Setdown 관리 Node

TypeScript 환경
  - 선택된 프로젝트 SDK

서버 간 연결
  - Svelte 확장이 vtsls에 플러그인 설정 제공

설정 출처
  - Setdown 기본값
  - 사용자 선택
  - 프로젝트 설정
  - 확장 제공 설정
```

그리고 이 계획이 만들어진 뒤에는 Setdown이 다른 루트 탐색기로 다시 판단하거나, 다른 Node를 몰래 선택하면 안 돼.

**준비 단계에서 확인한 실행 문맥과 실제 실행 문맥이 같아야 해.**

이렇게 해야 “설정 화면에는 A 환경이 보이는데 실제 분석은 B 환경에서 이루어지는” 문제가 생기지 않아.

### 일회성 설치 결과가 아니라 살아 있는 관계다

Svelte 확장을 켜거나 끄면 TypeScript 서버의 설정도 바뀔 수 있어. 프로젝트 SDK를 바꾸면 연결된 서버의 실행 계획도 다시 계산해야 할 수 있지.

그래서 Host는 설치하고 끝나는 프로그램이 아니라, **현재 프로젝트에 어떤 언어 도구 구성이 필요한지를 관리하는 서비스**가 돼.

그렇다고 키 입력마다 Rust 프로세스를 여러 번 왕복할 필요는 없어. 제안하는 구조에서는 준비와 설정 관리는 Host가 맡고, 통상적인 자동완성·진단 통신은 기존 Setdown의 LSP 경로를 사용할 수 있어.

## 5. 강하게 가져오되, 문서와 Undo의 주인은 당장 바꾸지 않는 것이 좋다

이 지점에서 “강한 도입”과 “최대한 많이 복사하기”를 구분해야 해.

내 추천에서는 다음의 주인은 계속 Setdown이야.

**현재 문서 내용, 저장 상태, Undo, Reader에 전달할 최신 내용, 노트북 셀의 정체성.**

왜냐하면 지금 필요한 것은 언어 지원의 완성도를 높이는 것이지, 문서를 두 시스템이 동시에 관리하게 만드는 것이 아니기 때문이야.

현재 Setdown에는 이미 노트북 셀의 진단을 URI와 revision에 연결하고, 화면에 보이지 않는 셀의 결과도 보존하며, 커널 실행과 정적 분석을 구분하는 구현이 기록되어 있어. 같은 분석 문맥의 노트북들이 서버 프로세스를 공유하는 규칙도 있어. 이런 자산을 언어 도구 도입 때문에 무조건 버릴 이유는 없어. 

권장하는 흐름은 다음과 같아.

```text
사용자가 편집
    ↓
Setdown 문서 모델 변경
    ↓
현재 LSP 세션에 변경 전달
    ↓
언어 서버가 진단·완성·수정안을 반환
    ↓
Setdown이 현재 문서 버전과 대조
    ↓
화면 표시 또는 정식 편집 경로로 적용
```

Zed에서 가져온 Host는 이 흐름에 필요한 도구와 설정을 준비하지만, 뒤에서 같은 파일을 따로 저장하거나 독립적인 Undo 기록을 만들지 않는 거야.

### 기존 구현도 책임에 따라 달라진다

현재 Setdown은 설치된 서버의 탐색과 연결을 지원하지만, 외부 서버의 설치는 수동으로 남겨 두고 있어. 

제안하는 구조를 적용하면 다음처럼 바뀔 수 있어.

| 현재 영역 | 강한 도입 이후의 역할 |
|---|---|
| 서버 카탈로그 | 사용자가 지원 범위와 상태를 보는 제품 카탈로그 |
| 설치본 탐색 | Zed 관리 대상은 Host가 담당하고, 수동 연결 경로는 유지 |
| 서버 선택·설정 | 사용자 의도를 저장하고 Host에 전달하는 정책 계층 |
| LSP 세션 | 기존 문서 동기화·프로세스 관리 기반 유지 |
| Monaco 기능 연결 | 기존 자동완성·탐색·진단·편집 UI 유지 |
| 언어별 특수 처리 | 가능한 것은 실제 Zed 어댑터와 확장 호출로 이동 |

특히 **같은 언어에 대해 기존 탐색기와 새 Host가 서로 다른 결론을 내린 뒤 경쟁하도록 만들면 안 돼.**

지원 대상별로 어느 경로가 책임지는지 명확해야 해.

## 6. `HeadlessProject` 전체를 가져오면 어떻게 되는가?

이것도 실제로 검토할 가치가 있어. 네가 말하는 강한 도입을 더 멀리 밀어붙인 구조니까.

다만 이 경우에는 구조가 달라져.

```text
Setdown 화면
    ↓
Setdown ↔ Zed 프로젝트 연결 계층
    ↓
Zed 프로젝트 엔진
    ├─ WorktreeStore
    ├─ BufferStore
    ├─ ToolchainStore
    ├─ LspStore
    ├─ TaskStore
    └─ 기타 프로젝트 서비스
```

**이때 Setdown은 Zed 프로젝트 엔진의 새로운 프런트엔드에 가까워져.**

이건 단순히 가상의 가능성만은 아니야. 실제 `HeadlessProject`가 저런 서비스들을 구성하고 있고, 원격 프로젝트 통신을 위한 핸들러도 등록하고 있어.  

하지만 여기에는 중요한 함정이 있어.

### Zed 원격 서버는 ‘모든 편집기가 연결하는 LSP 서버’가 아니다

실제 코드는 버퍼 열기, 버퍼 갱신, worktree 추가, 설정 동기화, 확장 동기화 등을 Zed의 프로젝트 RPC로 처리해.

그러므로 다음처럼 할 수는 없어.

```text
Monaco LSP client
    ↓
Zed remote-server 실행
    ↓
Zed의 모든 기능 획득
```

중간에 **Zed의 프로젝트·버퍼 모델을 이해하는 연결 계층**이 필요해. 

이것을 진지하게 채택하면, 현재 편집 내용의 권한을 어디에 둘 것인지 결정해야 해.

Zed 버퍼가 원본이고 Monaco가 표시·입력 역할을 맡게 할 수도 있어. 반대로 Setdown을 원본으로 유지하고 Zed 쪽에 분석용 복사본을 둘 수도 있지.

하지만 후자의 경우 Zed가 수행하는 수정·트랜잭션을 어떻게 Setdown의 편집 기록과 일치시킬 것인지가 큰 과제가 돼. 두 쪽이 독립적으로 수정과 저장을 수행하면 안 되니까.

**따라서 `LspStore` 전체를 가져오는 것은 “더 좋은 설치기를 넣는 것”이 아니라, 문서 편집 기반까지 다시 결정하는 선택이야.**

내 판단은 이래.

> **현재 Setdown의 단기적인 발전을 목표로 한다면, 실제 Rust·WASM 언어 도구 계층은 강하게 재사용하되, 프로젝트 엔진 전체의 소유권까지 당장 넘기지는 않는 편이 좋다.**

이것은 약한 도입이 아니야. **실행되는 원본 코드를 깊게 재사용하면서, 변경 범위는 필요한 책임에 집중하는 도입**이야.

## 7. 사용자에게는 무엇이 달라질까?

가장 중요한 변화는 카탈로그에 표시되는 서버 수가 아니야.

**사용자가 언어 서버를 조립하는 사람이 아니라, 준비된 개발 환경을 사용하는 사람이 되는 것**이야.

### Setdown 자체를 개발할 때

프로젝트를 열고 `.ts`와 `.svelte`를 편집하면, Setdown이 필요한 도구 구성을 준비하도록 설계할 수 있어.

앞서 확인한 Svelte 확장의 설치 코드와 추가 workspace 설정 코드를 실제로 실행한다면, Svelte 서버만 따로 띄우는 것이 아니라 TypeScript 서버와의 연동까지 준비하는 기반을 가져오는 셈이지. 

사용자에게 기본적으로 필요한 표시는 이런 것이야.

> TypeScript·Svelte 분석 준비 중  
> 프로젝트 TypeScript 사용 중  
> 분석 도구 준비 실패 — 기존 설치본 사용 가능

어떤 npm 패키지의 실행 파일 경로를 입력하라는 화면이 먼저 나올 필요는 없어.

다만 실제 성공 기준은 “서버 두 개가 실행됨”이 아니야. `.ts`에서 `.svelte`를 참조하는 경우, 반대 방향의 탐색, 변경 후 진단 갱신 같은 실제 작업이 되어야 해.

### Python 파일과 노트북을 사용할 때

도구 공급은 공통화하되, 일반 파일과 노트북이 같은 방식으로 동작한다고 가정해서는 안 돼.

현재 Setdown 문서에는 일반 파일의 Pyright와 노트북의 basedpyright 사용, `basic` 검사 정책, 환경 선택 및 커널 상태 보존 규칙이 따로 기록되어 있어. 

따라서 Zed 도입 이후에도 다음은 분리해야 해.

**분석기 설치, 분석 대상 Python 환경 선택, 노트북 커널 실행.**

언어 서버를 업데이트했다고 실행 중인 노트북 커널을 재시작해서는 안 돼. 분석 도구가 준비됐다고 프로젝트 의존성까지 설치됐다고 표시해서도 안 되지.

실제로 Zed도 Python 런타임 자체를 번들하지 않는다고 설명해. **언어 도구의 자동 준비와 프로젝트 실행 환경 전체의 자동 준비는 같은 약속이 아니야.** [Zed](https://zed.dev/docs/languages/python)

### Markdown·브라우저 작업을 할 때

내가 권하는 구조라면 이 사용 경험은 거의 그대로 유지하는 것이 맞아.

언어 도구 서비스가 필요한 시점에 시작되도록 하고, 단순한 문서 읽기나 웹 탐색이 수많은 언어 서버의 설치·탐색을 유발하지 않게 하는 거야.

**개발 기능은 깊어지지만, 모든 작업을 개발 프로젝트처럼 만들지는 않는 것.**

그게 Setdown에 맞는 재사용이라고 봐.

## 8. 그렇다고 Zed의 기본값과 동작을 전부 무비판적으로 가져오면 안 된다

여기서 강한 도입의 의미를 정확하게 잡아야 해.

**원본 코드를 재사용한다는 것과, 원본 제품의 모든 정책을 그대로 받아들인다는 것은 다르다.**

### 실제 소스에도 Setdown에서 보완할 지점이 있다

Svelte 확장에는 기존 설치본이 있는 상태에서 새 패키지 설치가 실패하면 기존 것을 사용할 수 있는 코드가 있어.

그런데 그보다 먼저 수행하는 최신 버전 조회는 실패 시 오류를 그대로 반환하는 형태야. 따라서 이 소스만 보고 **“캐시가 있으면 모든 오프라인 상황에서 작동한다”라고 보장할 수는 없어.** 최신 버전 조회 실패와 패키지 설치 실패의 처리가 같지 않기 때문이야. 

이런 부분을 읽고 제품 정책을 정하는 것이 Codex에게 필요한 일이야.

Setdown에는 예를 들어 다음과 같은 정책이 더 적절할 수 있어.

**검증된 버전을 우선 사용하고, 이미 준비된 도구는 네트워크 없이도 실행하며, 사용 중인 정상 세션은 업데이트 때문에 교체하지 않는다.**

이것은 원본 코드를 무시하는 재구현이 아니라, 원본 코드 위에 제품의 운영 조건을 적용하는 일이야. 차이가 있다면 패치와 테스트로 명시하면 돼.

### Zed의 확장이 실행된다고 모든 Zed 기능이 생기지는 않는다

Zed 확장은 언어, 문법, 디버거, 테마 등 여러 종류의 기능을 제공할 수 있어. 하지만 특정 기능의 데이터를 로드하는 것과 Setdown 화면에서 그 기능을 구현하는 것은 별개야. [Zed](https://zed.dev/docs/extensions/developing-extensions)

예를 들어 Tree-sitter 문법을 로드했다고 Monaco의 구문 강조가 자동으로 바뀌지는 않아. 테마 파일을 읽었다고 Setdown의 모든 화면에 정확히 적용되는 것도 아니고.

따라서 초기 제품 표기는 **“검증된 Zed 언어 확장 지원”**처럼 구체적이어야 해. “Zed 확장 완전 호환”이라고 넓게 주장하면 안 돼.

마찬가지로 언어 도구 Host를 가져온다고 VS Code 확장 호스트가 생기는 것도 아니야. 디버깅·원격 개발·프로젝트 편집의 추가 기능 역시 실제로 가져온 서비스와 UI 연결 범위에 달려 있어.

## 9. Codex에게 맡길 일의 중심은 새 구현이 아니라, 실행 경로와 경계를 확정하는 것이어야 한다

Codex에게 단순히 이렇게 시키면 부족해.

> Zed를 참고해서 자동 LSP 설치 기능을 만들어라.

그렇게 하면 기존 Setdown에 새 다운로드 함수를 추가하고 끝나기 쉬워.

이번 목표에 맞는 작업은 오히려 다음과 같아.

### 원본 코드가 실제 제품 실행 경로에 있어야 한다

저장소에 `vendor/zed`가 존재하는 것만으로는 도입이 아니야.

최종 설치본에 들어가는 Host가 어떤 Zed 코드를 빌드했는지, Svelte 지원을 켰을 때 실제 어떤 확장 코드가 실행됐는지 확인할 수 있어야 해.

제안하는 소스 배치는 대략 이렇겠어.

```text
vendor/
  zed/                          고정한 upstream 소스
  zed-extensions/
    svelte/                     고정한 확장 소스

tooling/
  setdown-tooling-host/          Rust 실행 파일과 연결부
  patches/                      upstream과 다른 부분
  supported-tools.lock.json     검증된 도구 구성

apps/desktop/
  .../tooling-host-client.ts     Electron ↔ Host 연결
  .../language/                 기존 LSP·문서 통합
```

실제로 어느 Cargo workspace에 실행 파일을 추가할지는 의존성에 맞춰 결정해야 해. 중요한 것은 폴더 이름이 아니라 **원본, 패치, Setdown 전용 연결부가 구분되는 것**이야.

### ‘지원한다’는 말 대신 작업을 통과시켜야 한다

가장 먼저 검증할 대상은 네 실제 Setdown 프로젝트가 적절해.

깨끗한 Setdown 사용자 데이터에서 시작하고, 시스템에 언어 서버가 없다는 조건으로 도구 준비를 확인해야 해. 다만 프로젝트 자체의 의존성 설치 여부는 별도의 조건으로 기록해야 하지.

그다음 `.ts`를 먼저 여는 경우와 `.svelte`를 먼저 여는 경우 모두에서 TypeScript 플러그인이 연결되는지 확인해야 해. 한 순서에서만 작동하면 제품 사용 중에는 쉽게 실패할 수 있으니까.

편집에서는 자동완성 화면이 뜨는지만 볼 것이 아니라, 미저장 내용의 진단, 정의 탐색, 지원되는 이름 변경, Undo, 저장 이후 상태를 확인해야 해.

장애에서는 오프라인 재실행, 다운로드 중단, 서버 충돌, Host 재시작, 사용자 지정 경로가 사라진 경우를 다뤄야 하고.

**합격 기준은 Zed와 비슷한 화면이 아니라, Zed에서 가져온 도구 구성이 Setdown의 기존 문서 보장과 함께 작동한다는 증거**야.

### 기존 기능을 약화시키면서 성공했다고 판단해서는 안 된다

새 Host를 연결하기 위해 노트북의 버전 검사, 최신 진단 확인, 한국어 입력, Undo 보존 같은 기존 보장을 지우면 안 돼.

이 작업의 결과는 “기존에는 없던 자동 설치가 생겼다”와 동시에 “기존 편집 동작이 유지된다”여야 해.

## 10. 유지보수 비용은 없어지지 않지만, 더 좋은 곳에 집중될 수 있다

강한 재사용의 가장 큰 이익은 첫 구현을 빨리 끝내는 것만이 아니야.

**언어별 문제 해결을 매번 독자적으로 반복하지 않을 가능성이 커진다는 것**이야.

예를 들어 Svelte 플러그인 연결 방식이나 특정 플랫폼의 경로 처리가 바뀌었을 때, Setdown은 자체 구현만 보고 문제를 풀지 않아도 돼. 원본 확장과 호스트의 변경을 확인할 기준이 생기지.

실제로 Zed의 확장 어댑터에는 WASI 환경에서 만들어진 Windows 경로의 선행 슬래시를 보정하는 처리도 들어 있어. 이런 예외 처리는 짧은 설치 함수의 개념도에서는 보이지 않지만, 실제 재사용의 가치를 만들어. 

대신 새로운 부담도 생겨.

Rust 빌드와 플랫폼별 Host 배포, Zed와 확장 API 버전의 조합, 패치 유지, 설치된 도구의 업데이트 정책을 관리해야 해. `remote_server`의 Cargo 의존 목록만 봐도 이 계층이 작은 무의존 바이너리는 아니라는 점은 분명해. 

그래서 이렇게 평가해야 해.

**첫 작업량만 최소화하려면 작은 TypeScript 설치기가 더 간단할 수 있다.  
언어 지원을 계속 넓히면서 실제 upstream 코드를 활용하려면 Rust·WASM Host가 더 강한 구조가 될 수 있다.**

그렇다고 후자가 반드시 더 적은 메모리를 쓰거나 더 빠르다고 말할 수는 없어. 특히 Zed의 네이티브 편집 화면을 가져오는 것이 아니므로, Zed의 렌더링 성능이 Monaco에 그대로 이전되는 것도 아니야.

이 방향의 주된 이득은 **언어 지원 구현의 재사용성과 관리의 일관성**이야.

## 11. 보안과 라이선스도 이 구조의 일부다

자동 설치는 사용자의 일을 대신하는 만큼 실행 권한을 가져오는 기능이야.

Zed의 확장 시스템은 프로세스 실행, 파일 다운로드, npm 설치를 capability로 구분하고, 제한할 수 있도록 설계되어 있어. 이 권한 체계를 가져오는 것은 의미가 있지만, 실제로 허용할 범위는 Setdown이 결정해야 해. [Zed](https://zed.dev/docs/extensions/capabilities)

특히 **WASM 확장의 권한 통제와, 그 확장이 내려받아 실행한 네이티브 언어 서버의 권한은 구분해서 생각해야 해.** “확장이 WASM이므로 모든 실행이 안전하다”는 설명으로 끝내서는 안 돼.

나는 Setdown의 관리 디렉터리, 허용된 공급원, 검증한 확장 목록, 설치·업데이트 기록을 명시적으로 두는 구조를 권하겠어. 웹페이지나 Reader 콘텐츠가 이 Host에 임의 명령을 전달하는 경로도 만들지 않아야 하고.

라이선스는 도입 파일과 패키지별로 추적해야 해. 확인한 `languages`, `node_runtime`, `remote_server`는 `GPL-3.0-or-later`로 표시되어 있고, 공식 안내도 소스 라이선스와 Zed의 서비스·상표 권리를 구분하고 있어. 따라서 필요한 소스를 직접 빌드하는 것과 Zed의 운영 서비스를 그대로 이용하는 것은 따로 검토해야 해.    [Zed](https://zed.dev/software-overview?utm_source=chatgpt.com)

## 최종적으로 Setdown은 무엇이 되는가?

내가 권하는 강한 도입이 성공하면 Setdown은 이렇게 정의할 수 있어.

> **문서와 작업 경험은 Setdown이 소유하고, 언어 도구의 공급과 언어별 연동은 Zed에서 가져온 실제 실행 계층을 이용하는 코드 편집 환경.**

겉으로는 지금의 Setdown이야. Monaco, Reader, 브라우저, 노트북, 통합 탭을 유지해.

하지만 코드 파일을 열었을 때 뒤에서 일어나는 일은 상당히 달라져.

Setdown이 언어마다 독자적인 설치·설정 방법을 계속 만들어내는 대신, **Zed의 내장 어댑터와 언어 확장이 실제로 필요한 도구와 설정을 준비해 주는 구조**가 되는 거지.

그리고 이 방향을 더 멀리 밀어붙여 `HeadlessProject` 전체를 가져온다면, Setdown은 Zed 프로젝트 엔진의 별도 프런트엔드에 가까워질 수 있어. 다만 그때부터는 문서 모델과 편집 처리까지 다루는 더 큰 구조 변경이야.

**내 추천은 전자야. Zed의 실행 가능한 언어 지원 코드는 강하게 가져오고, Setdown의 문서·Undo·노트북 체계는 명확하게 유지하는 것.**

핵심은 “Zed에서 몇 줄 복사할까?”가 아니야.

**“어떤 책임은 이제 Setdown이 새로 구현하지 않고, 실제 Zed 코드를 실행해서 해결할 것인가?”를 결정하는 것.**

그 경계를 잘 잡으면, Setdown은 독자적인 IDE 기반을 계속 발명하지 않으면서도 지금의 사용자 경험을 유지한 채 훨씬 제대로 된 코드 편집기로 성장할 수 있어.
