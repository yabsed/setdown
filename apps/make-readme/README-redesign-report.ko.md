# Setdown 이미지 중심 README 개편 보고서

작성일: 2026년 10월 31일

기능 기준: 현재 저장소 `433f241` 및 연결된 기능 문서

작업 위치: `apps/make-readme`

Setdown의 첫인상을 **웹 자료를 찾고, 문서를 읽고, 코드를 실행하고, 변경 사항을 정리하는 데스크톱 작업 공간**으로 바꾸는 것이 이번 개편의 핵심이다. Markdown의 읽기 경험은 중심에 두되, 브라우저·노트북·터미널·코드·Git이 연결되는 모습을 첫 화면부터 보여준다.

권장 구성은 **대표 전경 1장, 기능별 이미지 10장, 9종 테마의 별도 갤러리**다. 모든 기능을 작은 칸에 넣기보다, 첫 장에서 통합된 작업 공간을 보여주고 이후 장면에서 각 기능을 충분히 크게 보여준다. 이미지는 실제 Setdown에서 촬영하며, 하나의 선형대수 학습 프로젝트로 내용을 통일한다.

## 현재 README와 첨부 화면의 개선점

현재 [README](../../README.md)에는 브라우저, 노트북, 언어 분석, Git, 터미널까지 설명이 추가되어 있다. 다만 소개 문구와 대표 영상이 여전히 Markdown 읽기·편집에 집중하고, 그 뒤에 긴 기술 설명이 이어져 지금의 제품 범위가 시각적으로 전달되지 않는다.

기존 대표 GIF는 약 38.91 MiB이며, 대표 GIF와 기능 GIF 6개의 원본 크기를 합하면 약 96.50 MiB다. 이는 저장소 파일 크기의 합계이며 실제 방문자의 전송량을 측정한 값은 아니다. 새 README에서는 선명한 정지 이미지를 기본으로 삼고, 동작 설명이 필요한 곳에만 짧은 영상을 연결한다.

첨부한 화면은 출발점으로 좋다. 실제 웹사이트와 코드, 터미널, Markdown, Git이 하나의 앱 안에 존재한다는 사실이 분명하다. 다만 대표 홍보 이미지로 쓰기 위해서는 다음을 정리해야 한다.

| 첨부 화면에서 보이는 상태 | 이미지에서 생기는 문제 | 촬영 때 바꿀 상태 |
| --- | --- | --- |
| 폭이 좁은 코드와 웹 패널 | 코드가 자주 줄바꿈되고 웹 본문이 눌린다 | 주요 기능에 화면 폭의 절반 이상을 준다 |
| `python --version`만 실행된 터미널 | 공간은 많이 차지하지만 실제 작업이 보이지 않는다 | Codex가 프로젝트 파일을 다루는 실제 세션을 보여준다 |
| Git의 `No changes.`와 긴 기록 목록 | 현재 무엇을 검토하는지 알기 어렵다 | 의미 있는 변경 2~3개와 선택한 diff를 함께 보여준다 |
| 아래쪽에서 잘린 Markdown과 긴 수식 | 읽기 경험보다 잘림과 스크롤바가 먼저 보인다 | 제목·문단·짧은 수식·그림이 완결되는 위치를 선택한다 |
| 패널별로 크게 다른 확대율 | 화면의 글자 밀도와 시각적 무게가 불균형하다 | 실제 렌더링된 글자 크기를 기준으로 맞춘다 |
| 긴 로컬 경로와 문서명 | 시선을 빼앗고 탭 이름도 식별하기 어렵다 | 촬영용 프로젝트와 짧고 설명적인 파일명을 쓴다 |

사진의 완성도는 배경 장식보다 **앱 안의 콘텐츠, 패널 비율, 읽을 수 있는 글자 크기**에서 먼저 결정된다.

## Firefox에서 참고할 구성

[Firefox 한국어 페이지](https://www.firefox.com/ko/)는 첫 화면의 짧은 가치 제안과 다운로드 행동, 큰 제품 그림, 간단한 기능 묶음, 이미지와 짧은 설명이 이어지는 구성을 사용한다. 여백을 충분히 두고 한 구역에서 한 가지 장점을 전달한다.

Setdown에 적용할 부분은 이 정보의 순서와 시각적 호흡이다. 제안하는 배치는 다음과 같다.

| Firefox의 구성 방식 | Setdown README에 적용할 방식 |
| --- | --- |
| 첫 화면에서 제품의 가치를 설명한다 | 이름 바로 아래에 작업 공간이라는 설명을 한 문장으로 쓴다 |
| 제품 이미지가 첫인상을 만든다 | 실제 Setdown 전경을 크게 보여준다 |
| 기능을 사용자의 이점으로 설명한다 | “Jupyter 지원”보다 “읽은 내용을 바로 실행해 보세요”처럼 쓴다 |
| 기능마다 독립된 시각 자료가 있다 | 웹, Reader, 노트북, Codex, Markdown, 코드, Git에 별도 장면을 준다 |
| 다운로드를 쉽게 찾을 수 있다 | 상단과 하단에 현재 배포 링크를 둔다 |

Firefox의 일러스트 스타일이나 기기 모형을 그대로 옮길 필요는 없다. Setdown에서는 실행된 노트북의 그래프, 잘 조판된 문서, 코드의 문법 색상, Git 변경 표시 자체가 강한 시각 소재다. 얇은 테두리와 절제된 배경만으로 제품 화면이 충분히 돋보이게 만든다.

## 제품 소개와 README 순서

현재 README가 영어이므로 본문도 우선 영어를 유지하는 안을 권한다. 촬영 지시와 제작 기록은 한국어로 관리한다. 아래 문구는 README에 사용할 수 있는 초안이다.

> **Your research and development, in one workspace.**
>
> Browse the web, read and write Markdown, run notebooks, edit code, and manage Git alongside your terminal.

한국어 의미는 “자료 조사부터 개발까지, 하나의 작업 공간에서”다. 기존의 “Write plain. Read beautifully.”는 Markdown 섹션의 문구로 활용할 수 있다.

| 순서 | 섹션 문구 초안 | 독자가 이해해야 할 내용 | 이미지 |
| --- | --- | --- | --- |
| 1 | Your research and development, in one workspace. | 어떤 앱이며 무엇을 함께 할 수 있는가 | 01 대표 전경 |
| 2 | Keep the web beside your work. | 실제 YouTube·Google·나무위키를 작업 옆에서 연다 | 02, 03 |
| 3 | Turn a page into a focused read. | 웹 원문을 Reader로 읽을 수 있다 | 04 |
| 4 | Read an idea. Run the experiment. | `.ipynb`에서 설명·코드·실행 결과가 이어진다 | 05 |
| 5 | Bring your terminal into the workspace. | Codex 같은 CLI를 코드 옆에서 사용한다 | 06 |
| 6 | Write plain. Read beautifully. | Markdown 원문 편집과 읽기를 오간다 | 07 |
| 7 | Edit the code behind your ideas. | 코드 편집과 연결된 언어 기능을 사용한다 | 08 |
| 8 | Review the change. Follow the history. | 변경 검토와 Git 이력을 확인한다 | 09, 10 |
| 9 | Choose a theme for the whole workspace. | 9종 테마로 작업 공간의 분위기를 고른다 | 11 및 전체 갤러리 |
| 10 | Get Setdown | 다운로드와 시작 방법을 찾는다 | 짧은 링크 영역 |

각 기능 섹션은 제목, 설명 1~2문장, 큰 이미지로 구성한다. 한 이미지에 기능 설명문을 길게 박아 넣지 않는다. Markdown 본문에 설명을 두면 검색, 번역, 화면 낭독에도 유리하다.

설치의 최소 조건과 다운로드는 본문에 남긴다. 긴 빌드 방법, 언어 서버 설정, 아키텍처, 개발 검증 명령, 전체 단축키는 기존 `docs/` 문서로 연결하거나 별도 안내로 옮긴다. 기술 내용의 이동은 링크를 유지하면서 진행한다.

## 촬영 콘텐츠를 하나의 프로젝트로 연결하기

촬영용 프로젝트의 이름은 `linear-algebra-lab`으로 제안한다. 첨부 화면에 이미 선형대수 문서와 코드 작업이 있으므로 자연스럽게 이어진다. 장면의 줄거리는 **선형변환을 찾아보고, 작은 실험을 실행하고, 설명과 코드를 개선한 뒤 변경을 검토하는 과정**이다.

| 소재 | 준비할 내용 | 연결되는 장면 |
| --- | --- | --- |
| Google | `linear transformation eigenvectors` 또는 `선형변환 고유벡터` 검색 | 자료 찾기 |
| YouTube | 선형대수 강의의 벡터·행렬 도해가 보이는 장면 | 강의와 실험을 나란히 보기 |
| 나무위키 | 선형대수학 또는 관련 개념 문서의 읽기 좋은 본문 | 실제 웹과 Reader 비교 |
| `experiment.ipynb` | Markdown 설명, 짧은 NumPy 코드, 실행 번호, 고유벡터 결과와 그래프 | 노트북과 대표 전경 |
| `notes.md` | 실험 목적, 짧은 수식, 결과 그림, 간결한 표 | Markdown 읽기와 Git review |
| `transform.py` | 행렬 변환을 계산하는 실제 함수, 타입과 docstring | 코드 편집과 Codex |
| `test_transform.py` | 같은 함수의 동작을 확인하는 작은 검사 | Codex 작업과 변경 검토 |
| 촬영용 Git 저장소 | 준비·실험·설명 개선으로 이어지는 실제 커밋 | Changes와 Graph |

YouTube 후보는 3Blue1Brown의 [고유값 계산 강의](https://www.youtube.com/watch?v=e50Bj7jn9IQ)처럼 도형이 뚜렷한 영상이다. 촬영 프레임에서는 영상 제목과 채널을 식별할 수 있게 두고, 사용한 URL과 시점을 제작 기록에 남긴다. 검색 결과나 영상 이미지를 별도로 그려 넣지 않는다.

나무위키 후보는 [선형대수학](https://namu.wiki/w/%EC%84%A0%ED%98%95%EB%8C%80%EC%88%98%ED%95%99)이다. 실제 로딩과 Reader 추출을 확인한 뒤 사용할 문단을 확정한다. 해당 문서의 구성이 촬영에 적합하지 않으면 현재 추출 문서에서 다룬 [Markdown](https://namu.wiki/w/Markdown) 문서를 후보로 삼는다. 선형대수 시나리오는 웹 장면의 일관성을 위한 제안이며, 불완전하게 추출된 글을 억지로 사용하는 이유가 되어서는 안 된다.

실험에는 임의 장식용 그래프 대신 실제 코드가 만든 2차원 벡터·변환 결과를 사용한다. 축 이름과 범례를 짧게 하고 색을 2~3개로 제한한다. Notebook의 출력, `notes.md`의 그림, Codex가 수정하는 함수가 서로 같은 내용을 가리켜야 한다.

## 필요한 이미지와 구체적인 촬영 구도

아래 이름은 제작할 최종 이미지의 이름이다. 크기는 출력 파일의 픽셀 수보다 먼저 정해야 할 **앱 내부의 논리적 화면 크기**를 기준으로 한다. 고해상도 출력 방법은 뒤의 촬영 규격에서 정한다.

### 01 대표 전경

파일명: `01-workspace-hero.png`

문구: “Your research and development, in one workspace.”

앱 창은 약 1600 × 1000 비율로 잡는다. 왼쪽 약 230px에는 Source Control과 Graph를 둔다. 나머지 본문은 큰 노트북 영역과 오른쪽의 웹·터미널 영역으로 나눈다.

| 위치 | 권장 비중 | 보여줄 상태 |
| --- | --- | --- |
| 왼쪽 사이드바 | 전체 폭 약 14% | 변경 파일 2~3개, 선택한 저장소 이름, 짧은 커밋 기록 |
| 가운데 노트북 | 본문 폭 약 60% | 제목, 짧은 코드, 실행 결과 그래프가 한눈에 보이는 위치 |
| 오른쪽 위 웹 | 본문 폭 약 40%, 오른쪽 높이 약 55% | 나무위키의 제목과 핵심 본문 |
| 오른쪽 아래 터미널 | 오른쪽 높이 약 45% | 짧은 Codex 요청과 실제 완료 요약 |

읽히지 않는 탭을 많이 열지 않는다. `notes.md`와 `transform.py` 등 다음 장면과 연결되는 탭만 남긴다. 대표 전경의 임무는 앱의 전체 구조를 보여주는 것이므로 모든 세부 문장이 읽힐 필요는 없다. 대신 노트북 그래프, 실제 사이트, 터미널, Git이라는 구분은 축소 상태에서도 즉시 보여야 한다.

Codex 화면이 좁아서 로고와 한 줄도 알아보기 어렵다면, 터미널을 억지로 유지하지 말고 대표 전경에서는 노트북과 웹의 가독성을 우선한다. Codex의 본격적인 증명은 06 이미지가 맡는다.

### 02 YouTube와 작업 화면

파일명: `02-web-youtube.png`

문구: “Keep the web beside your work.”

좌우 두 그룹으로 나누고 YouTube에 약 60%, 노트북 또는 짧은 학습 메모에 약 40%를 준다. 영상의 도해가 선명한 순간에 일시 정지하고 마우스를 영상 밖으로 옮긴다. 사이트 이름, 영상 제목, 플레이어와 Setdown 탭·주소 표시줄을 남긴다.

플레이어만 잘라 붙이면 외부 동영상을 문서에 넣은 것처럼 보일 수 있다. 반드시 **Setdown 내부의 웹 탭**임을 알아볼 수 있는 테두리와 탐색 UI가 포함되어야 한다. 광고·로딩·오류 화면이 없는 실제 재생 상태를 확보한 뒤 촬영한다.

### 03 Google과 나무위키

파일명: `03-web-google-namu.png`

Google 검색 결과와 나무위키 문서를 각각 넓게 촬영한다. 두 원본에서 서비스 로고·주소 표시줄·핵심 본문을 포함한 같은 크기의 영역을 골라 위아래 두 단으로 편집한다. 각각 “Google”, “나무위키”라고 외부 캡션을 붙인다. 이는 **별도 장면을 묶은 비교 이미지**임이 드러나야 한다.

Google은 결과 제목 2~3개가 읽히는 위치를, 나무위키는 문서 제목과 짧은 본문이 함께 나오는 위치를 고른다. YouTube·Google·나무위키 세 사이트를 한 창에 세로로 가늘게 배치하는 구도는 피한다. 각 사이트가 실제로 열렸음을 증명할 크기가 필요하다.

### 04 웹 원문과 미리보기

파일명: `04-web-reader.png`

문구: “Turn a page into a focused read.”

여기서 웹 미리보기는 **웹 Reader 모드**를 뜻한다. 같은 나무위키 글의 같은 구간을 원문과 Reader 상태에서 각각 촬영한다. 원문에서 `Esc`로 Reader에 들어가고, 본문 더블클릭으로 원문 위치로 돌아오는 흐름을 사용한다.

두 이미지를 “Original page”와 “Reader mode”로 명확히 구분한다. 원문의 제목·본문 일부와 Reader의 대응 문단이 비교되어야 한다. 사진 안에 없는 단축키 안내는 이미지 아래 본문에 쓴다. 긴 본문을 읽게 할 때는 좌우 두 칸보다 위아래 배치가 낫다.

나무위키 추출기는 현재 SVG를 제거하며 일부 이미지·도식은 Reader에 남지 않을 수 있다. 본문, 표, 보존되는 그림이 깔끔한 구간을 고른다. 빠진 도식을 합성으로 되살리지 않는다. YouTube나 Google 결과 페이지 전체를 읽기 모드로 바꿀 수 있다고 표현하지도 않는다. [웹 Reader 동작과 추출 범위](../../docs/contracts/reading-surfaces.md)

### 05 Jupyter 노트북

파일명: `05-notebook.png`

문구: “Read an idea. Run the experiment.”

거의 전체 폭을 노트북에 준다. 보이는 순서는 **짧은 Markdown 설명 → 8~12줄 정도의 Python 코드 → 실제 실행 결과**다. 그래프는 화면 하단의 약 35~45%를 차지하도록 준비한다. `.ipynb` 탭 이름, Python 환경 선택, 실행 번호가 보이게 한다.

깨끗한 환경에서 실제 셀을 실행하고, 실행한 코드와 결과가 일치하는 상태를 저장한다. 예쁜 그림을 출력 셀 위에 덮어씌우거나 실행하지 않은 결과를 생성하지 않는다. 실행에는 선택한 Python 환경의 `ipykernel`, `jupyter_client`와 예제 의존성이 필요하다.

대표 장면은 Setdown의 자체 노트북 화면으로 촬영한다. JupyterLab의 위젯·디버깅 화면을 추가한다면 외부 도구 연동 장면으로 별도 표기한다. [노트북 기능과 실행 조건](../../docs/notebooks.md)

### 06 터미널에서 사용하는 Codex

파일명: `06-terminal-codex.png`

문구: “Bring your terminal into the workspace.”

왼쪽 약 45%에 `transform.py`, 오른쪽 약 55%에 터미널을 둔다. Codex에 촬영용 프로젝트의 작은 실제 작업을 맡기고, 요청과 변경 결과가 동시에 보이는 지점에서 촬영한다.

요청 예시는 “벡터 변환 함수에 입력 모양 검사를 추가하고, 기존 동작을 확인하는 테스트를 작성해 줘”다. 화면에는 실제 요청, 대상 파일명, 실제 작업 요약이 보여야 한다. 검사 결과를 보여줄 경우 실행 결과와 일치해야 한다. 긴 진행 로그와 반복 출력은 적절히 스크롤해 화면 밖으로 보낸다.

빈 프롬프트, 버전 출력, 출력만 흉내 낸 문자열은 이 장면을 대신할 수 없다. Codex 실행 환경을 준비하고 실제 CLI를 사용한다. 제품 설명은 **“통합 터미널에서 Codex를 사용”**으로 쓰고, Setdown에 Codex가 내장되어 있거나 계정이 함께 제공된다는 인상을 주지 않는다. [터미널 탭과 분할 동작](../../docs/integrated-terminal.md)

### 07 Markdown 편집과 읽기

파일명: `07-markdown.png`

문구: “Write plain. Read beautifully.”

`notes.md`의 같은 구간을 소스 상태와 읽기 상태로 각각 촬영해 비교한다. 짧은 제목, 설명 문단, `Av = λv` 같은 수식, 작은 표와 실험 그림을 사용한다. 편집 쪽에서는 실제 Markdown 문법이, 읽기 쪽에서는 수식과 조판 결과가 분명히 보여야 한다.

완전히 같은 파일의 같은 리비전으로 촬영하고, 원문과 결과를 “Source”와 “Reader”로 표시한다. 화면 전환을 보여주는 보조 영상은 본문 더블클릭 → 한 문장 수정 → `Esc` → 바뀐 내용 확인 순서로 만든다. 이미지에는 마지막으로 완성된 상태를 사용한다.

### 08 코드 편집

파일명: `08-code-editing.png`

문구: “Edit the code behind your ideas.”

`transform.py`를 넓게 열고 타입, 문법 색상, 짧은 docstring이 보이게 한다. 완성 제안이나 함수 정보 팝업 중 **하나만** 실제로 띄운다. 함수 전체를 가리는 큰 팝업이나 의미 없는 오류 표시가 화면의 중심이 되지 않도록 위치를 고른다.

Python 환경과 분석 서비스가 연결된 상태에서 촬영한다. 별도 보조 소재로 `.svelte`의 태그·스크립트·스타일 색상도 사용할 수 있다. 현재 Svelte 문법 색상은 로컬 지원이며 분석 서비스 연결과는 별개다. 화면에 보이는 수준에 맞춰 설명하고 “모든 언어에 모든 IDE 기능 제공” 같은 표현은 쓰지 않는다. [현재 언어 지원](../../docs/language-support.md)

### 09 Git 변경 검토

파일명: `09-git-review.png`

문구: “Review the change.”

왼쪽 약 25%에 Source Control, 나머지에 선택한 Markdown의 렌더링된 비교 화면을 둔다. `notes.md`에서 설명 한 문단, 수식 또는 표의 작은 변경이 보이도록 만든다. 삭제와 추가는 전체 화면을 뒤덮지 않을 정도로 제한한다.

Setdown의 특징을 보여주기 위해 **읽는 모습 그대로의 Markdown 변경 검토**를 우선한다. 코드 diff는 06 또는 별도 갤러리로 보완할 수 있다. Changes와 Staged Changes에 실제 상태가 나타나야 하며, 일반 편집 가능한 Working Tree와 읽기 전용 이력 비교를 구분한다.

### 10 Git 이력

파일명: `10-git-history.png`

문구: “Follow the history.”

Graph가 충분히 읽히도록 사이드바를 넓힌다. 실제 커밋 5~8개가 보이는 짧은 이력을 준비하고, 하나를 선택하여 변경 파일과 해당 비교를 함께 보여준다. 커밋 이름은 `Add transformation experiment`, `Explain eigenvectors`처럼 예제 내용과 연결한다.

곡선을 만들기 위한 장식용 분기를 남발하지 않는다. 분기와 병합이 필요하다면 촬영용 저장소에서 실제로 만든 이력을 쓴다. 과거 커밋 비교는 읽기 전용이다. 그래프 화면 자체에서 checkout·cherry-pick·브랜치 생성을 할 수 있다고 소개하지 않는다. [Git 이력 기능의 범위](../../docs/git-history.md)

### 11 테마 비교

파일명: `11-themes.png`

문구: “Choose a theme for the whole workspace.”

메인 README에는 아래 4종을 같은 크기의 2 × 2 비교로 싣는다. 비교용 장면은 Markdown 읽기와 코드 편집을 나란히 둔 동일한 구도로 고정한다. 탭, 문서 내용, 스크롤, 확대율을 그대로 유지하고 테마만 바꾼다.

## 고급스럽게 보이기 위한 촬영과 편집 규격

### 해상도와 가독성

| 항목 | 권장 기준 |
| --- | --- |
| 대표 전경 | 논리 크기 약 1600 × 1000, 앱 화면 위주 |
| 기능 상세 | 논리 크기 약 1200 × 800에서 시작하고 내용에 맞춰 조절 |
| 실제 캡처 | 가능하면 실제 2배 렌더링, 원본 PNG 보관 |
| README 표시 | 데스크톱 콘텐츠 폭 900~1000px를 가정해 검수 |
| 기능 이미지의 핵심 글자 | 위 표시 폭에서 약 12~14px 이상을 목표로 확대율 조정 |
| 모바일 검수 | 폭 375~430px에서 제목·핵심 시각 요소 식별, 원본 확대 링크 제공 |
| 외부 배경 여백 | 이미지 너비의 약 3~5%, 주요 화면을 압박하지 않는 수준 |
| 편집 효과 | 수평·수직 유지, 절제된 그림자와 테두리, 일관된 여백 |

현재 격리 디스플레이 래퍼의 기본 화면은 1920 × 1080이다. 이 상태에서도 1배 원본으로 구도를 검토할 수 있다. 2배 촬영은 별도 촬영용 디스플레이와 실제 출력 크기를 확인한 뒤 진행한다. 예를 들어 논리 크기 1600 × 1000의 2배 원본은 3200 × 2000이다. 작은 이미지를 확대 저장하거나 DPI 메타데이터만 바꾸는 것은 고해상도 촬영이 아니다.

모든 탭의 확대율을 숫자만 같게 만드는 것보다 실제 글자 크기와 줄 길이를 맞추는 것이 중요하다. 노트북, 터미널, 코드, 웹은 확대 범위와 글꼴이 다를 수 있다. 기존 앱의 확대 기능을 사용해 조정하고, 촬영을 위해 앱 CSS나 글꼴을 몰래 바꾸지 않는다.

### 콘텐츠와 화면 정리

실제 촬영용 파일과 데이터로 깨끗한 화면을 만든다. 계정 아바타, 개인 경로, 비공개 저장소 이름이 없는 별도 앱 프로필을 쓰고, 로컬 프로젝트 이름도 짧게 정한다. 나중에 큰 블러를 덮는 방식보다 처음부터 공개할 수 있는 콘텐츠를 사용하는 편이 완성도가 높다.

툴팁과 메뉴는 기능 설명에 필요한 장면에서만 연다. 평상시 커서는 본문을 가리지 않는 곳에 둔다. 깨진 글꼴, 잘린 수식, 로딩 표시, 미실행 노트북, stale 출력, 가로 스크롤바, 지나치게 긴 탭 이름은 촬영 전에 정리한다.

기본 색감은 어두운 작업 화면과 밝은 읽기 화면을 적절히 섞는다. 모든 장을 검은 화면으로 만들면 노트북 결과와 문서의 조판 차이가 덜 드러난다. 한 섹션 안에서는 배경색과 여백을 맞추고, 테마 비교에서만 색 변화를 적극적으로 보여준다.

### 이미지 가공의 범위

허용할 편집은 크롭, 균일한 축소, 여백, 그림자, 테두리, 이미지 밖의 짧은 캡션이다. 앞뒤 상태나 테마를 묶을 때는 별도 캡처라는 사실을 명시한다. 한 번에 실행 중인 앱 전경은 실제 한 창을 그대로 촬영한다.

제품 UI, 터미널 출력, 실행 결과, Git 상태를 AI 이미지나 수작업으로 재구성하지 않는다. 다른 앱의 노트북 화면을 Setdown 테두리 안에 넣지 않는다. 비스듬한 원근 변형, 광택, 과한 배경 효과도 작은 글자를 읽기 어렵게 하므로 사용하지 않는다.

### 파일 형식과 용량

텍스트가 많은 화면은 PNG를 기본으로 한다. WebP는 실제 GitHub 표시와 글자 가장자리를 비교한 뒤 선택한다. YouTube 영상 내부의 사진 영역 때문에 전체 이미지를 강하게 JPEG 압축하지 않는다.

README에서 처음 불러오는 정지 이미지 합계는 **12 MiB 이내를 편집 목표**로 삼는다. 대표 이미지는 약 1.5 MiB, 기능 이미지는 장당 약 0.5~0.9 MiB를 먼저 목표로 하되 가독성을 해치면서 맞추지 않는다. 용량이 초과하면 중요하지 않은 주변부를 줄이고, 확대 원본과 추가 갤러리를 본문 밖으로 옮긴다.

기존처럼 여러 큰 GIF를 동시에 재생하지 않는다. 웹 Reader 또는 Markdown 전환은 6~10초의 짧은 녹화를 선택 제작하고, 전체 흐름은 약 30~45초 영상 하나로 묶을 수 있다. 기본 표시는 정지 포스터와 영상 링크로 한다. 전환을 설명하는 영상에서는 실제 대기 구간을 잘라 즉각적인 반응인 것처럼 보이게 하지 않는다.

## 실제 촬영 방법

### 격리된 앱 환경

GUI 실행은 프로젝트의 [격리 디스플레이 래퍼](../desktop/scripts/with-isolated-display.sh)를 사용한다. 이 래퍼는 Xvfb뿐 아니라 Wayland 소켓, 런타임 디렉터리와 D-Bus도 분리한다. 사용자의 현재 작업 화면을 점유하지 않는 환경에서 촬영한다.

촬영 스크립트는 다음 형태로 실행하도록 구현한다. 아래의 `capture.mjs`는 후속 제작 대상이며 아직 존재하는 명령은 아니다.

```sh
bash apps/desktop/scripts/with-isolated-display.sh \
  node apps/make-readme/scripts/capture.mjs
```

기존 Electron 실행 도우미를 참고하되 촬영용 앱 데이터 경로와 예제 저장소를 별도로 사용한다. 빌드된 코드와 캡처에 기록한 커밋이 일치해야 한다. 캡처 스크립트는 기존 테스트의 성공·실패 기준과 분리해 작성한다.

### 실제 사이트를 그대로 열기

중요한 구현상의 주의점이 있다. 현재 [브라우저 테스트 fixture](../desktop/test/support/browser/browser-fixture.ts)는 Google 주소를 테스트 HTML로 바꾸고, 로컬 서버에서 연구 페이지·Reader 입력을 제공한다. 이 fixture를 그대로 재사용하면 실제 Google처럼 보이는 주소에서 가짜 페이지를 촬영할 수 있다.

촬영에서는 해당 응답 대체를 사용하지 않는다. YouTube, Google, 나무위키에 실제 네트워크로 접속하고 로고·URL·본문을 확인한다. 로컬 예제 파일은 재현 가능한 준비물이지만, 실제 웹사이트 화면을 대체하는 목업은 만들지 않는다.

사이트가 차단되거나 Reader 추출이 실패하면 그 장면은 미완료로 기록한다. 같은 서비스의 적절한 다른 콘텐츠를 찾거나 정상 접근 상태에서 다시 촬영한다. 오류 화면을 편집으로 숨겨 지원 장면처럼 만들지 않는다.

### 모든 화면 계층이 담기는 캡처

Setdown은 앱 UI와 웹·Markdown의 native view를 함께 사용한다. 따라서 한 renderer의 DOM만 캡처했을 때 제품 전체가 담긴다고 가정하면 안 된다. 실제 창 캡처 또는 격리 디스플레이의 완성 화면 캡처를 우선 검토한다.

첫 촬영은 브라우저, Markdown, 노트북, 터미널이 함께 있는 장면으로 한다. 저장된 PNG를 직접 열어 native view의 빈 영역, 검은 영역, 잘못된 경계가 없는지 확인한 뒤 동일한 방식으로 본 촬영을 진행한다. 문제가 있으면 캡처 방법을 고치고, 누락된 패널을 다른 화면으로 덮어씌우지 않는다.

### 준비 상태를 확인하고 촬영하기

고정된 몇 초의 대기만으로 준비 완료를 판단하지 않는다. 웹의 제목과 주요 이미지, 문서의 수식과 글꼴, 노트북의 실행 완료, 코드의 분석 연결, 터미널의 실제 출력, Git의 선택 항목이 모두 준비되었는지 확인한다.

Reader 전후 비교는 같은 문단을 기준으로 하고, Markdown 비교는 같은 리비전을 사용한다. 테마 비교는 같은 스크롤 위치에서 촬영한다. 원본과 최종 이미지는 각각 보관해 어떤 크롭과 편집을 했는지 추적할 수 있게 한다.

## 제작 디렉터리와 결과물

다음은 후속 제작 시 사용할 권장 구조다. 현재 단계의 결과물은 이 보고서이며, 아래의 예제·스크립트·이미지는 제작할 대상이다.

```text
apps/make-readme/
  README-redesign-report.ko.md
  README.draft.md
  shots.json
  fixtures/
    linear-algebra-lab/
  scripts/
    capture.mjs
    compose.mjs
  raw/
  exports/
  gallery/
```

`shots.json`에는 이미지 ID, 앱 커밋, 테마, 앱 크기, 출력 픽셀 크기, 확대율, 열린 파일과 모드, 웹 URL, 영상 시점, 예제 Git 커밋, 원본 경로를 기록한다. 계정 정보나 인증 토큰은 넣지 않는다. 테스트 저장소의 이력은 재생성 스크립트 또는 별도 보관물로 유지하고, 중첩 `.git` 디렉터리를 무심코 상위 저장소에 추가하지 않는다.

최종 공개 이미지의 위치는 기존 저장소 구조에 맞춰 `docs/assets/readme/`로 통일하는 것을 권한다. `apps/make-readme`는 제작 과정과 원본을 관리하는 공간으로 쓰고, 루트 README는 최종 이미지에 상대 경로로 연결한다. 대용량 원본·앱 프로필·임시 실행 로그는 배포 이미지에 섞지 않는다.

GitHub는 이미지의 상대 경로와 `<picture>` 기반 반응형 이미지를 지원한다. 기본 구현은 표준 Markdown 이미지로 시작하고, 필요할 때만 모바일용 크롭이나 밝은·어두운 배경용 파일을 `<picture>`로 분기한다. 적용 후 실제 GitHub 렌더링을 확인한다. [GitHub 이미지 문법](https://docs.github.com/en/get-started/writing-on-github/getting-started-with-writing-and-formatting-on-github/basic-writing-and-formatting-syntax#images)

README의 세로 흐름을 기본으로 삼는다. 웹사이트의 스크롤 애니메이션이나 복잡한 좌우 레이아웃에 의존하지 않는다. 대표 문구는 본문 텍스트로 남기고, 각 이미지에는 “Setdown에서 선형대수 노트북, 나무위키와 Codex 터미널을 나란히 연 화면”처럼 내용을 설명하는 alt text를 쓴다.

## 제작 순서와 완료 기준

| 단계 | 해야 할 일 | 다음 단계로 넘어가는 기준 |
| --- | --- | --- |
| 1 | 예제 프로젝트, 노트북 환경, 실제 웹 후보, Codex 세션 준비 | 노트북이 실제 실행되고 각 장면의 내용이 서로 연결됨 |
| 2 | 대표 전경, 노트북 상세, 웹 Reader 전후를 먼저 시범 촬영 | native view까지 정상 캡처되며 900px 표시 폭에서 핵심이 식별됨 |
| 3 | 01~11 이미지 촬영과 9종 테마 원본 수집 | 필수 기능마다 실제 상태를 보여주는 원본이 있음 |
| 4 | 크롭·여백·비교 편집과 파일 최적화 | 일정한 시각 규격과 읽을 수 있는 글자 크기 유지 |
| 5 | 이미지에 맞춰 짧은 README 초안 구성 | 상단만 읽어도 제품 범위와 다운로드 위치를 이해할 수 있음 |
| 6 | GitHub 밝은·어두운 화면과 모바일 폭에서 검수 | 이미지, 링크, alt text, 확대 경로, 글자 대비가 정상임 |

최종 검수에서는 다음 질문에 모두 답할 수 있어야 한다.

- 처음 보는 사람이 대표 이미지에서 통합 작업 공간임을 알아보는가?
- YouTube·Google·나무위키 각각 실제 화면이 충분한 크기로 등장하는가?
- 웹 원문과 Reader의 차이가 같은 내용을 통해 드러나는가?
- 노트북에서 코드와 실제 실행 결과가 연결되는가?
- Codex가 이름만 있는 탭이 아니라 실제 터미널 세션으로 보이는가?
- Markdown의 소스와 읽기 화면, 코드 편집, Git 변경 검토와 이력이 각각 보이는가?
- 9종 테마가 정확한 이름으로 제공되고 비교 장면은 동일한가?
- 빈 패널, 잘린 핵심 콘텐츠, 흐린 글자, 모의 사이트, 꾸며 낸 출력이 없는가?
- 이미지 아래의 설명이 촬영된 기능과 실제 제공 범위를 넘어서지 않는가?

스크린샷 제작 중 앱의 미리보기, 테마 CSS, 확대·native bounds 등 동작을 수정해야 한다면 [preview 성능 계약](../../docs/preview-performance-contract.md)에 따라 `npm run test:preview-contract`와 해당 성능 비교를 수행한다. 문서·이미지 제작과 앱 동작 변경을 구분하고, 보기 좋은 한 장으로 기능 검증을 대신하지 않는다.

첫 제작에서는 **대표 전경, 실행 결과가 있는 노트북, 웹 Reader 전후**를 먼저 완성하는 것이 좋다. 이 세 장에서 구도·내용·가독성의 기준을 확정하면 나머지 기능 이미지와 테마 시리즈도 같은 수준으로 맞출 수 있다.
